# Testing Strategy — استراتيجية الاختبار

> يُحدد هذا المعيار استراتيجية الاختبار الشاملة: المستويات، التغطية المطلوبة، قواعد بيانات الاختبار، UAT، ومعايير القبول.
>
> يبني على `EP-TEST-001..003`.
>
> يعتمد على جميع المعايير التفصيلية السابقة كمرجع لما يجب اختباره.
>
> القواعد المرتبطة بحزمة تقنية بعينها تُطبَّق عبر ملف تعريف الحزمة `profiles/<name>/`؛ الافتراضي `laravel-react`.

---

## 0. بندٌ حاكمٌ سابقٌ على كل ما تحته — آلية الإيقاف بقرار

> الافتراضي الصحي أن **كل قواعد هذا المعيار سارية**. لا يُوقَف شقٌّ منه إلا بقرار مالك منتج مُسجَّل، ويكون المعيار حينها **مُعلَّقًا لا مُلغى**.

**شروط أي قرار إيقاف:**

- يسمّي القواعد المُعلَّقة بمعرّفاتها — وهي حصرًا ما يطلب كتابةَ اختبارٍ أو تشغيلَه أو قياسَ تغطية (`TST-001` · `TST-002` · `TST-003` · `TST-004` · `TST-006` · `TST-010` · `TST-011` · البنود 1 · 2 · 6 من `TST-013`).
- يسمّي ما يبقى ولماذا (الجدول أدناه).
- لا يُحذف اختبارٌ من المستودع ولا يُنزَع وسمٌ، و`AS-035` يبقى مفعَّلًا يرفض وسمًا لا سيناريو له.
- كل بوابة مُوقفة تُعلِن نفسها **مُوقفةً** في كل تشغيلة ولا تُتخطّى صمتًا، وتعمل بأمرها المفرد أو بـ`--include-suspended`.
- يُعلَن في تقرير كل شريحة حجم ما كان سيقع في نطاق البند المُعلَّق، كي يُعرف حجم الدَّين يوم يُرفع الإيقاف.
- **العودة بلا إعادة تقييم:** المعيار يستأنف سريانه بحرفه يوم يرفع مالك المنتج الإيقاف.

**ما لا يسقط بأي إيقاف، ولماذا:**

| القاعدة | لماذا لا تسقط |
|---|---|
| `TST-005` — منع البيانات الحقيقية | مناطُها **البيانات الشخصية** لا الاختبار، وتسري على ما هو مكتوبٌ وعلى ما يُكتب يومَ تعود الكتابة — كنظيرتِها في معيار الأمن (لا أسرار ولو في اختبار) |
| `TST-007` · `TST-008` — UAT | بوابةٌ بشريةٌ قبل الإطلاق لا مرحلةٌ في `quality.sh` |
| `TST-009` — عزل الموديول | **قاعدةُ تصميمٍ لا قاعدةُ اختبار.** مفروضةٌ آليًا بـDeptrac و`arch-check.sh` |
| `TST-012` — Penetration Testing | خارج تسلسل البوابات أصلًا |
| `TST-013` بند 3 · بند 4 · بند 5 | تتبع `TST-005` و`TST-007` و`TST-009` الباقيات |

## 2. مستويات الاختبار

### TST-001 — هرم الاختبار

**التصنيف:** `MANDATORY`

| المستوى | النطاق | المسؤول |
|---|---|---|
| **Unit Tests** | منطق الأعمال داخل الموديول | المطور |
| **Integration Tests** | التفاعل بين الموديول والاعتماديات (DB, APIs) | المطور |
| **API Tests** | عقود API — المدخلات، المخرجات، الأخطاء | المطور / QA |
| **E2E Tests** | التدفقات الكاملة من واجهة المستخدم | QA |
| **UAT** | اختبار القبول من مالك المنتج أو ممثليه | مالك المنتج |

### TST-002 — التوزيع المطلوب

**التصنيف:** `RECOMMENDED`

يُتبع نمط هرم الاختبار:

- **كثافة عالية:** Unit Tests (الأسرع والأرخص).
- **كثافة متوسطة:** Integration + API Tests.
- **كثافة محدودة:** E2E Tests (الأبطأ والأغلى).

النسب الدقيقة تُحدد في التنفيذ حسب طبيعة كل موديول.

## 3. تغطية الاختبار لكل موديول

### TST-003 — المناطق الإلزامية

**التصنيف:** `MANDATORY`

كل موديول يجب أن يغطي اختباراته — كحد أدنى:

| المنطقة | مستوى الاختبار | المرجع |
|---|---|---|
| قواعد الأعمال (`BR-*`) | Unit | `business-rules.md` |
| انتقالات الحالة | Unit + Integration | `business-rules.md` |
| عقود API (نجاح + خطأ) | API | `api-contracts.md` |
| المصادقة والصلاحيات | Integration + API | `AUTH-*`, `AUTHZ-*` |
| التحقق من المدخلات | Unit + API | `ECS-005..007` |
| الحالات الحدية (Empty, Error, Permission Denied) | API + E2E | `screens/` |
| التدفقات الرئيسية | E2E | `user-flows.md` |

### TST-004 — المناطق الحساسة

**التصنيف:** `MANDATORY`

المناطق التالية تتطلب تغطية مُكثفة:

| المنطقة | السبب |
|---|---|
| المدفوعات والعمولات | مالية — لا هامش للخطأ |
| العمليات التجارية الرئيسية وانتقالات حالتها | تعقيد الحالات وأثر الأخطاء |
| الصلاحيات الحساسة (`AUTHZ-016`) | أمنية |
| OTP والمصادقة | أمنية |
| الحذف المنطقي و`RETENTION_HOLD` | قانونية |

## 4. بيانات الاختبار

### TST-005 — منع البيانات الحقيقية

**التصنيف:** `PROHIBITED`

لا تُستخدم بيانات حقيقية في الاختبارات (`EP-TEST-003`, `DD-009`, `SEC-013`):

- لا أسماء حقيقية.
- لا أرقام جوال حقيقية.
- لا بيانات مالية حقيقية.
- لا صور أو وثائق حقيقية.

### TST-006 — بيانات الاختبار المُولدة

**التصنيف:** `MANDATORY`

بيانات الاختبار تُولد أو تُخترع:

- Seed Data لأسماء وأرقام وهمية.
- Factory/Fixture لتوليد بيانات متسقة.
- لا تعتمد على ترتيب أو حالة قاعدة بيانات الإنتاج.

---

## 5. UAT — اختبار القبول

### TST-007 — UAT كبوابة نهائية

**التصنيف:** `MANDATORY`

UAT هو بوابة القبول النهائية قبل الإطلاق (`EP-TEST-002`):

- يُنفذ من مالك المنتج أو ممثليه.
- يُنفذ في بيئة Staging بإعدادات مماثلة للإنتاج.
- يغطي التدفقات الرئيسية والبديلة.
- لا يُطلق الموديول دون اجتياز UAT.

### TST-008 — سيناريوهات UAT

**التصنيف:** `MANDATORY`

سيناريوهات UAT تُشتق من:

- معايير القبول في `screens/` (`AC-SCR-*`).
- التدفقات الرئيسية في `user-flows.md`.
- قواعد الأعمال الحرجة.
- الحالات الحدية المعروفة.

---

## 6. التصميم القابل للاختبار

### TST-009 — عزل الموديول

**التصنيف:** `MANDATORY`

كل موديول قابل للاختبار المستقل (`EP-TEST-001`):

- واجهات واضحة قابلة للمحاكاة (Mockable) عند حدود الموديول.
- فصل منطق الأعمال عن البنية التحتية.
- كل اعتمادية خارجية قابلة للاستبدال (SMS, Payment, Storage).

### TST-010 — اختبار التكاملات الخارجية

**التصنيف:** `MANDATORY`

التكاملات الخارجية (بوابة الدفع، مزود SMS، التخزين السحابي) تُختبر عبر:

- Mock/Stub في Unit Tests.
- Sandbox/Test Mode في Integration Tests عند توفره من المزود.
- لا اتصال بأنظمة الإنتاج الخارجية في الاختبارات.

## 7. اختبارات الأمن

### TST-011 — الاختبارات الأمنية الأساسية

**التصنيف:** `MANDATORY`

كل موديول يغطي — كحد أدنى:

| السيناريو | المرجع |
|---|---|
| الوصول بدون مصادقة → `401` | `AUTH-016` |
| الوصول بدون صلاحية → `403` | `AUTHZ-011` |
| محاولة الوصول لبيانات مستخدم آخر → `403` | `AUTHZ-012` |
| تجاوز حدود OTP → `429` | `AUTH-004` |
| إدخال بيانات غير صالحة → `422` | `ECS-005` |
| SQL Injection / XSS → مرفوض | `SEC-014..015` |

### TST-012 — Penetration Testing

**التصنيف:** `RECOMMENDED`

اختبار اختراق شامل يُنفذ قبل الإطلاق التجاري. التوقيت والنطاق يُحددان لاحقًا.
