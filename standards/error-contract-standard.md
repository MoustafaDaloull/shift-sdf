# Error Contract Standard — معيار عقود الأخطاء

> يُحدد هذا المعيار البنية الموحدة لاستجابات الأخطاء عبر جميع واجهات المنصة البرمجية، وقواعد التصنيف والتوطين والأمن.
>
> هذا المعيار **عام وليس خاصًا بموديول**. يلتزم به كل `api-contracts.md` لكل موديول.
>
> **أولوية هذا الملف:** يخضع لأولوية `engineering-principles.md` (§0.3).

---

## 0. الغرض والنطاق

### 0.1 الغرض

يُحدد هذا المعيار:

- التصنيف الموحد لأنواع الأخطاء (`EP-ERR-002`).
- بنية استجابة الخطأ المعيارية.
- قواعد رسائل الخطأ الموجهة للمستخدم (`EP-ERR-003`).
- قواعد الأمن في استجابات الأخطاء (`EP-ERR-001`).
- أكواد الخطأ الداخلية وربطها بأكواد HTTP.
- قواعد توطين الأخطاء.
- قواعد تسجيل الأخطاء.

### 0.2 ما لا يغطيه

- عقود API التفصيلية لكل موديول → `api-design-standard.md` و`api-contracts.md` لكل موديول.
- تسجيل الأخطاء التقني (Structured Logging) → `audit-logging-standard.md`.
- استراتيجية الاختبار → `testing-strategy.md`.

## 2. تصنيف الأخطاء

### ECS-001 — الفئات المعتمدة

**التصنيف:** `MANDATORY`

جميع الأخطاء في المنصة تُصنف في خمس فئات (`EP-ERR-002`):

| الفئة | الكود المختصر | التعريف | مثال |
|---|---|---|---|
| **خطأ تحقق** | `VALIDATION` | البيانات المُدخلة لا تستوفي قواعد التحقق | حقل إلزامي فارغ، صيغة جوال غير صحيحة |
| **انتهاك قاعدة عمل** | `BUSINESS_RULE` | العملية تخالف قاعدة عمل معتمدة | الطلب غير قابل للإلغاء في حالته، العرض منتهٍ |
| **خطأ صلاحية** | `AUTHORIZATION` | المستخدم لا يملك الصلاحية المطلوبة | محاولة حذف سجل لا يملكه، صلاحية مرفوضة |
| **خطأ نظام** | `SYSTEM` | خطأ داخلي غير متوقع في النظام | فشل اتصال بقاعدة البيانات، خطأ غير معالج |
| **خطأ تكامل** | `INTEGRATION` | فشل في تكامل خارجي | فشل بوابة الدفع، فشل إرسال SMS |

### ECS-002 — عدم خلط الفئات

**التصنيف:** `MANDATORY`

لا يجوز تصنيف خطأ في أكثر من فئة. إذا تداخلت الحالة، يُختار التصنيف الأقرب لجذر السبب:

- فشل الدفع بسبب بطاقة منتهية → `VALIDATION` (بيانات غير صالحة من المستخدم).
- فشل الدفع بسبب عطل في بوابة الدفع → `INTEGRATION`.
- رفض الدفع بسبب تجاوز حدّ مبلغ تحكمه قاعدة عمل → `BUSINESS_RULE`.

## 3. بنية استجابة الخطأ

### ECS-003 — البنية المعيارية

**التصنيف:** `MANDATORY`

كل استجابة خطأ من API تتبع البنية التالية:

```text
{
  "success": false,
  "error": {
    "code": "ERR-[MODULE]-[CATEGORY]-###",
    "type": "VALIDATION | BUSINESS_RULE | AUTHORIZATION | SYSTEM | INTEGRATION",
    "message": "رسالة مفهومة للمستخدم بلغته",
    "details": [ ... ],
    "trace_id": "معرّف فريد للطلب"
  }
}
```

### ECS-004 — حقول الاستجابة

**التصنيف:** `MANDATORY`

| الحقل | الإلزامية | الوصف |
|---|---|---|
| `success` | إلزامي | دائمًا `false` في استجابات الخطأ |
| `error.code` | إلزامي | كود خطأ فريد ثابت — لا يتغير بتغير اللغة |
| `error.type` | إلزامي | إحدى الفئات الخمس (`ECS-001`) |
| `error.message` | إلزامي | رسالة بلغة المستخدم (`ECS-009`) |
| `error.details` | اختياري | قائمة تفاصيل إضافية — تُستخدم لأخطاء التحقق المتعددة |
| `error.trace_id` | إلزامي | معرّف فريد يربط الخطأ بالسجل الداخلي (`EP-OBS-004`) |

### ECS-005 — بنية التفاصيل (details)

**التصنيف:** `MANDATORY WHEN APPLICABLE`

يُستخدم حقل `details` عندما يتضمن الخطأ أكثر من نقطة فشل (مثل أخطاء تحقق متعددة):

```text
"details": [
  {
    "field": "phone_number",
    "code": "ERR-CUS-VAL-002",
    "message": "صيغة رقم الجوال غير صحيحة"
  },
  {
    "field": "email",
    "code": "ERR-CUS-VAL-003",
    "message": "البريد الإلكتروني مطلوب"
  }
]
```

## 4. أكواد الأخطاء

### ECS-006 — صيغة كود الخطأ

**التصنيف:** `MANDATORY`

```text
ERR-[MODULE_CODE]-[CATEGORY_CODE]-###
```

حيث:

- `MODULE_CODE`: كود الموديول من `module-registry.md` (مع مراعاة `identifier-alias-map.md`).
- `CATEGORY_CODE`: اختصار الفئة:

| الفئة | الكود |
|---|---|
| `VALIDATION` | `VAL` |
| `BUSINESS_RULE` | `BIZ` |
| `AUTHORIZATION` | `AUZ` |
| `SYSTEM` | `SYS` |
| `INTEGRATION` | `INT` |

- `###`: رقم تسلسلي بثلاث خانات يبدأ من `001`.

أمثلة:

```text
ERR-CUS-VAL-001    خطأ تحقق في موديول العملاء
ERR-ORD-BIZ-003    انتهاك قاعدة عمل في الطلبات
ERR-INV-INT-001    خطأ تكامل في الفواتير
ERR-SYS-SYS-001    خطأ نظام عام (لا ينتمي لموديول محدد)
```

### ECS-007 — أكواد الأخطاء العامة

**التصنيف:** `MANDATORY`

تُعرَّف أكواد أخطاء عامة لا تنتمي لموديول محدد تحت الكود `SYS`:

| الكود | الوصف |
|---|---|
| `ERR-SYS-VAL-001` | حقل إلزامي مفقود |
| `ERR-SYS-VAL-002` | صيغة بيانات غير صالحة |
| `ERR-SYS-VAL-003` | قيمة خارج النطاق المسموح |
| `ERR-SYS-VAL-004` | مسار غير موجود أو طريقة HTTP غير مدعومة — تُحفظ الحالةُ الحقيقية `404`/`405` |
| `ERR-SYS-BIZ-001` | تجاوز حدّ المعدّل — الحالة `429` (`API-025`) والفئة `BUSINESS_RULE`: رسالتُه «تجاوزتَ حدَّ المحاولات» تصل ويُسجَّل تحذيرًا لا عُطلًا |
| `ERR-SYS-AUZ-001` | غير مصادق (Unauthenticated) |
| `ERR-SYS-AUZ-002` | غير مصرح (Unauthorized) |
| `ERR-SYS-AUZ-003` | جلسة منتهية |
| `ERR-SYS-SYS-001` | خطأ داخلي غير متوقع |
| `ERR-SYS-SYS-002` | الخدمة غير متاحة مؤقتًا |
| `ERR-SYS-INT-001` | فشل تكامل خارجي عام |

### ECS-008 — ربط أكواد HTTP

**التصنيف:** `MANDATORY`

| فئة الخطأ | كود HTTP الافتراضي | ملاحظات |
|---|---|---|
| `VALIDATION` | `422 Unprocessable Entity` | بيانات غير صالحة — الصيغة مفهومة والمحتوى مرفوض. `400` تبقى للطلب المشوَّه الذي لا يُفهَم أصلًا: JSON فاسد أو ترويسة ناقصة |
| `BUSINESS_RULE` | `409 Conflict` أو `422 Unprocessable Entity` | العملية تخالف قاعدة عمل |
| `AUTHORIZATION` | `401 Unauthorized` أو `403 Forbidden` | `401` للمصادقة، `403` للصلاحية |
| `SYSTEM` | `500 Internal Server Error` | خطأ داخلي |
| `INTEGRATION` | `502 Bad Gateway` أو `503 Service Unavailable` | فشل مزود خارجي |

> كود HTTP هو مؤشر عام. الكود الداخلي (`ERR-*`) هو المعرّف الدقيق للخطأ.
>
> **استثناءٌ مُعلَن:** `ERR-SYS-VAL-004` من فئة `VALIDATION` يحمل الحالةَ الحقيقية `404` أو `405` لا `422`، لأن الخطأ في العنوان أو الطريقة لا في المحتوى.
>
> **استثناءٌ مُعلَن:** `ERR-SYS-BIZ-001` من فئة `BUSINESS_RULE` يحمل `429 Too Many Requests` لا `409`/`422`، لأن `API-025` يسمّي حالةَ تجاوز حدّ المعدّل؛ والفئةُ متوقَّعةٌ كي تصل رسالتُه ولا يُسجَّل تجاوزُ الحدّ عُطلًا.

## 5. أمن استجابات الأخطاء

### ECS-009 — منع تسريب المعلومات الداخلية

**التصنيف:** `MANDATORY`

لا تتضمن استجابة الخطأ الموجهة للمستخدم (`EP-ERR-001`):

1. تفاصيل قاعدة البيانات (أسماء جداول، أعمدة، استعلامات SQL).
2. مسارات الملفات الداخلية.
3. Stack Traces أو تفاصيل الاستثناء التقنية.
4. أسماء خوادم أو عناوين IP داخلية.
5. إصدارات المكتبات أو إطار العمل.
6. تفاصيل بنية النظام الداخلية.
7. بيانات مستخدمين آخرين.

### ECS-010 — الخطأ العام للنظام

**التصنيف:** `MANDATORY`

عند حدوث خطأ نظام غير متوقع (`SYSTEM`):

- يتلقى المستخدم رسالة عامة واضحة (مثل: "حدث خطأ غير متوقع. يُرجى المحاولة لاحقًا.").
- يُسجَّل الخطأ الكامل في السجل التقني الداخلي مع `trace_id`.
- لا تُعرض أي تفاصيل تقنية للمستخدم.

### ECS-011 — أخطاء الصلاحية

**التصنيف:** `MANDATORY`

عند رفض الوصول (`AUTHORIZATION`):

- لا يُكشف ما إذا كان المورد موجودًا أم لا (لتجنب تعداد الموارد).
- لا تُذكر الصلاحية المطلوبة بالتحديد إلا إذا كان ذلك مفيدًا وآمنًا.
- الرسالة واضحة: "ليس لديك صلاحية لتنفيذ هذا الإجراء."

## 6. توطين رسائل الأخطاء

### ECS-012 — لغة الرسالة

**التصنيف:** `MANDATORY`

رسالة الخطأ الموجهة للمستخدم (`error.message` و`details[].message`) تُعرض بلغة المستخدم (`EP-ERR-003`، `EP-L10N-005`):

- تُحدد اللغة من لغة حساب المستخدم.
- إذا لم يكن المستخدم مسجلاً → اللغة الافتراضية للمنصة (الافتراضي في الإطار: العربية).

### ECS-013 — قواعد صياغة الرسالة

**التصنيف:** `MANDATORY`

رسالة الخطأ يجب أن تكون (`EP-ERR-003`):

1. **واضحة** — تشرح ما حدث بلغة مفهومة.
2. **مفيدة** — تُوجِّه المستخدم لما يمكنه فعله لتصحيح المشكلة.
3. **خالية من المصطلحات التقنية** — لا "null reference"، لا "constraint violation"، لا "timeout exception".
4. **خالية من تفاصيل أمنية** — لا تكشف بنية النظام.
5. **محترمة** — لا تُلقي اللوم على المستخدم.

أمثلة:

| غير مقبول | مقبول |
|---|---|
| `NullPointerException at UserService.java:42` | حدث خطأ غير متوقع. يُرجى المحاولة لاحقًا. |
| `UNIQUE constraint failed: users.phone` | رقم الجوال مسجل مسبقًا. |
| `Forbidden` | ليس لديك صلاحية لتنفيذ هذا الإجراء. |
| `Invalid input` | يُرجى تعبئة جميع الحقول المطلوبة. |
| `Order not in ACTIVE state` | الطلب غير متاح للتعديل حاليًا. |

### ECS-014 — ثبات الكود مقابل تغير الرسالة

**التصنيف:** `MANDATORY`

- `error.code` (مثل `ERR-ORD-BIZ-003`) ثابت ولا يتغير — يُستخدم برمجيًا.
- `error.message` قابل للتعديل والتحسين — يُستخدم للعرض البشري.
- لا يعتمد أي منطق برمجي على نص الرسالة — يعتمد فقط على `error.code` أو `error.type`.

## 7. أخطاء التحقق

### ECS-015 — التحقق المجمع

**التصنيف:** `RECOMMENDED`

عند وجود أكثر من خطأ تحقق في نفس الطلب، يُفضَّل إرجاع جميع الأخطاء دفعة واحدة في `details` بدلاً من إرجاع الخطأ الأول فقط — لتقليل عدد المحاولات.

### ECS-016 — ربط الخطأ بالحقل

**التصنيف:** `MANDATORY WHEN APPLICABLE`

أخطاء التحقق المرتبطة بحقل محدد يجب أن تتضمن اسم الحقل في `details[].field` لتمكين الواجهة من إظهار الخطأ بجانب الحقل المعني.

---

## 8. أخطاء قواعد العمل

### ECS-017 — ربط الخطأ بقاعدة العمل

**التصنيف:** `RECOMMENDED`

عند رفض عملية بسبب قاعدة عمل، يُوصى بتوثيق مرجع القاعدة (`BR-*`) في التوثيق الداخلي للخطأ (وليس في الاستجابة للمستخدم). هذا يسهل تتبع الخطأ لاحقًا.

### ECS-018 — أخطاء الحالة

**التصنيف:** `MANDATORY`

عند رفض عملية بسبب حالة الكيان (مثل محاولة تعديل طلب مكتمل):

- الرسالة توضح أن الإجراء غير متاح في الحالة الحالية.
- لا تُكشف تفاصيل آلة الحالة الداخلية.

---

## 9. أخطاء التكامل

### ECS-019 — إخفاء تفاصيل المزود

**التصنيف:** `MANDATORY`

أخطاء التكامل الخارجي (`INTEGRATION`) لا تُسرِّب:

- اسم المزود الفعلي (لا "`<Provider>` returned error 422").
- رسالة خطأ المزود الخام.
- تفاصيل بروتوكول التكامل.

الرسالة للمستخدم عامة: "تعذر إتمام العملية حاليًا. يُرجى المحاولة لاحقًا." أو رسالة أكثر تحديدًا دون كشف المزود.

### ECS-020 — تسجيل خطأ التكامل

**التصنيف:** `MANDATORY`

أخطاء التكامل تُسجَّل بالكامل في السجل التقني الداخلي:

- اسم المزود.
- الاستجابة الخام.
- كود الخطأ.
- `trace_id`.
- الوقت والمدة.
- عدد محاولات إعادة المحاولة.

## 10. تسجيل الأخطاء

### ECS-021 — ما يُسجَّل داخليًا

**التصنيف:** `MANDATORY`

كل خطأ يُسجَّل في السجل التقني الداخلي يتضمن:

| الحقل | الإلزامية | الوصف |
|---|---|---|
| `trace_id` | إلزامي | المعرّف الفريد للطلب |
| `timestamp` | إلزامي | وقت الحدوث |
| `error_code` | إلزامي | كود الخطأ (`ERR-*`) |
| `error_type` | إلزامي | الفئة |
| `module` | إلزامي | الموديول المصدر |
| `endpoint` | إلزامي | نقطة النهاية (API endpoint) |
| `actor_id` | إلزامي عند التوفر | معرّف المستخدم |
| `request_summary` | إلزامي | ملخص الطلب (بدون بيانات حساسة) |
| `stack_trace` | إلزامي لـ `SYSTEM` | تفاصيل الاستثناء الكاملة |
| `integration_response` | إلزامي لـ `INTEGRATION` | استجابة المزود الخام |
| `severity` | إلزامي | `ERROR` أو `WARNING` |

### ECS-022 — أخطاء Audit Log

**التصنيف:** `MANDATORY`

الأخطاء التالية تُسجَّل أيضًا في Audit Log عبر موديول سجل التدقيق (بالإضافة للسجل التقني):

- فشل عملية مالية (كيانات المدفوعات).
- رفض صلاحية على عملية حساسة.
- فشل تكامل بوابة الدفع.
- فشل في انتقال حالة كيان جوهري.

> المرجع: `EP-AUD-001`.

## 11. إعادة المحاولة والأخطاء

### ECS-023 — أخطاء قابلة لإعادة المحاولة

**التصنيف:** `MANDATORY`

يُميَّز بين الأخطاء القابلة وغير القابلة لإعادة المحاولة:

| الفئة | قابل لإعادة المحاولة | ملاحظات |
|---|---|---|
| `VALIDATION` | لا | يحتاج تصحيح المدخلات |
| `BUSINESS_RULE` | لا | يحتاج تغيير الظروف |
| `AUTHORIZATION` | لا | يحتاج صلاحية مختلفة |
| `SYSTEM` | نعم (بحذر) | قد يكون مؤقتًا |
| `INTEGRATION` | نعم | وفق سياسة إعادة المحاولة (`EP-RETRY-001..004`) |

### ECS-024 — إشارة إعادة المحاولة

**التصنيف:** `RECOMMENDED`

يُوصى بتضمين حقل `retryable: true/false` في استجابة الخطأ لتوجيه المستهلك.

---

## 12. بوابة الجودة

### ECS-025 — قائمة التحقق

**التصنيف:** `MANDATORY`

عند مراجعة عقود API لأي موديول، يُتحقق من:

| # | البند | المرجع |
|---|---|---|
| 1 | كل خطأ مصنف في إحدى الفئات الخمس | `ECS-001` |
| 2 | كل خطأ يحمل كود `ERR-[MODULE]-[CATEGORY]-###` | `ECS-006` |
| 3 | لا تتضمن أي رسالة خطأ معلومات تقنية داخلية | `ECS-009` |
| 4 | رسائل الخطأ بلغة المستخدم وواضحة | `ECS-012`، `ECS-013` |
| 5 | أخطاء التحقق ترتبط بالحقل المعني | `ECS-016` |
| 6 | أخطاء التكامل لا تُسرِّب اسم أو تفاصيل المزود | `ECS-019` |
| 7 | أخطاء الصلاحية لا تكشف وجود الموارد | `ECS-011` |
| 8 | كل خطأ يُسجَّل في السجل التقني الداخلي | `ECS-021` |
| 9 | الأخطاء الحساسة تُسجَّل في Audit Log | `ECS-022` |
| 10 | البنية تتطابق مع المعيار (`ECS-003`) | `ECS-003` |
