# Engineering Principles — المبادئ الهندسية العامة

> هذا الملف هو أعلى معيار هندسي عام في المشروع — الدستور الهندسي.
>
> يُحدد المبادئ الثابتة والقواعد الحاكمة التي تسري على **جميع الموديولات** وجميع المخرجات الهندسية اللاحقة. لا يُحدد تفاصيل تنفيذ أو عقود تقنية — تلك تُوثَّق في المعايير التفصيلية اللاحقة (§29).
>
> **أولوية هذا الملف:** أي تعارض بين مبدأ هندسي في هذا الملف وقرار معتمد (`DEC-*`) في `project-decisions.md` — يسود القرار المعتمد دائمًا. هذا الملف لا يُلغي ولا يُعدِّل ولا يُعيد فتح أي قرار من Phase 0 أو أي مرحلة سابقة.
>
> القواعد المرتبطة بحزمة تقنية بعينها تُطبَّق عبر ملف تعريف الحزمة `profiles/<name>/`؛ الافتراضي `laravel-react`.

---

## 0. الغرض والنطاق

### 0.1 الغرض

يُحدد هذا المستند المبادئ الهندسية التي تحكم:

- حدود الموديولات وملكيتها.
- ملكية البيانات والوصول العابر للموديولات.
- المعالجة المتزامنة وغير المتزامنة.
- حدود المعاملات والذرّية.
- منع التكرار (Idempotency).
- التحكم في التزامن (Concurrency Control).
- آلات الحالة وملكية الانتقالات.
- معالجة الأخطاء والاستثناءات.
- أمان التكاملات الخارجية.
- الأمن بالتصميم.
- المصادقة والتفويض.
- قابلية التدقيق والمراقبة.
- إعادة المحاولة ومعالجة الفشل.
- الوسائط والملفات.
- الجاهزية السحابية.
- الاحتفاظ بالبيانات والحذف.
- التعريب والتوطين.
- مبادئ تصميم الواجهات البرمجية.
- القابلية للاختبار والتتبع.
- سلوك وكلاء الذكاء الاصطناعي الهندسيين.
- أمان التغيير.

### 0.2 ما لا يُحدده هذا المستند

لا يحتوي هذا الملف ولا يُنشئ أيًا مما يلي:

```text
- مخطط قاعدة بيانات فعلي (Physical DB Schema)
- أسماء حقول نهائية (Exact Field Names)
- نقاط نهاية API محددة (Concrete API Endpoints)
- هياكل DTO تفصيلية
- مخططات أحداث (Event Schemas)
- كود إطار عمل (Framework Code)
- Terraform أو CloudFormation أو أي بنية تحتية ككود
- CI/CD Pipelines
- تفاصيل تنفيذ الواجهة الأمامية (Frontend Implementation)
- سلوك أعمال خاص بموديول معين
- قواعد أعمال المدفوعات أو عمليات المجال الحساسة
- تكوين موارد سحابية محدد
```

### 0.3 مصادر الحقيقة والأولوية

ترتيب الأولوية عند حسم أي تعارض بين هذا الملف ومراجع أخرى:

1. تعليمات مالك المنتج الحالية والقرارات المعتمدة في `project-decisions.md`.
2. وثيقة BRD (`brd.md`).
3. الأسئلة والإجابات المعتمدة مع مالك المنتج.
4. سجل الموديولات `module-registry.md`.
5. الوثائق التحليلية للموديول (requirements، business-rules، …).
6. خريطة تكافؤ المعرّفات `identifier-alias-map.md`.
7. قواعد العمل العالمية `business-rules-global.md`.
8. المعجم `glossary.md`.
9. وثيقة المعمارية `architecture.md`.
10. **هذا الملف** (`engineering-principles.md`).

> المرجع: وثيقة الحوكمة الهندسية (`CLAUDE-ENGINEERING.md`).

## 1. نظام تصنيف المبادئ

كل مبدأ أو قاعدة في هذا المستند يحمل أحد التصنيفات التالية:

| التصنيف | المعنى | التأثير |
|---|---|---|
| `MANDATORY` | إلزامي — ينطبق دائمًا على جميع الموديولات | لا يجوز مخالفته إلا بقرار مالك منتج معتمد (`DEC-*`) |
| `MANDATORY WHEN APPLICABLE` | إلزامي عند انطباق الشرط المذكور | لا ينطبق إذا لم يتوفر الشرط |
| `RECOMMENDED` | توصية مهنية — يُتَّبع ما لم يكن هناك سبب تقني أو عملي مبرر | يجوز الخروج عنه مع التوثيق |
| `PROHIBITED` | ممنوع — لا يُنفَّذ في أي حالة | لا يجوز مخالفته إلا بقرار مالك منتج معتمد (`DEC-*`) |
| `DEFERRED TO LATER STANDARD` | يُحسم في معيار تفصيلي لاحق | لا يُخترع بديل مؤقت |
| `OPEN — DECISION REQUIRED` | يتطلب قرارًا من مالك المنتج أو جهة معتمدة | لا يُبنى عليه حتى يُحسم |

## 2. معمارية التطبيق

### EP-ARCH-001 — النمط المعماري

**التصنيف:** `MANDATORY`

النمط المعماري المعتمد هو **`Modular Monolith / Modular Services Ready`** (`architecture.md`). يُثبَّت النمط والحزمة التقنية بسجل قرار معماري معتمد (ADR) في `standards/adr/` قبل البناء عليهما في المعايير التفصيلية.

> **الحزمة الافتراضية في الإطار** (ملف التعريف `laravel-react`): Modular Monolith · Laravel · MySQL · Redis · فصل Frontend/Backend · React + TypeScript + Vite للواجهة.

تسري مع هذا النمط المبادئ التالية:

### EP-ARCH-002 — الفصل المنطقي الداخلي

**التصنيف:** `MANDATORY`

يجب تنظيم الكود داخليًا بحيث يكون لكل موديول نطاق منطقي مستقل يشمل:

- طبقة أعمال خاصة بالموديول.
- نماذج بيانات محصورة داخل حدود الموديول.
- واجهة برمجية أو عقد داخلي يُحدد كيف يتعامل بقية النظام مع هذا الموديول.
- اعتماديات صريحة ومعروفة على الموديولات الأخرى.

### EP-ARCH-003 — الجاهزية للفصل المستقبلي

**التصنيف:** `MANDATORY`

يُصمَّم كل موديول بحيث يمكن فصله لاحقًا كخدمة مستقلة دون إعادة بناء كاملة. يتطلب ذلك:

- عدم الاعتماد على حالة مشتركة في الذاكرة بين الموديولات.
- تجنب الاستعلامات المباشرة عبر حدود الموديولات على مستوى قاعدة البيانات.
- الاتصال بين الموديولات عبر عقود محددة وليس عبر تفاصيل التنفيذ الداخلية.

> المرجع: `architecture.md` — "Future Service Separation".

### EP-ARCH-004 — الوعي بالتكلفة

**التصنيف:** `MANDATORY`

لا تُستخدم حلول مبالغ بها قبل التحقق من الاستخدام الفعلي. الأولوية في المرحلة الأولى (MVP) هي الإطلاق الفعّال بتكلفة معقولة مع قابلية التوسع عند الحاجة.

> المرجع: `architecture.md` — "Cost-aware Architecture".

## 3. حدود الموديولات وملكيتها

### EP-MOD-001 — الموديول ككيان ملكية

**التصنيف:** `MANDATORY`

كل موديول مسجَّل في `module-registry.md` هو وحدة ملكية مستقلة. لا يجوز:

- إنشاء موديول جديد دون موافقة صريحة من مالك المنتج.
- دمج موديولين أو تقسيم موديول.
- نقل وظيفة بين موديولين دون Change Request معتمد.
- إعادة تسمية أو تغيير مرحلة أو أولوية موديول.

### EP-MOD-002 — الموديول المالك للوظيفة المشتركة

**التصنيف:** `MANDATORY`

لكل وظيفة مشتركة موديول مالك واحد فقط. يُثبَّت جدول الملكية في `module-registry.md` للمشروع، ويشمل — كحد أدنى — الوظائف المشتركة التالية:

| الوظيفة المشتركة | الموديول المالك |
|---|---|
| الهوية، تسجيل الدخول، OTP، الأدوار، الصلاحيات | `{{MODULE_CODE}}` — موديول الهوية والوصول |
| الملف الشخصي ووثائق التوثيق | `{{MODULE_CODE}}` — موديول الملف الشخصي |
| رفع الوسائط والملفات | `{{MODULE_CODE}}` — موديول الوسائط |
| البحث والفلترة | `{{MODULE_CODE}}` — موديول البحث |
| المدفوعات، الرسوم، العمولات | `{{MODULE_CODE}}` — موديول المدفوعات |
| الإشعارات | `{{MODULE_CODE}}` — موديول الإشعارات |
| عمليات الإدارة | `{{MODULE_CODE}}` — موديول الإدارة |
| Audit Log | `{{MODULE_CODE}}` — موديول سجل التدقيق |
| التقارير ولوحات المتابعة | `{{MODULE_CODE}}` — موديول التقارير |
| الإعدادات والبيانات المرجعية | `{{MODULE_CODE}}` — موديول الإعدادات |
| المحتوى والسياسات القانونية | `{{MODULE_CODE}}` — موديول المحتوى |
| التكاملات | `{{MODULE_CODE}}` — موديول التكاملات |
| السحابة، المراقبة، النسخ الاحتياطي | `{{MODULE_CODE}}` — موديول البنية والتشغيل |

> المرجع: `CLAUDE.md`، `module-registry.md`.

### EP-MOD-003 — حدود الاستهلاك

**التصنيف:** `MANDATORY`

عندما يستهلك موديول وظيفة مشتركة مملوكة لموديول آخر:

1. يُشير إلى الموديول المالك.
2. يوضح سبب أو حدث الاستهلاك.
3. يحدد حدود مسؤولية الموديول المستهلك.
4. لا يكرر قواعد العمل المملوكة للموديول الآخر.
5. لا يكرر نموذج البيانات المملوك.
6. لا يكرر عقد API.
7. لا يُنشئ كيانًا بديلًا أو شاشة بديلة لوظيفة مشتركة مملوكة لموديول آخر.

### EP-MOD-004 — تعديل الوظائف المشتركة

**التصنيف:** `MANDATORY`

لا يجوز للموديول المستهلك إعادة تعريف أو تعديل وظيفة مشتركة يملكها موديول آخر. أي تعديل يتطلب:

1. Change Request أو قرار منتج جديد.
2. مراجعة الأثر على الموديول المالك.
3. اعتماد التغيير من مالك المنتج.
4. تحديث وثائق الموديول المالك أولًا.
5. ثم تحديث الموديولات المستهلكة عند الحاجة.

## 4. ملكية البيانات

### EP-DATA-001 — ملكية الكيانات

**التصنيف:** `MANDATORY`

لكل كيان بيانات موديول مالك واحد. الموديول المالك هو الجهة الوحيدة المسؤولة عن:

- إنشاء الكيان.
- تعديل بنيته.
- تحديد قواعد تحققه.
- تحديد دورة حياته (الإنشاء، التعديل، الأرشفة، الحذف).
- تحديد صلاحيات الوصول إليه.

### EP-DATA-002 — جدول الحقيقة المصدرية

**التصنيف:** `MANDATORY`

**DEFERRED TO LATER STANDARD** — `domain-modeling-standard.md` و`data-modeling-standard.md` يُحددان الجدول التفصيلي لملكية كل كيان. يسري المبدأ العام:

- بيانات المستخدم والحسابات → موديول الهوية والوصول.
- الملف الشخصي → موديول الملف الشخصي.
- كيانات المجال الرئيسية (مثل الطلبات `ORD` والعملاء `CUS`) → الموديول المالك لكل منها في `module-registry.md`.
- الوسائط والملفات → موديول الوسائط.
- الباقات والرسوم → موديول الباقات.
- المدفوعات والمعاملات المالية → موديول المدفوعات.
- الإشعارات → موديول الإشعارات.
- سجل التدقيق → موديول سجل التدقيق.
- الإعدادات والبيانات المرجعية → موديول الإعدادات.

### EP-DATA-003 — عدم تخزين الوسائط في قاعدة البيانات

**التصنيف:** `PROHIBITED`

لا تُحفظ الصور أو الفيديوهات أو أي ملف ثنائي داخل جداول قاعدة البيانات. جميع الوسائط تُحفظ في Object Storage خارجي.

> المرجع: `architecture.md` — "Media Offloading".

## 5. الوصول العابر للموديولات

### EP-XMOD-001 — الوصول عبر عقد فقط

**التصنيف:** `MANDATORY`

لا يجوز لموديول الوصول إلى بيانات موديول آخر إلا عبر عقد محدد (واجهة برمجية داخلية أو خدمة). الوصول المباشر لجداول موديول آخر في قاعدة البيانات ممنوع.

### EP-XMOD-002 — مبدأ القراءة فقط للاستهلاك

**التصنيف:** `MANDATORY WHEN APPLICABLE`

عندما يستهلك موديول بيانات من موديول آخر لأغراض العرض فقط (مثل عرض اسم العميل في شاشة الطلبات)، يجب أن يكون الوصول للقراءة فقط. لا يجوز للموديول المستهلك تعديل بيانات الموديول المالك.

### EP-XMOD-003 — توثيق الاعتماديات

**التصنيف:** `MANDATORY`

كل اعتمادية بين موديولين يجب أن تكون:

- مسجلة في `module-registry.md`.
- موثقة في `requirements.md` للموديول المستهلك.
- مرئية في `traceability-matrix.md` عند إنشائه.

### EP-XMOD-004 — منع الاعتماديات الدائرية

**التصنيف:** `MANDATORY`

لا يجوز وجود اعتمادية دائرية مباشرة بين موديولين (A يعتمد على B و B يعتمد على A في نفس العملية). إذا ظهرت حاجة فعلية لذلك، يُحل الأمر عبر:

- حدث (Event) إذا كانت إحدى الاعتماديات غير متزامنة.
- وسيط مشترك (Shared Mediator) يُملك لأحد الموديولين.
- رفع القرار لمالك المنتج لإعادة توزيع المسؤوليات.

## 6. المعالجة المتزامنة وغير المتزامنة

### EP-SYNC-001 — القاعدة العامة

**التصنيف:** `MANDATORY`

يُستخدم الاتصال المتزامن (Synchronous) عندما:

- يحتاج المستخدم إلى نتيجة فورية لإكمال تفاعله.
- العملية سريعة ومتوقعة الاكتمال خلال ثوانٍ قليلة.
- فشل العملية يجب أن يُبلَّغ للمستخدم فورًا.

يُستخدم الاتصال غير المتزامن (Asynchronous) عندما:

- العملية ثقيلة أو بطيئة بطبيعتها.
- فشل العملية لا يجب أن يمنع المستخدم من إكمال تفاعله الحالي.
- العملية تتضمن تكاملًا خارجيًا قد يتأخر أو يفشل.

### EP-SYNC-002 — حالات المعالجة غير المتزامنة المعتمدة

**التصنيف:** `MANDATORY`

الحالات التالية يجب أن تُنفَّذ عبر معالجة خلفية وليس في السياق المتزامن لطلب المستخدم:

| الحالة | السبب |
|---|---|
| إرسال SMS أو Email | لا يجب أن يوقف تجربة المستخدم عند بطء المزود |
| معالجة الصور (ضغط، إنشاء Thumbnails) | مكلف زمنيًا |
| معالجة الفيديو (ضغط، إنشاء Preview) | مكلف جدًا |
| توليد PDF | يمكن تنفيذه كعملية خلفية |
| الإشعارات المجدولة أو المرتبطة بأحداث زمنية | تحتاج إدارة أحداث وزمن |
| Webhooks الدفع | تحتاج معالجة موثوقة وإعادة محاولة عند الفشل |

> المرجع: `architecture.md` — المعالجة الخلفية.

### EP-SYNC-003 — آلية المعالجة غير المتزامنة

**التصنيف:** `OPEN — DECISION REQUIRED`

الآليات التقنية المحددة للمعالجة غير المتزامنة (طوابير مُدارة، Pub/Sub، مهام مجدولة سحابية) تُحسم لكل مشروع بسجل قرار معماري (ADR) وبوابة `HG-E-05`. لا يُبنى على خدمة مصنفة `PROPOSED` في `architecture.md` كخدمة معتمدة قبل ذلك.

**DEFERRED TO LATER STANDARD** — `event-contract-standard.md` يُحدد تفاصيل العقود والأنماط.

> الحاجب المعتاد: قرار نمط التشغيل (`EP-CLOUD-003`) يؤثر على آلية المعالجة الخلفية، وكتالوج الأحداث يجب أن يكون محسومًا قبل البناء عليه.

### EP-SYNC-004 — عدم جعل كل شيء حدثيًا

**التصنيف:** `PROHIBITED`

لا يُحوَّل كل تفاعل أو عملية إلى حدث غير متزامن. المعالجة المتزامنة المباشرة هي الخيار الافتراضي. لا يُستخدم النمط الحدثي إلا عندما تتوفر أحد الشروط في `EP-SYNC-001`.

> المرجع: `architecture.md` — "Event-driven Operations" يعني العمليات الثقيلة فقط، وليس جميع العمليات.

## 7. حدود المعاملات والذرّية

### EP-TXN-001 — مبدأ الذرّية

**التصنيف:** `MANDATORY`

كل عملية تُغيِّر حالة أعمال ذات أهمية يجب أن تكون ذرّية — إما تنجح بالكامل أو تفشل بالكامل. لا يجوز ترك النظام في حالة وسيطة غير متسقة.

### EP-TXN-002 — حدود المعاملة

**التصنيف:** `MANDATORY`

حدود المعاملة (Transaction Boundary) يجب أن تتطابق مع حدود العملية التجارية الواحدة. عند تصميم المعاملات:

- العمليات داخل موديول واحد: معاملة قاعدة بيانات واحدة.
- العمليات العابرة للموديولات:
  - الأصل: كل موديول يدير معاملته مستقلًا. المعاملة الواحدة العابرة لحدود موديولين هي استثناء معماري يتطلب تبريرًا موثقًا ومراجعة، لأنها تُقيّد الفصل المستقبلي (`EP-ARCH-003`).
  - إذا تضمنت تكاملًا خارجيًا أو معالجة غير متزامنة: تُستخدم أنماط الاتساق التدريجي (Eventual Consistency) مع آليات التعويض (Compensation) عند الفشل.

### EP-TXN-003 — المعاملات المالية

**التصنيف:** `MANDATORY`

أي عملية تمس أموالًا (رسوم، عمولات، مبالغ محجوزة، استرداد) يجب أن تُصمَّم بأعلى مستوى من ضمان الذرّية والاتساق. لا يجوز اختراع آلية معاملات مالية — تفاصيل التنفيذ تُحسم عبر بوابة `HG-E-02`.

> المرجع: `CLAUDE-ENGINEERING.md` — بوابة `HG-E-02`.

### EP-TXN-004 — تعويض الفشل

**التصنيف:** `MANDATORY WHEN APPLICABLE`

عند استخدام الاتساق التدريجي، يجب تصميم آلية تعويض واضحة لكل خطوة:

- ما الذي يُلغى إذا فشلت الخطوة التالية.
- من المسؤول عن تنفيذ التعويض.
- كيف يُسجَّل الفشل والتعويض في سجل التدقيق.

> **ملاحظة:** هذا المبدأ يسد فجوة «حدود المعاملات» على المستوى المبدئي. التفاصيل التنفيذية تُحدد في `data-modeling-standard.md`.

## 8. منع التكرار (Idempotency)

### EP-IDEM-001 — العمليات الحساسة

**التصنيف:** `MANDATORY WHEN APPLICABLE`

كل عملية حساسة يجب أن تكون idempotent — تنفيذها أكثر من مرة بنفس المدخلات يُنتج نفس النتيجة دون آثار جانبية مكررة. ينطبق ذلك على العمليات التي يمكن أن تُعاد أو تتكرر، ومنها:

- معالجة Webhooks الدفع.
- معالجة إعادة محاولة الإشعارات.
- عمليات تغيير حالة الكيانات.
- أي عملية قابلة لإعادة المحاولة (Retry).

### EP-IDEM-002 — آليات منع التكرار

**التصنيف:** `RECOMMENDED`

تتوفر عدة آليات لضمان منع التكرار، تُختار حسب طبيعة العملية:

- **Idempotency Key**: مفتاح فريد يُرسله المستهلك مع الطلب — مناسب لعمليات API الخارجية والمدفوعات.
- **Natural Key / Unique Constraint**: قيد تفرّد طبيعي على مستوى قاعدة البيانات — مناسب لمنع التسجيل المكرر.
- **State Check (Pre-condition)**: التحقق من الحالة الحالية قبل التنفيذ — مناسب لانتقالات الحالة.
- **Deduplication Window**: نافذة زمنية لرفض الطلبات المتكررة — مناسب لمعالجة Webhooks.

يُحدد المعيار التفصيلي النمط المعتمد لكل حالة.

**DEFERRED TO LATER STANDARD** — `api-design-standard.md` يُحدد الأنماط التفصيلية لمنع التكرار.

## 9. التحكم في التزامن (Concurrency Control)

### EP-CONC-001 — حماية العمليات المتزامنة

**التصنيف:** `MANDATORY WHEN APPLICABLE`

أي عملية يمكن أن يتنافس عليها أكثر من مستخدم أو عملية في نفس الوقت يجب أن تكون محمية ضد حالات السباق (Race Conditions). يشمل ذلك:

- العروض أو الطلبات المتنافسة على مورد واحد في اللحظة نفسها.
- تغيير حالة سجل (مثل قبول طلب أثناء تعديله).
- تعديل إعدادات مشتركة من مستخدمين إداريين متعددين.
- أي عملية مالية متنافسة.

### EP-CONC-002 — آلية الحماية

**التصنيف:** `MANDATORY WHEN APPLICABLE`

يجب اختيار آلية حماية مناسبة لكل حالة تزامن. تشمل الآليات المتاحة:

- **Optimistic Locking** (القفل المتفائل): يُفضَّل كخيار افتراضي للعمليات التي يندر فيها التزامن الفعلي.
- **Pessimistic Locking** (القفل المتشائم): للعمليات الحرجة التي لا يُقبل فيها أي فشل بسبب التزامن.
- **Atomic Compare-and-Swap**: لعمليات التحديث الذرية البسيطة على قيمة واحدة.
- **Queue-based Serialization**: لتحويل العمليات المتنافسة إلى تسلسل مُدار.

يُحدد المعيار التفصيلي الآلية المناسبة لكل حالة استخدام.

**DEFERRED TO LATER STANDARD** — `data-modeling-standard.md` يُحدد الأنماط التفصيلية لكل حالة.

## 10. آلات الحالة وملكية الانتقالات

### EP-STATE-001 — مصدر الحقيقة للحالات

**التصنيف:** `MANDATORY`

الحالات المعتمدة لكل كيان أعمال (حساب مستخدم، طلب، فاتورة، دفعة، إشعار، …) تُعرَّف في:

1. `business-rules-global.md` — الحالات المعيارية العامة.
2. `glossary.md` — قاموس الحالات المعياري.
3. `business-rules.md` لكل موديول — الحالات الخاصة بالموديول.

لا يجوز إنشاء حالة جديدة غير واردة في هذه المراجع دون قرار معتمد (`DEC-*`).

### EP-STATE-002 — ملكية الانتقالات

**التصنيف:** `MANDATORY`

لكل انتقال حالة مالك واحد — الموديول الذي يملك الكيان. لا يجوز لموديول آخر تنفيذ انتقال حالة على كيان لا يملكه.

الاستثناء: عندما يكون الانتقال **أثرًا تلقائيًا** لعملية في موديول آخر (مثل: تغيير حالة سجل العميل `CUS` كأثر لإتمام طلب في موديول الطلبات `ORD`). في هذه الحالة، الموديول المصدر يطلب الانتقال، والموديول المالك ينفذه.

### EP-STATE-003 — تسجيل الانتقالات

**التصنيف:** `MANDATORY`

كل انتقال حالة لكيان أعمال يجب أن يُسجَّل مع:

- الحالة السابقة.
- الحالة الجديدة.
- الفاعل (من نفَّذ أو طلب الانتقال).
- الوقت.
- السبب عند الحاجة.

الانتقالات الحساسة يجب أن تُسجَّل في Audit Log (الموديول المالك لسجل التدقيق).

### EP-STATE-004 — التحقق من صحة الانتقال

**التصنيف:** `MANDATORY`

كل انتقال حالة يجب أن يُتحقق منه مقابل مخطط الانتقالات المعتمد في `business-rules.md` للموديول. لا يجوز تنفيذ انتقال غير مُعرَّف.

## 11. معالجة الأخطاء والاستثناءات

### EP-ERR-001 — مبدأ الفشل الآمن

**التصنيف:** `MANDATORY`

عند حدوث خطأ غير متوقع، يجب أن يفشل النظام بطريقة آمنة:

- لا يكشف تفاصيل تقنية داخلية للمستخدم النهائي.
- لا يترك البيانات في حالة غير متسقة.
- يُسجِّل الخطأ مع سياق كافٍ للتشخيص.
- يُرسل رسالة خطأ مفهومة للمستخدم بلغته.

### EP-ERR-002 — التمييز بين أنواع الأخطاء

**التصنيف:** `MANDATORY`

يجب التمييز بوضوح بين:

| نوع الخطأ | المعنى | الاستجابة |
|---|---|---|
| خطأ مدخلات المستخدم (Validation Error) | بيانات غير صالحة قدمها المستخدم | رسالة واضحة للمستخدم تشرح ما يجب تصحيحه |
| خطأ أعمال (Business Rule Violation) | العملية مخالفة لقاعدة عمل | رسالة واضحة للمستخدم تشرح القاعدة المخالَفة |
| خطأ تفويض (Authorization Error) | المستخدم لا يملك الصلاحية | رسالة منع وصول دون كشف تفاصيل |
| خطأ نظام (System Error) | فشل داخلي غير متوقع | رسالة عامة للمستخدم + تسجيل تفصيلي في السجلات |
| خطأ تكامل خارجي (Integration Error) | فشل مزود خارجي | معالجة خاصة حسب المزود مع إعادة محاولة عند الحاجة |

### EP-ERR-003 — رسائل الخطأ

**التصنيف:** `MANDATORY`

رسائل الخطأ الموجهة للمستخدم يجب أن تكون:

- بلغة المستخدم (اللغة الأساسية للمنصة هي الافتراض).
- واضحة وتشرح ما حدث وما المطلوب لتصحيحه.
- خالية من مصطلحات تقنية داخلية أو أكواد خطأ خام.
- خالية من تفاصيل يمكن استغلالها أمنيًا.

**DEFERRED TO LATER STANDARD** — `error-contract-standard.md` يُحدد بنية رسائل الخطأ وأكوادها التقنية.

## 12. أمان التكاملات الخارجية

### EP-INT-001 — مبادئ التكامل العامة

**التصنيف:** `MANDATORY`

كل تكامل خارجي يجب أن يحقق:

- حفظ الأسرار (مفاتيح API، بيانات اعتماد) في خدمة إدارة أسرار مُدارة — وليس في الكود أو ملفات التكوين.
- فصل مفاتيح وأسرار التطوير والاختبار والإنتاج.
- عدم استخدام حسابات شخصية في أي تكامل إنتاجي.
- تسجيل Webhooks المهمة.
- دعم Retry أو معالجة فشل للتكاملات الحرجة.

> المرجع: `architecture.md` — الأمن والتكاملات الخارجية.

### EP-INT-002 — عزل تكامل الدفع

**التصنيف:** `MANDATORY`

تكامل بوابة الدفع يجب أن يكون معزولًا منطقيًا داخل موديول المدفوعات المالك. لا يجوز لأي موديول آخر التعامل مباشرة مع بوابة الدفع.

> المرجع: `architecture.md` — التكاملات الخارجية.

### EP-INT-003 — حياد المزودين

**التصنيف:** `MANDATORY WHEN APPLICABLE`

عندما يكون قرار المزود محايدًا تقنيًا (مثل مزود SMS أو مزود البريد المعتمدين بحياد بلا اسم تجاري)، يجب تصميم الطبقة الداخلية بحيث لا تعتمد على تفاصيل مزود بعينه. يُستخدم نمط التجريد المناسب لتسهيل استبدال المزود لاحقًا.

عندما يكون المزود معتمدًا بالاسم (مثل بوابة دفع بعينها بقرار معتمد)، يُصمَّم العزل على مستوى حدود الموديول المالك.

### EP-INT-004 — المزودون المعتمدون

**التصنيف:** `MANDATORY`

لا يُفترض أو يُقترح مزود خارجي غير موثق ومعتمد في `architecture.md` و`project-decisions.md`. يُثبَّت جدول المزودين المعتمدين للمشروع بالشكل التالي، ولا يُضاف صف إليه إلا بقرار معتمد:

| Object Storage | `{{PROVIDER}}` | `APPROVED` وظيفيًا | `FR-{{...}}` |
| SMS Provider | — | `APPROVED` بحياد — لا اسم تجاري | `DEC-{{...}}` |
| Email Provider | — | `APPROVED` بحياد — يدعم اتجاه اللغة الأساسية | `DEC-{{...}}` |
| قنوات المراسلة (مثل WhatsApp Business API) | `{{PROVIDER}}` | `APPROVED` بقيود نطاق | `DEC-{{...}}` |
| الدخول الاجتماعي (OAuth) | `{{PROVIDERS}}` | `APPROVED` | `DEC-{{...}}` |

## 13. الأمن بالتصميم (Security by Design)

### EP-SEC-001 — المبدأ العام

**التصنيف:** `MANDATORY`

الأمن ليس طبقة تُضاف لاحقًا. يجب تضمين الضوابط الأمنية في التصميم من البداية:

- تشفير كلمات المرور بطريقة آمنة — لا تُحفظ كنص صريح.
- HTTPS في واجهات الإنتاج.
- RBAC (Role-Based Access Control) كنموذج أساسي للصلاحيات.
- حفظ المفاتيح والأسرار في خدمة إدارة أسرار مُدارة.
- Signed URLs للوصول المؤقت للملفات الخاصة.
- تسجيل الإجراءات الحساسة في Audit Log.
- فصل بيئات التطوير والاختبار والإنتاج.

**التصنيف:** `MANDATORY`

### EP-SEC-003 — إخفاء البيانات الشخصية لأصحاب السجلات

### EP-SEC-004 — عدم استخدام بيانات حساسة في الأمثلة

**التصنيف:** `PROHIBITED`

لا تُستخدم بيانات حساسة حقيقية أو شبه حقيقية في أمثلة التوثيق أو Seed Data أو سيناريوهات الاختبار.

> المرجع: `architecture.md` — المحظورات.

**DEFERRED TO LATER STANDARD** — `security-architecture.md` يُحدد ضوابط الأمن التفصيلية.

## 14. المصادقة (Authentication)

### EP-AUTH-001 — آلية المصادقة المعتمدة

**التصنيف:** `MANDATORY`

آلية المصادقة المعتمدة تُحسم بقرارات معتمدة وتُوثَّق في `authentication-standard.md`. العناصر التي يجب أن تكون محسومة قبل التنفيذ:

- **الآلية الأساسية:** (مثال: تسجيل بالجوال + كلمة مرور + OTP للتحقق والاستعادة).
- **حدود OTP:** عدد المحاولات، مدة الصلاحية، تبريد إعادة الإرسال — قيم محسومة بقرار لا تُكتب في الكود. مزود تنفيذ OTP يُحسم بقرار رسمي مستقل.
- **الجلسات:** رموز Bearer مبهمة (الافتراضي في ملف التعريف `laravel-react`: Laravel Sanctum).
- **الدخول الاجتماعي:** مزودو OAuth المعتمدون — تفعيل/تعطيل من لوحة الإدارة.

### EP-AUTH-002 — عدم اختراع مسار مصادقة بديل

**التصنيف:** `PROHIBITED`

لا يجوز إنشاء مسار مصادقة بديل أو إضافي غير معتمد في القرارات أعلاه. أي تغيير يتطلب Change Request.

### EP-AUTH-003 — ملكية المصادقة

**التصنيف:** `MANDATORY`

كل ما يتعلق بالمصادقة وإدارة الهوية مملوك حصريًا لموديول الهوية والوصول. لا يجوز لأي موديول آخر تنفيذ أو تعديل أو تكرار منطق المصادقة.

## 16. قابلية التدقيق (Auditability)

### EP-AUD-001 — تسجيل الإجراءات الحساسة

**التصنيف:** `MANDATORY`

كل إجراء حساس يجب أن يُسجَّل في Audit Log. يشمل ذلك — كحد أدنى:

- اعتماد أو رفض توثيق مستخدم أو دور.
- تعليق أو تفعيل حساب.
- تعديل صلاحيات المستخدم.
- إنشاء أو إلغاء عملية تجارية رئيسية (مثل طلب `ORD`).
- تغيير حالات العمليات التجارية الرئيسية.
- تغيير حالة توثيق كيان المجال الرئيسي.
- إخفاء أو إعادة إظهار سجل عام.
- تعديل العمولات أو الباقات.
- تعديل القيم المالية القابلة للضبط.
- معالجة فشل الدفع.
- التحويل اليدوي لنتيجة عملية (مثل اختيار المستفيد البديل).
- تعديل الإعدادات الحساسة.

> المرجع: `architecture.md` — سجل التدقيق.

### EP-AUD-002 — ملكية Audit Log

**التصنيف:** `MANDATORY`

Audit Log مملوك حصريًا لموديول سجل التدقيق. جميع الموديولات الأخرى تُرسل سجلاتها إليه ولا تُنشئ نظام تدقيق بديل.

### EP-AUD-003 — لا حذف لسجلات التدقيق

**التصنيف:** `MANDATORY`

سجلات Audit Log ثابتة نهائيًا — لا تُحذف ولا تُعدَّل. هذه سياسة صلبة تمنع أي عملية DELETE أو UPDATE فعلية على سجلات التدقيق.

### EP-AUD-004 — مدة الاحتفاظ

**التصنيف:** `MANDATORY`

مدة الاحتفاظ الافتراضية بسجلات التدقيق قيمة محسومة بقرار معتمد (القيمة المرجعية في المشروع الأصل: 12 شهرًا)، قابلة للضبط بصلاحية SYSADMIN عبر موديول الإعدادات ولا تُكتب في الكود.

### EP-AUD-005 — بيانات السجل

**التصنيف:** `MANDATORY`

كل سجل تدقيق يجب أن يتضمن — كحد أدنى:

- معرّف الفاعل.
- دور الفاعل وقت التنفيذ.
- نوع الإجراء.
- نوع الكيان المتأثر.
- معرّف الكيان المتأثر.
- القيمة السابقة والجديدة عند توفرهما.
- السبب أو الملاحظة عند الحاجة.
- الوقت.
- عنوان IP عند توفره.

> المرجع: `architecture.md` — بيانات سجل التدقيق.

### EP-AUD-006 — استمرار الخدمة عند الفشل

**التصنيف:** `MANDATORY`

عند فشل كتابة سجل التدقيق، يجب أن يستمر النظام في تقديم الخدمة مع إرسال تنبيه فوري لـ SYSADMIN. لا يُوقف النظام بسبب فشل التدقيق.

## 17. المراقبة والقابلية للملاحظة (Observability)

### EP-OBS-001 — التسجيل التقني مقابل التدقيق

**التصنيف:** `MANDATORY`

التسجيل التقني (Logging) والتدقيق الحوكمي (Audit Log) نظامان منفصلان:

| الجانب | Logging التقني | Audit Log |

> المرجع: `architecture.md` — "Logging التقني لا يغني عن Audit Log الخاص بالحوكمة."

### EP-OBS-002 — ما يجب مراقبته

**التصنيف:** `MANDATORY`

يجب مراقبة — كحد أدنى:

### EP-OBS-003 — ما يجب تسجيله

## 18. إعادة المحاولة ومعالجة الفشل (Retry and Failure Handling)

### EP-RETRY-001 — مبدأ عام

**التصنيف:** `MANDATORY WHEN APPLICABLE`

أي عملية تتعامل مع مزود خارجي أو معالجة خلفية يجب أن تدعم إعادة المحاولة عند الفشل المؤقت (Transient Failure).

### EP-RETRY-002 — سياسة الإشعارات

**التصنيف:** `MANDATORY`

سياسة إعادة المحاولة للإشعارات (عدد المحاولات والفاصل بينها) قيمة محسومة بقرار معتمد لا تُكتب في الكود (القيمة المرجعية في المشروع الأصل: 3 محاولات كل 5 دقائق).

### EP-RETRY-003 — حدود إعادة المحاولة

**التصنيف:** `MANDATORY`

كل آلية إعادة محاولة يجب أن تحدد:

- الحد الأقصى لعدد المحاولات.
- الفترة الفاصلة بين المحاولات (يُفضَّل Exponential Backoff مع Jitter).
- الإجراء عند استنفاد المحاولات (تنبيه، تسجيل، تصعيد يدوي).

### EP-RETRY-004 — Retry مع Idempotency

**التصنيف:** `MANDATORY`

كل عملية قابلة لإعادة المحاولة يجب أن تكون idempotent (انظر §8).

## 19. الوسائط والملفات (File and Media)

### EP-MEDIA-001 — التخزين الخارجي

**التصنيف:** `MANDATORY`

جميع الوسائط والملفات تُحفظ في Object Storage خارجي معتمد وظيفيًا. لا تُحفظ في قاعدة البيانات (`EP-DATA-003`).

### EP-MEDIA-002 — ملكية الوسائط

**التصنيف:** `MANDATORY`

موديول الوسائط هو المالك الحصري لرفع وإدارة ومعالجة الوسائط. جميع الموديولات الأخرى تستهلك خدمات الوسائط عبره.

### EP-MEDIA-003 — الحدود المعتمدة

**التصنيف:** `MANDATORY`

حدود الوسائط المعتمدة لكل كيان مجال يحمل وسائط تُحسم بقرار معتمد وتُثبَّت في جدول بالشكل التالي:

| الحد | القيمة | المرجع |
|---|---|---|
| حجم الصورة | `{{MAX_IMAGE_SIZE}}` | `DEC-{{...}}` |
| عدد الصور الإضافية | `{{MAX_EXTRA_IMAGES}}` | `DEC-{{...}}` |
| حجم الفيديو | `{{MAX_VIDEO_SIZE}}` | `DEC-{{...}}` |
| مدة الفيديو | `{{MAX_VIDEO_DURATION}}` | `DEC-{{...}}` |
| عدد الفيديو | `{{MAX_VIDEOS}}` لكل سجل | `DEC-{{...}}` |

لا تُتجاوز هذه الحدود دون Change Request، ولا تُكتب قيمها في الكود (`CS-004`).

### EP-MEDIA-004 — الوصول الآمن

**التصنيف:** `MANDATORY`

الملفات الخاصة (وثائق، تقارير، مرفقات حساسة) يُصل إليها عبر Signed URLs بصلاحية زمنية محدودة محسومة بقرار (القيمة المرجعية في المشروع الأصل: 24 ساعة).

### EP-MEDIA-005 — دورة حياة الوسائط

**التصنيف:** `MANDATORY`

- عند استبدال وثيقة حساسة: تُحتفظ بها في حالة `RETENTION_HOLD` لمدة محسومة بقرار (القيمة المرجعية في المشروع الأصل: 90 يومًا).
- عند أرشفة السجل الأم: تُخفى الوسائط تلقائيًا — لا تُحذف.

### EP-MEDIA-006 — Lifecycle السحابية

**التصنيف:** `OPEN — DECISION REQUIRED`

تحديد سياسة Lifecycle السحابية التفصيلية للوسائط (أرشفة، نقل بين طبقات التخزين) يُحسم لكل مشروع بقرار معتمد. لا يُخترع بديل.

**DEFERRED TO LATER STANDARD** — `file-media-contract-standard.md` يُحدد تفاصيل العقود.

### EP-CLOUD-003 — نمط تشغيل التطبيق

### EP-CLOUD-005 — الفصل بين البيئات

**التصنيف:** `MANDATORY`

يجب فصل البيئات (تطوير، اختبار، إنتاج) مع مفاتيح وأسرار مستقلة لكل بيئة.

> المرجع: `architecture.md` — الأمن.

### EP-CLOUD-006 — النسخ الاحتياطي

**التصنيف:** `MANDATORY`

تُحسم بقرارات معتمدة قبل الإطلاق — ولا تُفترض:

- دورية النسخ الاحتياطي للبيانات التشغيلية.
- مدة الاحتفاظ بالنسخ.

(القيم المرجعية في المشروع الأصل: نسخ يومي · احتفاظ 30 يومًا · RPO ≤ 24 ساعة.)

## 21. الاحتفاظ بالبيانات والحذف (Data Retention and Deletion)

### EP-RET-001 — السياسة العامة

**التصنيف:** `MANDATORY`

سياسات الاحتفاظ بالبيانات والحذف تُحدد في `business-rules-global.md` وقرارات `project-decisions.md`. لا يجوز اختراع سياسة احتفاظ أو حذف غير واردة في هذه المراجع.

### EP-RET-002 — القرارات المعتمدة

**التصنيف:** `MANDATORY`

يُثبَّت لكل مشروع جدول القرارات المرجعية للاحتفاظ والحذف بالشكل التالي، ولا يُبنى على سياسة ليس لها صف فيه:

| القرار | المحتوى |
|---|---|
| `DEC-{{...}}` | سياسة حذف الحسابات |
| `DEC-{{...}}` | سياسة الاحتفاظ بسجلات كيان المجال الرئيسي |
| `DEC-{{...}}` | سياسة حذف السجلات |
| `DEC-{{...}}` | `RETENTION_HOLD` — مدة الاحتفاظ بالوثائق الحساسة المستبدلة |
| `DEC-{{...}}` | إخفاء الوسائط عند الأرشفة (لا حذف) |
| `DEC-{{...}}` | لا حذف لسجلات التدقيق |
| `DEC-{{...}}` | مدة احتفاظ سجلات التدقيق |

### EP-RET-003 — لا حذف فعلي بدون مرجع

**التصنيف:** `PROHIBITED`

لا يُنفَّذ حذف فعلي (Hard Delete) لأي بيانات أعمال دون سياسة احتفاظ معتمدة تُحدد:

- ما يُحذف.
- متى يُحذف.
- ما يُحتفظ به.
- من يملك صلاحية الحذف.

## 25. القابلية للتتبع (Traceability)

### EP-TRACE-001 — تتبع المعرّفات

**التصنيف:** `MANDATORY`

كل مخرج هندسي يجب أن يكون قابلًا للتتبع إلى معرّف (أو معرّفات) Phase 0 مصدرية. العلاقة بين المخرجات والمعرّفات المصدرية هي **متعدد-إلى-متعدد** — مخرج واحد قد يتتبع لعدة معرّفات مصدرية، ومعرّف مصدري واحد قد يظهر في عدة مخرجات:

```text
US-[MODULE-CODE]-### ↔ FR-[MODULE-CODE]-### (1:N أو N:1)
TS-[MODULE-CODE]-### ↔ AC-SCR-[MODULE-CODE]-###-### (1:N أو N:1)
API-[MODULE-CODE]-### ↔ FR-[MODULE-CODE]-### + BR-[MODULE-CODE]-### (N:M)
ENT-[MODULE-CODE]-### ↔ BR-[MODULE-CODE]-### + FR-[MODULE-CODE]-### (N:M)
```

> المرجع: `CLAUDE-ENGINEERING.md` — قابلية التتبع.

### EP-TRACE-002 — خريطة تكافؤ المعرّفات

**التصنيف:** `MANDATORY`

عند وجود انحراف بين الصيغة الفعلية لمعرّفات Phase 0 والصيغة المعيارية، تُستخدم `identifier-alias-map.md` لتحويل الصيغة. تُسجَّل في تلك الخريطة الانحرافات المعروفة في المشروع، ومن أصنافها المعتادة:

- كود موديول فعلي يخالف الكود المشتق من اسمه.
- موديولات بلا بادئة `FR-` في المتطلبات.
- موديولات تستخدم ترقيم `BR` بعدد خانات مختلف.

> المرجع: `identifier-alias-map.md`.

### EP-TRACE-003 — مصفوفة التتبع

**التصنيف:** `MANDATORY`

لكل موديول، تُنشأ `traceability-matrix.md` تربط بين:

- المتطلبات (`FR-*`).
- قواعد العمل (`BR-*`).
- التدفقات (`FLOW-*`).
- الشاشات (`SCR-*`).
- الكيانات (`ENT-*`).
- عقود API (`API-*`).
- قصص المستخدم (`US-*`).
- سيناريوهات الاختبار (`TS-*`).

**التصنيف:** `MANDATORY`

> المرجع: `CLAUDE-ENGINEERING.md` — بوابات الجودة.
