# API Design Standard — معيار تصميم الواجهات البرمجية

> يُحدد هذا المعيار القواعد العامة لتصميم الواجهات البرمجية الداخلية والخارجية: البنية، التسمية، الاستجابات، الترقيم، منع التكرار، الإصدارات، والأمن.
>
> يبني على `EP-API-001..004`، `EP-IDEM-001..002`، وعقد الأخطاء (`ECS-001..025`).
>
> **أولوية هذا الملف:** يخضع لأولوية `engineering-principles.md` (§0.3).

---

## 0. الغرض والنطاق

### 0.1 الغرض

يُحدد هذا المعيار:

- قواعد بنية API (RESTful Conventions).
- تسمية المسارات والموارد.
- بنية الاستجابات ومعالجة الأخطاء (`ECS-*`).
- ترقيم الصفحات والفلترة والترتيب.
- منع التكرار (Idempotency) على مستوى API (`EP-IDEM-001..002`).
- ملكية API (`EP-API-002`).
- سياسة الإصدارات (`EP-API-003`).
- أمن API وحماية البيانات.
- توثيق API.

### 0.2 ما لا يغطيه

- بنية الجداول والأعمدة → `data-modeling-standard.md`.
- المصادقة والتوثيق → `authentication-standard.md`.
- التفويض والصلاحيات → `authorization-standard.md`.
- عقود API التفصيلية لكل موديول → `api-contracts.md` لكل موديول.
- عقود الأحداث → `event-contract-standard.md`.

## 2. المبادئ الأساسية

### API-001 — API-first

**التصنيف:** `MANDATORY`

يُعتمد نمط API-first (`EP-API-001`): الواجهة البرمجية تُصمم وتُوثق قبل التنفيذ. الواجهة الأمامية (Web/Mobile) تتعامل حصريًا مع الخلفية عبر API موثقة.

### API-002 — RESTful

**التصنيف:** `MANDATORY`

تُصمم واجهات API الداخلية وفق مبادئ REST:

- الموارد تُمثل كيانات المجال (`DMS-*`).
- أفعال HTTP تُستخدم حسب المعنى (§3).
- الاستجابات بصيغة JSON.
- Stateless — لا يُحفظ سياق الجلسة في الخادم بين الطلبات.

### API-003 — ملكية API

**التصنيف:** `MANDATORY`

لا يُنشأ عقد API لموديول دون مراجعة ملكية الموديول في `module-registry.md` (`EP-API-002`). كل نقطة نهاية (Endpoint) تنتمي لموديول مالك واحد.

لا يجوز لموديول إنشاء نقطة نهاية تكرر وظيفة مملوكة لموديول آخر.

### API-004 — APIs خارجية

**التصنيف:** `MANDATORY`

أي API يُستهلك من خارج المنصة أو يُصدِّر بيانات شخصية يتطلب بوابة `HG-E-04` (`EP-API-004`).

## 3. بنية المسارات والموارد

### API-005 — صيغة المسار

**التصنيف:** `MANDATORY`

```text
/api/v{N}/{module-code}/{resource-plural}
/api/v{N}/{module-code}/{resource-plural}/{id}
/api/v{N}/{module-code}/{resource-plural}/{id}/{sub-resource-plural}
```

- `v{N}`: رقم الإصدار (§10).
- `{module-code}`: كود الموديول المالك بالأحرف الصغيرة (`ord`, `cus`, `inv`).
- `{resource-plural}`: اسم المورد بالجمع، `kebab-case`.
- `{id}`: معرّف المورد.

أمثلة:

```text
GET    /api/v1/ord/orders
GET    /api/v1/ord/orders/{id}
POST   /api/v1/inv/invoices
GET    /api/v1/ord/orders/{id}/items
```

### API-006 — أفعال HTTP

**التصنيف:** `MANDATORY`

| الفعل | الاستخدام | Idempotent | رمز النجاح |
|---|---|---|---|
| `GET` | قراءة مورد أو قائمة | نعم | `200 OK` |
| `POST` | إنشاء مورد جديد | لا (إلا مع Idempotency Key) | `201 Created` |
| `PUT` | تحديث مورد بالكامل | نعم | `200 OK` |
| `PATCH` | تحديث حقول محددة | نعم | `200 OK` |
| `DELETE` | حذف مورد (منطقي عادةً) | نعم | `204 No Content` أو `200 OK` |

### API-007 — أفعال الأعمال (Actions)

**التصنيف:** `MANDATORY WHEN APPLICABLE`

العمليات التي لا تتطابق مع CRUD تُمثل كأفعال صريحة:

```text
POST /api/v1/ord/orders/{id}/actions/cancel
POST /api/v1/ord/orders/{id}/actions/accept
POST /api/v1/cus/customers/{id}/actions/suspend
```

- المسار ينتهي بـ `/actions/{verb}`.
- الفعل دائمًا `POST`.
- يُوثق في `api-contracts.md`.

### API-008 — تسمية الموارد

**التصنيف:** `MANDATORY`

| القاعدة | مثال صحيح | مثال خاطئ |
|---|---|---|
| جمع الموارد | `orders` | `order` |
| `kebab-case` | `purchase-requests` | `purchaseRequests` |
| لا أفعال في المسار (إلا §API-007) | `GET /orders` | `GET /getOrders` |
| الاسم يعكس الكيان (`DMS-002`) | `invoices` | `invoice-data` |

## 4. بنية الاستجابات

### API-009 — استجابة النجاح

**التصنيف:** `MANDATORY`

```json
{
  "success": true,
  "data": { ... }
}
```

- مورد مفرد: `data` = كائن.
- قائمة: `data` = مصفوفة + `pagination` (§6).
- إنشاء: `data` = الكائن المُنشأ مع `id`.
- حذف: بدون `data` (أو `data: null`).

### API-010 — استجابة الخطأ

**التصنيف:** `MANDATORY`

تُطبق بنية `ECS-005..009` (من `error-contract-standard.md`):

```json
{
  "success": false,
  "error": {
    "code": "ERR-ORD-VAL-001",
    "type": "VALIDATION",
    "message": "رقم الطلب مطلوب",
    "details": [...],
    "trace_id": "req_abc123"
  }
}
```

### API-011 — أكواد HTTP

**التصنيف:** `MANDATORY`

تُطبق جدول ربط `ECS-008`:

| كود HTTP | الاستخدام |
|---|---|
| `200` | نجاح القراءة أو التحديث |
| `201` | نجاح الإنشاء |
| `204` | نجاح الحذف |
| `400` | طلب مشوَّه لا يُفهَم أصلًا (JSON فاسد · ترويسة ناقصة) |
| `401` | غير مصادق (`AUTHORIZATION` — Identity) |
| `403` | غير مخوَّل (`AUTHORIZATION` — Permission) |
| `404` | المورد غير موجود |
| `409` | تعارض أعمال (`BUSINESS_RULE`) |
| `422` | خطأ تحقق (`VALIDATION`) أو قاعدة عمل مرفوضة (`BUSINESS_RULE`) |
| `429` | تجاوز حد الطلبات |
| `500` | خطأ نظام داخلي (`SYSTEM`) |
| `502/503` | خطأ تكامل (`INTEGRATION`) |

> **ملاحظة اتساق:** الجدول أعلاه مطابق لـ`ECS-008` في `error-contract-standard.md`؛ أخطاء التحقق وقواعد العمل تُعاد بـ`422`، و`400` للطلب المشوَّه فقط. عند تعديل أحد الجدولين يُعدَّل الآخر في الطلب نفسه.

## 5. حقول الاستجابة

### API-012 — تسمية الحقول

**التصنيف:** `MANDATORY`

- حقول JSON بصيغة `snake_case` (تتطابق مع `DD-026`).
- الأوقات بصيغة ISO 8601 بـ UTC: `2026-01-01T14:30:00Z`.
- المبالغ المالية: كائن `{ "amount": "1500.00", "currency": "<ISO 4217>" }` — `amount` كنص لتجنب فقدان الدقة، و`currency` هي العملة المعتمدة للمنصة (`EP-L10N-003`).
- المعرّفات: نص (`string`) حتى لو كانت UUID أو رقمية داخليًا.

### API-013 — إخفاء البيانات الحساسة

**التصنيف:** `MANDATORY`

- الحقول بحساسية `شخصي` / `حساس` / `مالي` / `نظامي` (`DD-008`) لا تظهر في استجابات API العامة.
- الحقول النظامية (مفاتيح التشفير، Tokens) لا تظهر في أي استجابة API إطلاقًا.
- `ECS-019..021` (أمن استجابات الأخطاء) تُطبق.

### API-014 — تنسيق القوائم المتداخلة

**التصنيف:** `RECOMMENDED`

- عند إرجاع مورد مع موارد فرعية، استخدم الحد الأقصى لمستوى تداخل واحد.
- للتداخل الأعمق، وفّر نقطة نهاية مستقلة للمورد الفرعي.
- القوائم المتداخلة الطويلة تُحصر (مثل: آخر 5 عناصر فقط مع رابط القائمة الكاملة).

## 6. ترقيم الصفحات والفلترة والترتيب

### API-015 — ترقيم الصفحات

**التصنيف:** `MANDATORY`

كل نقطة نهاية تُرجع قائمة تدعم ترقيم الصفحات:

```text
GET /api/v1/ord/orders?page=2&page_size=20
```

الاستجابة تتضمن:

```json
{
  "success": true,
  "data": [...],
  "pagination": {
    "page": 2,
    "page_size": 20,
    "total_items": 150,
    "total_pages": 8
  }
}
```

- الحد الافتراضي: `page_size = 20`.
- الحد الأقصى: `page_size = 100`.
- يُحدد الحد الأقصى في `api-contracts.md` لكل نقطة نهاية.

### API-016 — Cursor-based Pagination

**التصنيف:** `RECOMMENDED`

للقوائم الكبيرة أو المتغيرة بسرعة (مثل سجل أحداث طلب نشط)، يُفضل ترقيم بالمؤشر:

```text
GET /api/v1/ord/orders/{id}/events?cursor=abc123&limit=20
```

### API-017 — الفلترة

**التصنيف:** `MANDATORY`

- الفلاتر تُمرر كـ Query Parameters.
- أسماء المعاملات تتطابق مع أسماء الحقول (`DD-026`).
- الفلاتر المركبة تستخدم لاحقة: `_min`, `_max`, `_from`, `_to`.

```text
GET /api/v1/ord/orders?status=open&region_id=456&total_min=100&total_max=500
```

### API-018 — الترتيب

**التصنيف:** `MANDATORY`

```text
GET /api/v1/ord/orders?sort=created_at&order=desc
```

- `sort`: اسم الحقل.
- `order`: `asc` (افتراضي) أو `desc`.
- الحقول القابلة للترتيب تُحدد في `api-contracts.md`.

## 7. منع التكرار (Idempotency)

### API-019 — Idempotency Key

**التصنيف:** `MANDATORY WHEN APPLICABLE`

عمليات `POST` الحساسة (إنشاء دفعة، تقديم عرض، إنشاء طلب) تتطلب `Idempotency-Key` في الترويسة (`EP-IDEM-001..002`):

```text
POST /api/v1/{{MODULE_CODE}}/payments
Idempotency-Key: unique-client-generated-key
```

**السلوك:**

1. الخادم يتحقق من وجود مفتاح مُعالج مسبقًا (`DMOD-030`).
2. إذا وُجد: يُرجع نفس الاستجابة السابقة دون تنفيذ مكرر.
3. إذا لم يوجد: يُنفذ ويُحفظ المفتاح مع الاستجابة.
4. نافذة الاحتفاظ: تُحدد في `api-contracts.md` (الحد الأدنى المقترح: 24 ساعة).

### API-020 — State Pre-condition

**التصنيف:** `MANDATORY WHEN APPLICABLE`

أفعال تغيير الحالة (`API-007`) تتضمن الحالة الحالية المتوقعة:

```json
{
  "expected_status": "new",
  "action": "accept"
}
```

يتقاطع مع `DMOD-012` (Atomic Compare-and-Swap) و`DMS-025` (قواعد انتقال الحالة).

## 8. معرّفات التعريف والتتبع

### API-021 — معرّف الطلب

**التصنيف:** `MANDATORY`

كل طلب API يحمل معرّف تتبع فريد (`trace_id`) يُولد من الخادم ويُرجع في الاستجابة (النجاح والخطأ) وفي الترويسة:

```text
X-Trace-Id: req_abc123
```

يُستخدم في:

- ربط الأخطاء (`ECS-009`).
- ربط سجلات التدقيق (`audit-logging-standard.md`).
- ربط سجلات المراقبة (`architecture.md`).

### API-022 — معرّف API

**التصنيف:** `MANDATORY`

كل نقطة نهاية في `api-contracts.md` تحمل معرّفًا:

```text
API-[MODULE-CODE]-###
```

> المرجع: `CLAUDE-ENGINEERING.md` — نظام المعرّفات.

## 9. أمن API

### API-023 — HTTPS

**التصنيف:** `MANDATORY`

جميع واجهات API الإنتاجية تعمل عبر HTTPS (`architecture.md`).

### API-024 — المصادقة

**التصنيف:** `MANDATORY`

كل طلب API (ما عدا نقاط النهاية العامة المحددة صراحة) يتطلب مصادقة. التفاصيل في `authentication-standard.md`.

### API-025 — Rate Limiting

**التصنيف:** `MANDATORY`

تُطبق حدود استخدام على نقاط النهاية الحساسة:

- نقاط OTP والمصادقة.
- نقاط الإنشاء (POST).
- نقاط البحث.

التفاصيل تُحدد في `api-contracts.md` لكل نقطة نهاية. استجابة تجاوز الحد: `429 Too Many Requests`.

### API-026 — حماية البيانات في URL

**التصنيف:** `MANDATORY`

لا تُمرر بيانات حساسة (كلمات مرور، Tokens، بيانات شخصية) في Query Parameters أو URL Path. تُمرر في Body أو ترويسة `Authorization`.

### API-027 — CORS

**التصنيف:** `MANDATORY`

يُقيد CORS بالنطاقات المسموحة فقط. لا يُستخدم `Access-Control-Allow-Origin: *` في الإنتاج.

## 10. إصدارات API

### API-028 — سياسة الإصدارات

**التصنيف:** `OPEN — DECISION REQUIRED`

سياسة إصدارات API تُحسم لكل مشروع (`EP-API-003`).

**التوصية المعمارية:**

- استخدام إصدار في المسار: `/api/v1/...`.
- الإصدار الأول: `v1`.
- تُحدد سياسة الإهمال (Deprecation Policy) قبل الحاجة لـ `v2`.

**ما يُحسم الآن:**

1. جميع APIs تبدأ بـ `/api/v1/`.
2. لا يُنشأ `v2` دون قرار معماري مكتوب.

**ما يُحسم لاحقًا:**

- مدة دعم الإصدار القديم.
- آلية الإبلاغ عن الإهمال (ترويسة `Deprecation`).
- سياسة التغييرات غير المنكسرة (Backward-compatible changes).

## 11. توثيق API

### API-029 — صيغة التوثيق

**التصنيف:** `MANDATORY`

كل `api-contracts.md` لموديول يتضمن لكل نقطة نهاية:

| الخاصية | الوصف |
|---|---|
| المعرّف | `API-[MODULE-CODE]-###` |
| المسار | المسار الكامل |
| الفعل | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |
| الوصف | غرض النقطة |
| الأدوار المسموحة | الأدوار التي يمكنها الوصول |
| الترويسات | الترويسات المطلوبة |
| المعاملات | Query Parameters إن وجدت |
| جسم الطلب | البنية مع أنواع الحقول |
| استجابة النجاح | البنية مع رمز HTTP |
| استجابات الخطأ | الأخطاء المحتملة (`ERR-*`) |
| Idempotency | هل تتطلب Idempotency Key |
| Rate Limit | الحد إن وجد |
| ملاحظات | قواعد أعمال أو قيود |

### API-030 — OpenAPI Specification

**التصنيف:** `MANDATORY`

يُنتج ملف OpenAPI (Swagger) 3.0+ من `api-contracts.md` عند بدء التنفيذ. يُحافظ على تزامنه مع التوثيق.

**في مرحلة التنفيذ:** لكل موديول يُنفَّذ ملف OpenAPI **مُولَّد من الكود** لا مكتوبًا يدويًا — الملف اليدوي ينحرف عن التنفيذ بصمت فيصير توثيقًا يكذب، وهو أسوأ من غيابه. غياب الملف أو عدم تطابقه مع `api-contracts.md` يمنع إعلان الشريحة مكتملة (`DoD-SL-09`). الملف واحد للمستودع، وتفحصه مرحلة `stage_openapi` في `scripts/quality.sh` بإعادة توليد ومقارنة.

## 12. واجهات بين الموديولات (Internal API)

### API-031 — عقد القراءة الداخلي

**التصنيف:** `MANDATORY`

الوصول القرائي بين الموديولات (`DMS-020`) يتم عبر عقد داخلي موثق. في نمط Modular Monolith (`EP-ARCH-001`):

- يُنفذ كاستدعاء مباشر بين الموديولات عبر واجهة محددة (Interface).
- يُوثق كعقد في `api-contracts.md` بصيغة API (حتى لو لم يكن HTTP حقيقيًا حاليًا).
- يظل قابلًا للتحويل لاحقًا إلى API شبكي عند فصل الموديولات.

### API-032 — عقد الكتابة الداخلي

**التصنيف:** `MANDATORY`

لا يجوز لموديول تعديل بيانات موديول آخر مباشرة (`DMS-020`). التعديل يتم عبر:

1. استدعاء API/واجهة الموديول المالك.
2. إرسال حدث يُعالجه الموديول المالك (`event-contract-standard.md`).

## 13. التوافق مع اللغة والترجمة

### API-033 — ترويسة اللغة

**التصنيف:** `MANDATORY`

يُحدد المستهلك لغة الاستجابة عبر:

```text
Accept-Language: ar
```

- اللغة الأساسية للمنصة هي الافتراض (الافتراضي في الإطار: `ar`).
- اللغة الثانية (مثل `en`) عند دعمها.

تؤثر على:

- رسائل الخطأ (`ECS-012`).
- التسميات في البيانات المرجعية (`DD-012`).
- الترجمة الآلية للمحتوى الديناميكي عند الطلب (`BR-LANG-004`).

### API-034 — بيانات الترجمة

**التصنيف:** `MANDATORY WHEN APPLICABLE`

عند إرجاع محتوى ديناميكي:

```json
{
  "description": "وصف المنتج كما أدخله صاحبه...",
  "description_lang": "ar",
  "description_translated": "Product description as entered by its owner...",
  "is_translated": true
}
```

- `is_translated`: يُشير لكون النص مترجمًا آليًا (`BR-LANG-007`).
- `description_translated`: يُرجع فقط إذا طلب المستهلك لغة مختلفة عن `description_lang`.

## 14. بوابة الجودة

### API-035 — قائمة التحقق

**التصنيف:** `MANDATORY`

عند مراجعة `api-contracts.md` لأي موديول، يُتحقق من:

| # | البند | المرجع |
|---|---|---|
| 1 | المسارات تتبع الصيغة المعيارية | `API-005` |
| 2 | أفعال HTTP مستخدمة حسب المعنى | `API-006` |
