# Event Contract Standard — معيار عقود الأحداث

> يُحدد هذا المعيار القواعد العامة لعقود الأحداث بين الموديولات: التسمية، البنية، الملكية، التسليم، وضمانات المعالجة.
>
> يبني على `EP-SYNC-001..003`، `DMS-031..033` (أحداث المجال)، و`EP-XMOD-004` (منع الاعتماديات الدائرية).
>
> **ملاحظة تقنية:** آلية التنفيذ (الناقل، الطوابير) تُحسم في ملف تعريف الحزمة وبـADR (`EP-SYNC-003`). هذا المعيار يُحدد العقود المنطقية بصورة محايدة تقنيًا.

---

## 0. الغرض والنطاق

### 0.1 الغرض

يُحدد هذا المعيار:

- تسمية الأحداث وبنيتها.
- ملكية الأحداث.
- أنماط التسليم والاستهلاك.
- ضمانات المعالجة ومنع التكرار.
- كتالوج الأحداث المرجعي الأولي.
- توثيق عقود الأحداث لكل موديول.

### 0.2 ما لا يغطيه

- تفاصيل البنية التحتية (أسماء Topics وQueues) → تُحسم بعد `EP-SYNC-003` في ملف تعريف الحزمة.
- عقود الأحداث التفصيلية لكل موديول → `event-contracts.md`.
- API المتزامن → `api-design-standard.md`.

## 2. تسمية الأحداث

### EVT-001 — صيغة اسم الحدث

**التصنيف:** `MANDATORY`

```text
[ModuleCode].[EntityName].[PastTenseVerb]
```

- `ModuleCode`: كود الموديول المالك بالأحرف الكبيرة.
- `EntityName`: اسم الكيان PascalCase (`DMS-002`).
- `PastTenseVerb`: فعل ماضي يصف ما حدث.

أمثلة:

```text
CUS.Customer.Created
ORD.Order.Created
ORD.Order.Confirmed
ORD.OrderLine.Added
INV.Invoice.Issued
INV.Invoice.Paid
```

> المرجع: `DMS-032` — صيغة `[EntityName].[PastTenseVerb]` مع إضافة `ModuleCode` كبادئة.

### EVT-002 — معرّف عقد الحدث

**التصنيف:** `MANDATORY`

كل حدث في `event-contracts.md` يحمل معرّفًا:

```text
EVENT-[MODULE-CODE]-###
```

## 3. ملكية الأحداث

### EVT-003 — المنتج المالك

**التصنيف:** `MANDATORY`

لكل حدث منتج واحد فقط — الموديول الذي يملك الكيان الذي حدث عليه التغيير (`DMS-006`).

### EVT-004 — منع النشر عن الآخرين

**التصنيف:** `PROHIBITED`

لا يجوز لموديول نشر حدث عن كيان لا يملكه. إذا احتاج الموديول المستهلك إبلاغ الآخرين بتفاعله، يُنشئ حدثًا عن كيانه هو.

مثال:

```text
صحيح: موديول الفواتير (INV) يُنشر INV.Invoice.Paid
خطأ:  موديول الفواتير (INV) يُنشر ORD.Order.Completed (يملكه موديول الطلبات ORD)
```

## 4. بنية الحدث

### EVT-005 — البنية المعيارية

**التصنيف:** `MANDATORY`

```json
{
  "event_id": "evt_unique_id",
  "event_type": "ORD.Order.Confirmed",
  "event_version": "1.0",
  "produced_at": "2000-01-01T00:00:00Z",
  "producer": "ORD",
  "entity_type": "Order",
  "entity_id": "order_id_123",
  "correlation_id": "req_trace_id",
  "payload": {
    ...
  }
}
```

| الحقل | النوع | الوصف | إلزامي |
|---|---|---|---|
| `event_id` | string | معرّف فريد للحدث (UUID) | نعم |
| `event_type` | string | اسم الحدث (EVT-001) | نعم |
| `event_version` | string | إصدار بنية الحمولة | نعم |
| `produced_at` | string (ISO 8601 UTC) | وقت الإنتاج | نعم |
| `producer` | string | كود الموديول المنتج | نعم |
| `entity_type` | string | نوع الكيان | نعم |
| `entity_id` | string | معرّف الكيان | نعم |
| `correlation_id` | string | معرّف التتبع (`API-021`) | نعم |
| `payload` | object | البيانات الخاصة بالحدث | نعم |

### EVT-006 — محتوى الحمولة

**التصنيف:** `MANDATORY`

- الحمولة تتضمن البيانات الضرورية للمستهلكين — لا تتضمن الكيان بالكامل.
- البيانات الحساسة (`DD-008`) لا تُضمن في الحمولة — يُمرر المعرّف فقط ويقرأ المستهلك البيانات عبر عقد القراءة (`DMS-020`).
- المبالغ المالية تتبع `DD-013` (amount + currency).
- الأوقات بـ UTC (`DD-021`).

## 5. أنماط التسليم

### EVT-007 — الأنماط المعتمدة

**التصنيف:** `MANDATORY`

| النمط | الاستخدام | المرجع |
|---|---|---|
| **Publish-Subscribe** | حدث واحد له عدة مستهلكين مستقلين | الأحداث العابرة للموديولات |
| **Point-to-Point** | حدث موجه لمستهلك واحد | مهام خلفية محددة |
| **Request-Reply (Async)** | طلب غير متزامن مع استجابة مؤجلة | تكاملات خارجية ثقيلة |

### EVT-008 — حياد التنفيذ

**التصنيف:** `MANDATORY`

التصميم يُجرد عن آلية التسليم (`EP-SYNC-003`). العقد يُحدد:

- ما يُنشر (البنية).
- من ينتج (المالك).
- من يستهلك (المستهلكون).
- ضمانات التسليم.

ولا يُحدد:

- اسم Topic أو Queue.
- تقنية التنفيذ (ناقل رسائل مُدار، RabbitMQ، In-process).

## 6. ضمانات المعالجة

### EVT-009 — At-least-once

**التصنيف:** `MANDATORY`

ضمان التسليم الافتراضي: **at-least-once**. قد يصل الحدث أكثر من مرة.

### EVT-010 — Idempotent Consumer

**التصنيف:** `MANDATORY`

كل مستهلك يجب أن يكون idempotent — معالجة نفس الحدث أكثر من مرة لا تُنتج آثارًا جانبية مكررة:

1. يُتحقق من `event_id` قبل المعالجة (`DMOD-030`).
2. إذا عُولج مسبقًا: يُتجاهل.
3. إذا لم يُعالج: يُنفذ ويُسجل `event_id`.

### EVT-011 — Ordering

**التصنيف:** `MANDATORY WHEN APPLICABLE`

ترتيب الأحداث غير مضمون افتراضيًا. إذا احتاج المستهلك ترتيبًا:

- يُستخدم `produced_at` للترتيب الزمني.
- يُستخدم `entity_id` كمفتاح تقسيم (Partition Key) لضمان ترتيب أحداث نفس الكيان.

### EVT-012 — Dead Letter

**التصنيف:** `MANDATORY`

الأحداث التي تفشل معالجتها بعد عدد محدد من المحاولات تُحوَّل إلى Dead Letter:

- تُسجل مع سبب الفشل.
- تُراقب.
- تتطلب تدخل تشغيلي.

## 7. كتالوج الأحداث المرجعي

### EVT-013 — الكتالوج الأولي

**التصنيف:** `MANDATORY`

الكتالوج المرجعي يُشتق من `EP-SYNC-002` و`DMS-032..033` ومن القرارات المعتمدة للمشروع. كل موديول يوسعه في `event-contracts.md`. صيغة الكتالوج:

| الحدث | المنتج | المستهلكون المحتملون | المرجع |
|---|---|---|---|
| `{{MODULE_CODE}}.{{Entity}}.{{Verb}}` | `{{MODULE_CODE}}` | `{{CONSUMER_MODULE_CODES}}` | `DEC-*` / `BR-*` |

> **ملاحظة:** كتالوج الأحداث الشامل يُبنى تدريجيًا مع `event-contracts.md` لكل موديول، ويُوحَّد في `cross-module-contract-registry.md`.

### EVT-014 — تحديث الكتالوج

**التصنيف:** `MANDATORY`

عند إضافة حدث جديد في `event-contracts.md` لأي موديول:

1. يُضاف للكتالوج المرجعي.
2. يُحدد المنتج والمستهلكون.
3. يُتحقق من عدم تكرار حدث بنفس المعنى.
4. يُتحقق من عدم وجود اعتماديات دائرية (`EP-XMOD-004`).

## 8. توثيق عقود الأحداث

### EVT-015 — صيغة التوثيق

**التصنيف:** `MANDATORY`

كل حدث في `event-contracts.md` يُوثق:

| الخاصية | الوصف |
|---|---|
| المعرّف | `EVENT-[MODULE-CODE]-###` |
| الاسم | `[ModuleCode].[Entity].[Verb]` |
| الوصف | ما يعنيه الحدث |
| المنتج | الموديول المالك |
| المحفز | ما يُسبب نشر الحدث |
| بنية الحمولة | الحقول وأنواعها |
| المستهلكون | الموديولات المستهلكة وماذا تفعل |
| ضمان التسليم | at-least-once (افتراضي) |
| ملاحظات | قيود أو قواعد أعمال |

### EVT-016 — إصدارات الحمولة

**التصنيف:** `MANDATORY`

- `event_version` يتبع الإصدارات الدلالية (major.minor).
- تغيير minor: إضافة حقول اختيارية (backward-compatible).
- تغيير major: تغيير بنية أو حذف حقول (breaking).
- المستهلكون يجب أن يتجاهلوا الحقول غير المعروفة (forward-compatible).

## ملاحظةُ تطبيقٍ على `EVT-002` — فضاءا المعرّفات `EVT-*`

> `EVENT-[MODULE-CODE]-###` يبقى صيغةَ ملفات `event-contracts.md` كما ينصّ `EVT-002`. **والمعرّفاتُ `EVT-[CODE]-###` قد تعيش في المستودع في فضاءين يُقرأ كلٌّ في وثيقته:** أحداثُ المجال في أقسام الأحداث بنماذج البيانات والعقود (`data-model.md` لكل موديول)، وأنواعُ الإشعارات في كتالوج موديول الإشعارات (`requirements.md` الخاص به) — و«فريدٌ عالميًّا» في قاعدة عمل الإشعارات يخصّ الكتالوجَ الثاني. **قاعدةُ حجز:** كلُّ معرّف `EVT-*` جديدٍ يُسكّ حرًّا في الفضاءين معًا. **تصادمٌ قائمٌ يُعلَن ولا يُعاد ترقيمُه:** تُسجَّل المعرّفات المتصادمة في سجل القرارات، والنداءاتُ في الجهتين بالاسم لا بالرقم. **لا إعادةَ تسميةٍ لأيّ إحالة.**
