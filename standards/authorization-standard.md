# Authorization Standard — معيار التفويض والصلاحيات

> يُحدد هذا المعيار القواعد التقنية للتفويض وإدارة الصلاحيات: نموذج RBAC، أنماط التحقق من الصلاحيات، نطاق الوصول للبيانات، وحوكمة الصلاحيات الحساسة.
>
> يبني على `EP-AUTHZ-001..005` ويُفصِّل التنفيذ المؤجل فيها.
>
> **الملكية:** تعريف الأدوار والصلاحيات الأساسية مملوك لموديول الهوية والوصول (`{{MODULE_CODE}}`). كل موديول يُعرِّف صلاحياته التفصيلية في `permission-matrix.md`.

---

## 0. الغرض والنطاق

### 0.1 الغرض

يُحدد هذا المعيار:

- نموذج RBAC المعتمد.
- بنية الأدوار والصلاحيات.
- أنماط التحقق من الصلاحيات (API-level، Data-level).
- نطاق الوصول للبيانات (Data Scope).
- حوكمة الصلاحيات الحساسة (`HG-E-03`).
- سلوك الواجهة عند غياب الصلاحية.

### 0.2 ما لا يغطيه

- المصادقة وإدارة الجلسات → `authentication-standard.md`.
- الصلاحيات التفصيلية لكل موديول → `permission-matrix.md` (Phase 0).
- ضوابط الأمن الشاملة → `security-architecture.md`.

## 2. نموذج RBAC

### AUTHZ-001 — النموذج الأساسي

**التصنيف:** `MANDATORY`

النظام يعتمد RBAC (`EP-AUTHZ-001`):

```text
User → Role(s) → Permission(s) → Resource + Action
```

### AUTHZ-002 — تعدد الأدوار

**التصنيف:** `MANDATORY`

الحساب متعدد الأدوار (`EP-AUTHZ-002`). الأدوار النشطة تُقرأ من قاعدة البيانات عند كل طلب (`AUTH-011`).

### AUTHZ-003 — الأدوار المعتمدة

**التصنيف:** `MANDATORY`

الأدوار المعتمدة تُشتق من `glossary.md` (قسم الأدوار) ومن القرارات المعتمدة في `project-decisions.md`. لكل دور: رمز، نوع (عام · تجاري · متخصص · إداري)، وطريقة منح (تلقائي · سياقي · طلب + اعتماد إداري · تعيين):

| الدور | الرمز | النوع | طريقة المنح | المرجع |
|---|---|---|---|---|
| `{{ROLE_NAME}}` | `{{ROLE_CODE}}` | `{{TYPE}}` | `{{GRANT_METHOD}}` | `glossary.md` / `DEC-*` |
| مشرف وحدة | `SUPERVISOR` | إداري | تعيين من SYSADMIN | `glossary.md` |
| مدير النظام | `SYSADMIN` | إداري | تعيين حصري | `glossary.md` |

> الدوران الإداريان `SUPERVISOR` و`SYSADMIN` تعتمد عليهما معايير أخرى (`AUD-010`، `AUTHZ-017`) فيُحتفظ بهما في كل مشروع؛ بقية الأدوار من المجال.

### AUTHZ-004 — حجب الدور

**التصنيف:** `MANDATORY`

حجب الدور (`glossary.md`) يُوقف صلاحيات الدور المحجوب مع بقاء الحساب نشطًا وبقية الأدوار عاملة. يتطلب مبررًا إلزاميًا (`DD-025`).

## 3. بنية الصلاحيات

### AUTHZ-005 — معرّف الصلاحية

**التصنيف:** `MANDATORY`

كل صلاحية تحمل معرّفًا بالصيغة:

```text
PERM-[MODULE-CODE]-[ACTION]-[RESOURCE]
```

مثال: `PERM-ORD-CREATE-ORDER`, `PERM-INV-DELETE-INVOICE`.

### AUTHZ-006 — أنواع الإجراءات

**التصنيف:** `MANDATORY`

| الإجراء | الرمز | الوصف |
|---|---|---|
| عرض | `VIEW` | قراءة المورد |
| إنشاء | `CREATE` | إنشاء مورد جديد |
| تعديل | `EDIT` | تحديث مورد قائم |
| حذف | `DELETE` | حذف (منطقي عادةً) |
| اعتماد | `APPROVE` | الموافقة على طلب أو عملية |
| رفض | `REJECT` | رفض طلب أو عملية |
| إلغاء | `CANCEL` | إلغاء عملية قائمة |
| تصدير | `EXPORT` | تصدير البيانات |

### AUTHZ-007 — المرجعية

**التصنيف:** `MANDATORY`

لا تُدرج صلاحية حساسة دون مرجع صريح في `permission-matrix.md` (`EP-AUTHZ-003`، `HG-E-03`).

## 4. التحقق من الصلاحيات

### AUTHZ-008 — الرفض الافتراضي

**التصنيف:** `MANDATORY`

الوصول مرفوض افتراضيًا (`EP-SEC-002`). كل مورد أو عملية محمية ما لم يُصرَّح بالوصول صراحة.

### AUTHZ-009 — مستويات التحقق

**التصنيف:** `MANDATORY`

التحقق يتم على مستويين:

| المستوى | الوصف | مثال |
|---|---|---|
| **الإجراء** (Action-level) | هل يملك المستخدم صلاحية الإجراء على نوع المورد | هل يستطيع العميل إنشاء طلب |
| **البيانات** (Data-level) | هل يحق للمستخدم الوصول لهذا السجل بالذات | هل هذا الطلب يخص المستخدم الحالي |

### AUTHZ-010 — نمط التحقق في API

**التصنيف:** `MANDATORY`

1. **المصادقة أولًا:** التحقق من رمز الجلسة (`AUTH-010..015`).
2. **التحقق من الدور:** هل أحد أدوار المستخدم يملك الصلاحية المطلوبة.
3. **التحقق من نطاق البيانات:** هل المستخدم يملك حق الوصول لهذا السجل (§5).
4. **تنفيذ العملية** عند نجاح جميع الخطوات.

### AUTHZ-011 — الفشل الآمن

**التصنيف:** `MANDATORY`

- عدم وجود صلاحية → `403 Forbidden` (`API-011`).
- عدم المصادقة → `401 Unauthorized`.
- المورد غير موجود مع عدم وجود صلاحية → `403` (لا يُكشف وجود المورد).

## 5. نطاق الوصول للبيانات

### AUTHZ-012 — أنماط نطاق الوصول

**التصنيف:** `MANDATORY`

| النمط | الوصف | أمثلة |
|---|---|---|
| `OWN` | بيانات المستخدم نفسه | ملفي الشخصي، طلباتي، فواتيري |
| `ASSIGNED` | بيانات مُعيّنة للمستخدم | الطلبات المسندة إلى الموظف المختص |
| `MODULE` | جميع بيانات الموديول | مشرف الوحدة يرى جميع طلبات الموديول |
| `ALL` | جميع البيانات المصرح بها للدور | SYSADMIN |

### AUTHZ-013 — توثيق النطاق

**التصنيف:** `MANDATORY`

في `permission-matrix.md` لكل موديول، يُحدد نطاق الوصول لكل صلاحية عرض:

```markdown
| الدور | الإجراء | المورد | النطاق | المرجع |
|---|---|---|---|---|
| CUSTOMER | VIEW | Order | OWN | FR-ORD-001 |
| SUPERVISOR | VIEW | Order | MODULE | FR-ORD-002 |
```

## 6. سلوك الواجهة عند غياب الصلاحية

### AUTHZ-014 — أنماط السلوك

**التصنيف:** `MANDATORY`

يُحدد في `permission-matrix.md` و`screens/` لكل عنصر:

| السلوك | الاستخدام |
|---|---|
| **إخفاء** (Hidden) | العنصر لا يظهر إطلاقًا |
| **تعطيل** (Disabled) | العنصر ظاهر لكن غير قابل للتفاعل |
| **قراءة فقط** (Read-only) | البيانات ظاهرة لكن غير قابلة للتعديل |
| **رفض وصول** (Access Denied) | رسالة منع وصول عند محاولة الدخول |

### AUTHZ-015 — القاعدة الافتراضية

**التصنيف:** `MANDATORY`

إذا لم يُحدد السلوك صراحة في `permission-matrix.md`، الافتراضي هو **إخفاء** (`Hidden`).

## 7. الصلاحيات الحساسة

### AUTHZ-016 — بوابة الصلاحيات الحساسة

**التصنيف:** `MANDATORY`

الصلاحيات التي تؤثر على:

- المال أو المعاملات المالية.
- تعطيل أو حذف الحسابات.
- تغيير حالة معاملة تجارية.
- تعديل العمولات أو الإعدادات المالية.
- الوصول لبيانات شخصية حساسة.
- تعديل الأدوار أو الصلاحيات.

تخضع لبوابة `HG-E-03` وتتطلب:

1. مرجع صريح في `permission-matrix.md`.
2. تسجيل في Audit Log (موديول سجل التدقيق `{{MODULE_CODE}}`).
3. مراجعة مالك المنتج عند إضافتها.

### AUTHZ-017 — فصل المستخدمين الداخليين

**التصنيف:** `MANDATORY`

المستخدمون الإداريون (SUPERVISOR، SYSADMIN) حسابات منفصلة وليسوا حسابات عادية بصلاحيات مرتفعة (`EP-AUTHZ-004`).
