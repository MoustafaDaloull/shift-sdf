# Data Modeling Standard — معيار النمذجة التقنية للبيانات

> يُحدد هذا المعيار الأنماط التقنية لنمذجة البيانات: بنية الجداول، الأنواع، القيود، التحكم في التزامن، حدود المعاملات، الحذف المنطقي، والتدقيق.
>
> يبني على `domain-modeling-standard.md` الذي يُحدد الكيانات والملكية والعلاقات على المستوى المنطقي. هذا المعيار يُترجم تلك القواعد إلى أنماط تقنية.
>
> **أولوية هذا الملف:** يخضع لأولوية `engineering-principles.md` (§0.3).
>
> القواعد المرتبطة بحزمة تقنية بعينها تُطبَّق عبر ملف تعريف الحزمة `profiles/<name>/`؛ الافتراضي `laravel-react`.

---

## 0. الغرض والنطاق

### 0.1 الغرض

يُحدد هذا المعيار:

- قواعد تسمية الجداول والأعمدة.
- الأعمدة المعيارية المشتركة (Base Columns).
- أنواع البيانات المعتمدة.
- أنماط التحكم في التزامن (`EP-CONC-001..002`).
- أنماط حدود المعاملات (`EP-TXN-001..004`).
- أنماط الحذف المنطقي والاحتفاظ.
- أنماط تتبع التعديل (Audit Trail على مستوى الصف).
- قواعد المراجع العابرة للموديولات على مستوى قاعدة البيانات.
- قواعد الفهرسة الأساسية.

### 0.2 ما لا يغطيه

- تعريف الكيانات وملكيتها → `domain-modeling-standard.md`.
- عقود API → `api-design-standard.md`.
- تصميم الجداول التفصيلي لكل موديول → `data-model.md`.
- اختيار محرك قاعدة البيانات المحدد → ADR الحزمة التقنية (`ADR-ARCH-001`) وملف تعريف الحزمة.

### 0.3 ملاحظة التقنية

محرك قاعدة البيانات يُحسم بـADR الحزمة التقنية (في الملف التعريفي الافتراضي `laravel-react`: MySQL). هذا المعيار مكتوب بصورة تتوافق مع أي قاعدة بيانات علائقية مُدارة. الأمثلة تستخدم صيغة SQL معيارية. عند اعتماد المحرك رسميًا، قد يُضاف ملحق بأنماط خاصة بالمحرك داخل ملف تعريف الحزمة.

## 2. تسمية الجداول والأعمدة

### DMOD-001 — تسمية الجداول

**التصنيف:** `MANDATORY`

- اسم الجدول بالإنجليزية، `snake_case`، جمع.
- يبدأ بكود الموديول المالك كبادئة.
- لا تُستخدم الكلمات المحجوزة في SQL.

```text
الصيغة: [module_code]_[entity_name_plural]
مثال:  cus_customers, ord_orders, inv_invoices
```

### DMOD-002 — تسمية الأعمدة

**التصنيف:** `MANDATORY`

- اسم العمود بالإنجليزية، `snake_case`.
- المعرّف الأساسي: `id`.
- المراجع الخارجية: `[referenced_entity]_id`.
- لا تبدأ الأعمدة بكود الموديول (البادئة على الجدول فقط).

```text
مثال: id, phone_number, created_at, customer_id, order_id
```

### DMOD-003 — تسمية الفهارس والقيود

**التصنيف:** `MANDATORY`

| العنصر | الصيغة | مثال |
|---|---|---|
| المفتاح الأساسي | `pk_[table]` | `pk_cus_customers` |
| المفتاح الخارجي | `fk_[table]_[column]` | `fk_ord_orders_customer_id` |
| الفهرس | `idx_[table]_[columns]` | `idx_ord_orders_status_created_at` |
| القيد الفريد | `uq_[table]_[columns]` | `uq_cus_customers_phone_number` |
| القيد التحققي | `ck_[table]_[description]` | `ck_inv_invoices_amount_positive` |

## 3. الأعمدة المعيارية المشتركة

### DMOD-004 — أعمدة الهوية والتتبع

**التصنيف:** `MANDATORY`

كل جدول كيان جوهري أو داعم يتضمن الأعمدة التالية:

| العمود | النوع | الوصف | الإلزامية |
|---|---|---|---|
| `id` | UUID أو BIGINT | المعرّف الأساسي الفريد | إلزامي |
| `created_at` | TIMESTAMP WITH TIME ZONE | وقت الإنشاء — يُملأ تلقائيًا ولا يُعدَّل | إلزامي |
| `updated_at` | TIMESTAMP WITH TIME ZONE | وقت آخر تعديل — يُحدَّث تلقائيًا | إلزامي |
| `created_by` | UUID/BIGINT (مرجع User) | معرّف المنشئ | إلزامي عند الانطباق |
| `updated_by` | UUID/BIGINT (مرجع User) | معرّف آخر مُعدِّل | إلزامي عند الانطباق |

### DMOD-005 — أعمدة الحذف المنطقي

**التصنيف:** `MANDATORY WHEN APPLICABLE`

الكيانات التي تخضع لسياسة Soft Delete (§7) تتضمن:

| العمود | النوع | الوصف |
|---|---|---|
| `deleted_at` | TIMESTAMP WITH TIME ZONE (nullable) | وقت الحذف المنطقي — `NULL` يعني نشط |
| `deleted_by` | UUID/BIGINT (nullable) | معرّف من نفذ الحذف |

### DMOD-006 — عمود إصدار التزامن

**التصنيف:** `MANDATORY WHEN APPLICABLE`

الكيانات التي تخضع لـ Optimistic Locking (§5) تتضمن:

| العمود | النوع | الوصف |
|---|---|---|
| `version` | INTEGER | يبدأ من `1` ويتزايد مع كل تحديث |

## 4. أنواع البيانات المعتمدة

### DMOD-007 — الأنواع المعيارية

**التصنيف:** `MANDATORY`

| نوع المجال | النوع المعياري | ملاحظات |
|---|---|---|
| معرّف فريد | UUID أو BIGINT | يُختار نوع واحد على مستوى المشروع ويُثبَّت |
| نص قصير | VARCHAR(N) | يُحدد الحد الأقصى لكل حقل |
| نص طويل | TEXT | للأوصاف والمحتوى الحر |
| عدد صحيح | INTEGER أو BIGINT | حسب نطاق القيم |
| رقم عشري مالي | DECIMAL(precision, scale) | **إلزامي لجميع المبالغ المالية** — لا يُستخدم FLOAT أو DOUBLE |
| تاريخ ووقت | TIMESTAMP WITH TIME ZONE | جميع الأوقات بـ UTC — يُحوَّل للمنطقة المحلية عند العرض |
| تاريخ فقط | DATE | للتواريخ بدون وقت |
| منطقي | BOOLEAN | `true` / `false` |
| حالة | VARCHAR أو ENUM | حسب المحرك — القيم من `DMS-024` |
| لغة | VARCHAR(5) | رمز لغة (`ar`، `en`) |
| عملة | VARCHAR(3) | رمز العملة ISO 4217 |
| JSON مرن | JSONB (أو ما يعادله) | للبيانات شبه المهيكلة — يُستخدم بحذر مع توثيق البنية |

### DMOD-008 — قواعد المبالغ المالية

**التصنيف:** `MANDATORY`

- جميع المبالغ المالية تُخزَّن بنوع `DECIMAL` بدقة كافية (مثل `DECIMAL(12,2)`).
- لا يُستخدم `FLOAT` أو `DOUBLE` للمبالغ المالية إطلاقًا.
- العملة تُخزَّن صراحة مع المبلغ (حتى لو كان المشروع يعمل بعملة واحدة حصريًا حاليًا — جاهزية بنيوية لعملات لاحقة).
- يُستخدم كائن القيمة `Money` (`DMS-016`) لتمثيل المبالغ.

## 5. التحكم في التزامن (Concurrency Control)

### DMOD-009 — القاعدة العامة

**التصنيف:** `MANDATORY WHEN APPLICABLE`

كل عملية تعديل على كيان قابل للتعديل المتزامن يجب أن تكون محمية (`EP-CONC-001`). يُختار النمط المناسب حسب الحالة (`EP-CONC-002`).

### DMOD-010 — Optimistic Locking

**التصنيف:** `MANDATORY WHEN APPLICABLE`

النمط الافتراضي للعمليات التي يندر فيها التزامن الفعلي:

1. الكيان يحمل عمود `version` (`DMOD-006`).
2. عند القراءة: يُقرأ `version` مع البيانات.
3. عند التحديث: يُشترط `WHERE id = :id AND version = :read_version`.
4. إذا لم تتأثر أي صفوف: العملية فشلت بسبب تزامن — يُرجع خطأ `BUSINESS_RULE` (`ECS-001`).
5. عند النجاح: `version = version + 1`.

**حالات الاستخدام المرجعية:**

- تعديل بيانات الطلب (`ENT-ORD-001`).
- تعديل بيانات العميل (`ENT-CUS-001`).
- تعديل إعدادات النظام (كيان الإعداد النظامي في موديول الإعدادات).
- تعديل الملف الشخصي.

### DMOD-011 — Pessimistic Locking

**التصنيف:** `MANDATORY WHEN APPLICABLE`

للعمليات الحرجة التي لا يُقبل فيها أي فشل بسبب التزامن:

1. يُقفل الصف عند بداية المعاملة (`SELECT ... FOR UPDATE` أو ما يعادله).
2. يُنفَّذ التحديث.
3. يُفك القفل عند انتهاء المعاملة.

**قواعد الاستخدام:**

- يُستخدم فقط عند الحاجة الحقيقية — القفل المتشائم يؤثر على الأداء.
- مدة القفل يجب أن تكون أقصر ما يمكن.
- يُوثق السبب في `data-model.md`.

### DMOD-012 — Atomic Compare-and-Swap

**التصنيف:** `MANDATORY WHEN APPLICABLE`

لعمليات التحديث الذرية البسيطة على قيمة واحدة:

```text
UPDATE table SET value = :new_value WHERE id = :id AND value = :expected_value
```

**حالات الاستخدام المرجعية:**

- تحديث رصيد (بشرط أن القيمة الحالية مطابقة للمتوقع).
- تحديث حالة (بشرط الحالة الحالية — يتقاطع مع `DMS-025`).

### DMOD-013 — Queue-based Serialization

**التصنيف:** `MANDATORY WHEN APPLICABLE`

لتحويل العمليات المتنافسة إلى تسلسل مُدار:

- العمليات تُدرج في قائمة انتظار.
- تُعالج بالترتيب بواسطة عامل واحد (أو عملية واحدة).

**ملاحظة:** التفاصيل التقنية (ناقل الرسائل، الطوابير) تعتمد على آلية المعالجة غير المتزامنة المحسومة في ملف تعريف الحزمة (`EP-SYNC-003`).

### DMOD-014 — توثيق نمط التزامن

**التصنيف:** `MANDATORY`

في `data-model.md` لكل موديول، يُوثق لكل كيان يخضع لحماية التزامن:

1. الكيان والعملية المحمية.
2. النمط المختار (Optimistic / Pessimistic / CAS / Queue).
3. السبب.
4. السلوك عند فشل التزامن (رسالة الخطأ، إعادة المحاولة، أو رفض).

## 6. حدود المعاملات (Transaction Boundaries)

### DMOD-015 — معاملة لكل مجموعة

**التصنيف:** `MANDATORY`

كل معاملة قاعدة بيانات تعمل على مجموعة واحدة فقط (`DMS-012`، `EP-TXN-002`).

### DMOD-016 — المعاملة العابرة للمجموعات

**التصنيف:** `MANDATORY`

المعاملة الواحدة العابرة لحدود مجموعتين (حتى داخل نفس الموديول) هي **استثناء معماري** يتطلب:

1. تبرير موثق في `data-model.md`.
2. مراجعة المهندس المعماري.
3. التأكد من أن الجمع لا يُقيّد الفصل المستقبلي (`EP-ARCH-003`).

### DMOD-017 — المعاملة العابرة للموديولات

**التصنيف:** `MANDATORY`

لا تُستخدم معاملة قاعدة بيانات واحدة عابرة لحدود موديولين (`EP-TXN-002`). بدلاً من ذلك:

- كل موديول يُدير معاملته مستقلًا.
- يُستخدم الاتساق التدريجي (Eventual Consistency) مع آليات التعويض (`EP-TXN-004`).
- العمليات المالية تخضع لبوابة `HG-E-02`.

### DMOD-018 — توثيق المعاملات

**التصنيف:** `MANDATORY`

في `data-model.md` لكل موديول، يُوثق:

1. المعاملات الرئيسية (ما يُقرأ، ما يُكتب، الحدود).
2. أي معاملة استثنائية عابرة للمجموعات مع التبرير.
3. حالات الاتساق التدريجي مع آلية التعويض.

## 7. الحذف المنطقي والاحتفاظ

### DMOD-019 — القاعدة العامة

**التصنيف:** `MANDATORY`

لا يُحذف أي سجل أعمال فعليًا (Hard Delete) من قاعدة البيانات إلا وفق سياسة معتمدة (`EP-RET-003`، `DMS-028`).

### DMOD-020 — أنماط الحذف

**التصنيف:** `MANDATORY`

| النمط | التنفيذ | الحالات |
|---|---|---|
| **Soft Delete** | `deleted_at` يُملأ بوقت الحذف (`DMOD-005`) | الكيانات الجوهرية القابلة للإلغاء أو الأرشفة |
| **RETENTION_HOLD** | `retention_until` يُحدد تاريخ انتهاء الاحتفاظ | وثائق حساسة مُستبدَلة — `{{RETENTION_HOLD_DAYS}}` يومًا (قرار المشروع) |
| **Hard Delete مُجدوَل** | حذف فعلي بعد انتهاء مدة الاحتفاظ | بعد انتهاء `RETENTION_HOLD` |
| **لا حذف** | لا حذف إطلاقًا | سجلات التدقيق (`AUD-007`) |

### DMOD-021 — الاستعلامات والحذف المنطقي

**التصنيف:** `MANDATORY`

- الاستعلامات الافتراضية تستبعد السجلات المحذوفة منطقيًا (`WHERE deleted_at IS NULL`).
- يُوصى باستخدام عرض (View) أو نطاق افتراضي (Default Scope) لتجنب نسيان الشرط.
- الواجهات الإدارية قد تحتاج الوصول للسجلات المحذوفة — يُوثق ذلك صراحة.

## 8. تتبع التعديل (Row-level Audit Trail)

### DMOD-022 — التتبع الأساسي

**التصنيف:** `MANDATORY`

الأعمدة المعيارية (`created_at`, `updated_at`, `created_by`, `updated_by` — `DMOD-004`) توفر تتبعًا أساسيًا لكل صف.

### DMOD-023 — سجل التغييرات التفصيلي

**التصنيف:** `MANDATORY WHEN APPLICABLE`

الكيانات التي تتطلب تتبع القيم القديمة والجديدة (مثل الكيانات المالية، انتقالات الحالة الحساسة) تُستخدم لها إحدى الآليتين:

1. **جدول تاريخ** (History Table): `[table]_history` يحفظ كل تعديل مع القيم القديمة والجديدة.
2. **Audit Log عبر موديول سجل التدقيق (`{{MODULE_CODE}}`)**: يُرسل حدث التغيير لموديول سجل التدقيق الذي يحفظه في كيان `AuditRecord` (`EP-AUD-005`).

> الآلية الأولى لتتبع على مستوى الموديول. الثانية لتدقيق الحوكمة العام. قد تُستخدم كلتاهما معًا للكيانات الحساسة.

---

## 9. المراجع العابرة للموديولات على مستوى قاعدة البيانات

### DMOD-024 — مرجع بالمعرّف فقط

**التصنيف:** `MANDATORY`

عند الإشارة لكيان في موديول آخر (`DMS-019`):

- يُخزَّن معرّف الكيان المستهدف كعمود عادي (وليس كمفتاح خارجي مُقيَّد بـ Foreign Key Constraint).
- لا يُنشأ `FOREIGN KEY` عابر لحدود الموديول — هذا يُقيّد الفصل المستقبلي (`EP-ARCH-003`).

### DMOD-025 — التسمية

**التصنيف:** `MANDATORY`

عمود المرجع العابر يُسمى:

```text
[entity_name]_id
```

ويُوثق في `data-model.md` أنه مرجع عابر مع ذكر الموديول المالك.

### DMOD-026 — سلامة البيانات

**التصنيف:** `MANDATORY`

بدون Foreign Key Constraint عابر، تُضمن سلامة البيانات عبر:

1. التحقق عند الكتابة — التأكد من وجود الكيان المستهدف قبل الإدراج أو التحديث (عبر عقد الوصول).
2. التعامل مع الحذف — إذا حُذف الكيان المستهدف منطقيًا، يُحدد السلوك في `data-model.md` (إبقاء المرجع مع علامة "غير نشط"، أو تحديث المرجع).

## 10. الفهرسة

### DMOD-027 — قواعد الفهرسة

**التصنيف:** `MANDATORY`

1. كل `id` يحمل فهرسًا أساسيًا (Primary Key).
2. كل عمود مرجع خارجي (`*_id`) يحمل فهرسًا.
3. أعمدة البحث والفلترة المتكررة تحمل فهارس مركبة حسب أنماط الاستعلام.
4. عمود `deleted_at` يُفهرس إذا استُخدم Soft Delete.
5. أعمدة `status` / `state` تُفهرس إذا استُخدمت في الفلترة.

### DMOD-028 — توثيق الفهارس

**التصنيف:** `MANDATORY`

في `data-model.md` لكل موديول، تُوثق الفهارس الرئيسية مع السبب ونمط الاستعلام الذي تخدمه.

---

## 11. منع التكرار (Idempotency) على مستوى البيانات

### DMOD-029 — القيود الفريدة

**التصنيف:** `MANDATORY WHEN APPLICABLE`

العمليات التي يجب أن تكون idempotent (`EP-IDEM-001`) تُحمى على مستوى قاعدة البيانات عبر:

1. **Natural Key / Unique Constraint** (`EP-IDEM-002`): قيد تفرّد على الحقول التي تُعرِّف العملية بشكل طبيعي.
2. **Idempotency Key**: عمود مخصص (`idempotency_key`) بقيد فريد — يُرسله المستهلك مع الطلب.
3. **State Check**: شرط الحالة الحالية في جملة `WHERE` (يتقاطع مع `DMOD-012`).

### DMOD-030 — Deduplication Window

**التصنيف:** `MANDATORY WHEN APPLICABLE`

لمعالجة Webhooks والأحداث المكررة (`EP-IDEM-002`):

- يُحفظ معرّف الحدث المُعالج في جدول `processed_events` مع وقت المعالجة.
- الأحداث ذات المعرّف المُعالج سابقًا تُتجاهل.
- يُحدد حجم نافذة الاحتفاظ (مثل 7 أيام) وتُحذف السجلات القديمة.

## 12. قواعد خاصة

### DMOD-031 — تخزين الوسائط

**التصنيف:** `PROHIBITED`

لا تُحفظ الصور أو الفيديوهات أو أي ملف ثنائي داخل جداول قاعدة البيانات (`EP-DATA-003`). يُحفظ فقط:

- معرّف الملف في Object Storage.
- البيانات الوصفية (النوع، الحجم، الحالة، الارتباط).

### DMOD-032 — تخزين الأوقات

**التصنيف:** `MANDATORY`

جميع الأوقات تُخزَّن بـ UTC. التحويل للمنطقة الزمنية المحلية يتم عند العرض فقط.

### DMOD-033 — تخزين المبالغ المالية

**التصنيف:** `MANDATORY`

يُحيل إلى `DMOD-008`. كل مبلغ مالي يُخزَّن مع رمز العملة صراحة حتى لو كان المشروع يعمل بعملة واحدة حصريًا حاليًا.

## 14. القرارات المفتوحة ذات الأثر على هذا المعيار

| القرار | الأثر | الحالة | المرجع |
|---|---|---|---|
| محرك قاعدة البيانات | قد يُضاف ملحق بأنماط خاصة بالمحرك | يُحسم بـADR الحزمة التقنية | `ADR-ARCH-001` |
| نوع المعرّف الأساسي (UUID vs BIGINT) | يجب حسمه قبل أول `data-model.md` | `OPEN` — يُحسم لكل مشروع بقرار | `DMOD-007` |

| النمط المعماري (Modular Monolith) | يؤثر على مستوى الفصل الفعلي بين قواعد البيانات | يُحسم بـADR الحزمة التقنية | `EP-ARCH-001` |
