# بوابة جودة نموذج البيانات — Data Model Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/data-model-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن `data-model.md` يصف الكيانات والحقول والعلاقات والقيود والملكية ودورة الحياة بصورة متسقة مع المتطلبات وقواعد العمل والتدفقات والشاشات وAPI.

---

## 2. متى تُنفذ؟

- بعد إعداد أو تعديل `data-model.md`.
- قبل اعتماد API أو تنفيذ Backend أو شاشات تعتمد على بيانات جديدة.
- عند تغيير كيان أو حالة أو علاقة أو سياسة احتفاظ.

---

## 3. المراجع والمدخلات الإلزامية

- `requirements.md`
- `business-rules.md`
- `user-flows.md`
- `screen-inventory.md`
- `screens/`
- `api-contracts.md`
- `module-registry.md`
- `business-rules-global.md`
- `قرارات المشروع ومراجع الموديولات المالكة`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. اربط كل كيان وحقله بمتطلب أو قاعدة أو تدفق.
2. تحقق من الملكية قبل اقتراح كيان مشترك جديد.
3. اختبر علاقات الإنشاء والتعديل والحذف والأرشفة.
4. طابق النموذج مع الحقول المعروضة وContracts.
5. أخرج تقريرًا ثم أصلح Critical وHigh وأعد المراجعة.

---

## 5. قائمة التحقق

### الهوية والملكية

- [ ] كل كيان له اسم ومعرف ووصف ومالك واضح.
- [ ] لا توجد نسخة محلية مكررة من User أو Payment أو Notification أو كيان مشترك دون سبب.
- [ ] مسؤولية الإنشاء والتحديث والحذف أو الأرشفة مفهومة.
- [ ] الأسماء متسقة مع Glossary والموديولات الأخرى.

### الحقول

- [ ] كل حقل يحدد الاسم والنوع المنطقي والوصف والإلزامية والقيمة الافتراضية عند الحاجة.
- [ ] الحقول الحساسة معلّمة ومقيدة.
- [ ] الحقول المحسوبة تحدد مصدرها وقاعدة احتسابها.
- [ ] Lookup وEnums تحدد المصدر والمالك والقيم المسموحة.
- [ ] التواريخ والمنطقة الزمنية والعملات والوحدات والدقة والتقريب واضحة عند الحاجة.
- [ ] لا توجد حقول بلا استخدام أو مصدر موثق.

### العلاقات والقيود

- [ ] Cardinality والمفاتيح المرجعية وقيود التكامل واضحة.
- [ ] سلوك الحذف أو الأرشفة أو التعطيل للعلاقات موثق.
- [ ] Business Keys وUnique Constraints محددة عند الحاجة.
- [ ] لا توجد تبعيات دائرية أو علاقات تنتج فقدان بيانات غير مقصود.
- [ ] الحالة والملكية متسقتان مع العلاقات.

### دورة الحياة والاتساق

- [ ] حالة السجل والحذف والأرشفة والإخفاء والتعطيل مميزة بوضوح.
- [ ] Audit Log والاحتفاظ والاسترجاع وAnonymization محددة عند الحاجة.
- [ ] Versioning أو optimistic locking مذكوران عند الحاجة.
- [ ] حقول الشاشات وAPI متسقة مع النموذج.
- [ ] قيود البيانات تطابق قواعد التحقق ورسائل الخطأ.

### الجودة التقنية

- [ ] تم تجنب تخزين بيانات مشتقة بلا مبرر.
- [ ] لم تستخدم نصوص حرة بدل Enums للحالات المحددة دون سبب.
- [ ] القوائم والوسائط والبيانات الضخمة تراعي الأداء.
- [ ] احتياجات البحث والفهرسة أو البيانات المرجعية موثقة عند الحاجة.

---

## 6. أسباب الرفض أو الإيقاف

- كيان أو حقل بلا مالك أو غرض أو مصدر.
- تعارض Data Model مع Rule أو API أو Screen.
- علاقة قد تسبب فقدان بيانات أو خرق خصوصية أو ملكية.
- منطق مالي أو State بلا قرار.
- غياب قيد أساسي يمنع تكرارًا أو عدم اتساق معروف.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | خطأ في النطاق أو المال أو الأمان أو الصلاحيات أو القانون أو حالة السجل | يمنع الاعتماد |
| High | نقص أو تعارض قد يسبب تنفيذًا خاطئًا أو إعادة عمل كبيرة | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

---

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## قابلية التتبع
| Entity / Field | Owner | Source Requirement / Rule | Screen / API Usage | Result |
|---|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- عدد `Critical = 0` و`High = 0`.
- الكيانات والحقول والعلاقات لها ملكية واستخدام ومصدر واضح.
- الخصوصية ودورة الحياة والتدقيق والقيود مغطاة عند الحاجة.
- النموذج متسق مع الشاشات وAPI وقواعد العمل.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
