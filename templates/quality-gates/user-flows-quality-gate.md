# بوابة جودة تدفقات المستخدم — User Flows Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/user-flows-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن `user-flows.md` يصف رحلات المستخدم والعمليات التشغيلية بصورة كاملة ومنطقية، قابلة للتحويل إلى شاشات وAPI وقصص مستخدم وسيناريوهات اختبار.

---

## 2. متى تُنفذ؟

- بعد إعداد أو تعديل `user-flows.md`.
- قبل اعتماد `screen-inventory.md`.
- عند تغيير قواعد العمل أو الصلاحيات أو حالات السجل.

---

## 3. المراجع والمدخلات الإلزامية

- `requirements.md`
- `business-rules.md`
- `permission-matrix.md`
- `project-decisions.md`
- `business-rules-global.md`
- `module-registry.md`
- `مراجع الوظائف المشتركة ذات الصلة`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. راجع كل تدفق من نقطة البداية إلى النهاية.
2. طابق كل قرار مع Rule أو Permission أو Decision.
3. اختبر التدفق لأدوار وبيانات وحالات فشل مختلفة.
4. أخرج تقريرًا دون تعديل.
5. أصلح Critical وHigh ثم أعد المراجعة.

---

## 5. قائمة التحقق

### هوية التدفق وغايته

- [ ] لكل Flow معرف ثابت مثل `FLOW-[MODULE]-###`.
- [ ] العنوان يعبر عن هدف مستخدم أو ضرورة تشغيلية حقيقية.
- [ ] الأدوار ونقطة البدء والشروط المسبقة والنهاية محددة.
- [ ] التدفق مرتبط بالمتطلبات والقواعد ذات الصلة.
- [ ] التدفق لا يضم عنصرًا مؤجلًا كأنه ضمن المرحلة الحالية.

### التسلسل ونقاط القرار

- [ ] كل خطوة تحدد جهة التنفيذ: مستخدم أو نظام أو مشغل أو تكامل.
- [ ] الخطوات مرتبة زمنيًا ومنطقيًا بلا قفزات مجهولة.
- [ ] كل Decision يحدد الشرط والمسارات الناتجة.
- [ ] الإجراء لا يفترض بيانات أو صلاحية غير متاحة.
- [ ] النتيجة النهائية واضحة لكل مسار.

### المسارات البديلة والاستثناءات

- [ ] الإدخال غير الصحيح والبيانات الناقصة مغطاة.
- [ ] رفض الصلاحية وانتهاء الجلسة وحالة السجل غير المتاح مغطاة عند الحاجة.
- [ ] فشل التكامل والمهلة وإعادة المحاولة موثقة عند الانطباق.
- [ ] الإلغاء والعودة والاستئناف واسترداد العملية محددة.
- [ ] الدفع والاعتماد والرفض والانتهاء مغطاة عند انطباقها.

### الجاهزية للشاشات والاختبار

- [ ] لا يعيد التدفق تصميم OTP أو الدفع أو الإشعارات أو Audit Log المملوكة لموديولات أخرى.
- [ ] الحالات اللازمة للشاشة ظاهرة: Loading وError وEmpty وSuccess وPermission Denied وPending عند الحاجة.
- [ ] يمكن اشتقاق سيناريو نجاح وفشل لكل مسار رئيسي.
- [ ] لا توجد تدفقات مكررة أو مسار بلا هدف واضح.

---

## 6. أسباب الرفض أو الإيقاف

- تدفق رئيسي بلا بداية أو نهاية.
- نقطة قرار بلا Rule أو Permission أو Decision.
- خطوة ينفذها دور غير مخول.
- تجاهل فشل يؤثر على المال أو الحالة أو الامتثال.
- تكرار وظيفة مشتركة أو غياب Flow لمتطلب معتمد.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | خطأ في النطاق أو المال أو الأمان أو الصلاحيات أو القانون أو حالة السجل | يمنع الاعتماد |
| High | نقص أو تعارض قد يسبب تنفيذًا خاطئًا أو إعادة عمل كبيرة | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

---

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## قابلية التتبع
| Requirement ID | Flow ID | Main / Alternative / Exception | Related Rules | Result |
|---|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- عدد `Critical = 0` و`High = 0`.
- كل متطلب مناسب مغطى بتدفق أو بمبرر موثق.
- المسارات الرئيسية والبديلة والاستثنائية الضرورية مكتملة.
- يمكن تحويل التدفقات إلى حصر شاشات واختبارات دون افتراضات جوهرية.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
