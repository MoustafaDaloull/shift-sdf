# بوابة جودة تحليل المدخلات الهندسية — Engineering Input Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/engineering-input-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن `engineering-input-analysis.md` يوثق بدقة الحالة الفعلية لمخرجات Phase 0 المدخلة للمرحلة الهندسية: صيغ المعرّفات وانحرافاتها، القرارات المفتوحة، الفجوات المحتملة، الاعتماديات المشتركة، والافتراضات المؤقتة — قبل بدء نموذج البيانات أو عقود API أو قصص المستخدم.

---

## 2. متى تُنفذ؟

- بعد إعداد أو تعديل `engineering-input-analysis.md`.
- قبل البدء بـ `data-model.md` أو `api-contracts.md`.
- عند تغيير جوهري في مخرجات Phase 0 للموديول.

---

## 3. المراجع والمدخلات الإلزامية

- `requirements.md`
- `business-rules.md`
- `user-flows.md`
- `screen-inventory.md`
- `screens/`
- `permission-matrix.md`
- `module-registry.md`
- `identifier-alias-map.md`
- `project-decisions.md`
- `business-rules-global.md`
- `glossary.md`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. تحقق من أن التحليل يغطي جميع ملفات Phase 0 للموديول.
2. طابق المعرّفات مع `identifier-alias-map.md`.
3. تحقق من تحديد الانحرافات والفجوات والقرارات المفتوحة.
4. تأكد من أن الاعتماديات المشتركة محددة بمالكيها.
5. لا تعدل في الجولة الأولى — أنشئ التقرير أولًا.
6. أصلح مشكلات `Critical` و`High` وأعد المراجعة.

---

## 5. قائمة التحقق

### اكتمال المسح

- [ ] جميع ملفات Phase 0 للموديول مشمولة في التحليل.
- [ ] هوية الموديول ومرحلته وحدوده مطابقة لسجل الموديولات.
- [ ] نطاق التحليل واضح (ما هو داخل وما هو خارج).

### المعرّفات والصيغ

- [ ] صيغ المعرّفات الفعلية (FR, BR, FLOW, SCR, AC) موثقة.
- [ ] الانحرافات عن الصيغة القياسية محددة ومقارنة بـ `identifier-alias-map.md`.
- [ ] قواعد التحويل من الصيغة الفعلية إلى الصيغة الهندسية واضحة.
- [ ] لا يوجد معرّف غامض أو مكرر أو متعارض.

### القرارات والفجوات

- [ ] القرارات المعتمدة المؤثرة على الهندسة مدرجة.
- [ ] القرارات المفتوحة مصنفة بحسب أثرها (حاجبة أو غير حاجبة).
- [ ] الافتراضات المؤقتة (`PROPOSED`) محددة ومبررة.
- [ ] الفجوات بين مخرجات Phase 0 والاحتياجات الهندسية موثقة.
- [ ] لا يوجد قرار مالي أو قانوني أو أمني مفترض دون اعتماد.

### الاعتماديات والوظائف المشتركة

- [ ] الوظائف المشتركة المستهلكة محددة بمالكيها.
- [ ] الاعتماديات المباشرة على موديولات أخرى واضحة.
- [ ] لا يوجد تكرار لوظيفة مشتركة مملوكة لموديول آخر.
- [ ] نقاط التكامل والاستهلاك محددة.

### الكيانات والحالات الأولية

- [ ] الكيانات المتوقعة والعلاقات الأولية مستخلصة من Phase 0.
- [ ] الحالات وانتقالاتها المذكورة في Phase 0 محصورة.
- [ ] لا يوجد تعارض بين الحالات في الملفات المختلفة.
- [ ] الملاحظات الخاصة بالبيانات الحساسة أو الخصوصية مدرجة.

### الجاهزية للمخرجات الهندسية

- [ ] التحليل كافٍ للبدء بـ `data-model.md`.
- [ ] لا توجد عوائق حرجة تمنع التقدم.
- [ ] توصية واضحة بالبدء أو الإيقاف مع تبرير.

---

## 6. أسباب الرفض أو الإيقاف

- غياب مسح لملف Phase 0 أساسي.
- انحراف في المعرّفات غير موثق أو غير مقارن بـ `identifier-alias-map.md`.
- قرار مفتوح حرج (مالي، صلاحيات، ملكية، حالة) غير مصنف أو غير مصعّد.
- افتراض غير مبرر يؤثر على نموذج البيانات أو API.
- تكرار وظيفة مشتركة مملوكة لموديول آخر.
- تعارض بين ملفات Phase 0 غير مكتشف أو غير موثق.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | فجوة أو تعارض يؤثر في نموذج البيانات أو الصلاحيات أو المال أو الملكية | يمنع الاعتماد |
| High | نقص أو غموض قد ينتج عنه نموذج بيانات أو API خاطئ | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## تغطية المسح
| Phase 0 File | Scanned | Identifiers Checked | Gaps Found | Notes |
|---|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- عدد `Critical = 0` و`High = 0`.
- جميع ملفات Phase 0 مشمولة في المسح.
- المعرّفات والانحرافات موثقة ومقارنة.
- القرارات المفتوحة والفجوات مصنفة ومصعّدة عند الحاجة.
- الاعتماديات والوظائف المشتركة محددة بمالكيها.
- التحليل كافٍ للبدء بالمخرجات الهندسية.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
