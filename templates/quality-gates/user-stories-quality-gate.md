# بوابة جودة قصص المستخدم — User Stories Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/user-stories-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن `user-stories.md` يحول المتطلبات إلى قصص قابلة للتنفيذ والتقدير والاختبار، مع توضيح القيمة ومعايير القبول وتعريف الاكتمال والاعتماديات، دون أن يصبح بديلًا عن وثائق التحليل.

---

## 2. متى تُنفذ؟

- بعد إعداد أو تعديل `user-stories.md`.
- قبل تخطيط Sprint أو تسليم Backlog للتطوير.
- عند تغير المتطلبات أو القواعد أو الشاشات أو الاعتماديات.

---

## 3. المراجع والمدخلات الإلزامية

- `requirements.md`
- `business-rules.md`
- `user-flows.md`
- `screen-inventory.md`
- `screens/`
- `permission-matrix.md`
- `data-model.md`
- `api-contracts.md`
- `project-decisions.md`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. طابق كل Story بمتطلب أو أكثر.
2. تحقق من القيمة والدور والنطاق والاستقلالية.
3. راجع Acceptance Criteria مقابل Rules وFlows وStates.
4. لا تعدل في الجولة الأولى.
5. أصلح Critical وHigh وأعد المراجعة.

---

## 5. قائمة التحقق

### الهوية والبنية

- [ ] كل Story تحمل معرفًا مثل `US-[MODULE]-###`.
- [ ] مرتبطة بـ Epic أو Capability مناسب.
- [ ] الصياغة توضح الدور والهدف والقيمة أو صيغة تشغيلية مبررة.
- [ ] الأولوية والمرحلة والحالة محددة.
- [ ] لا تجمع أكثر من هدف مستقل كبير في Story واحدة دون تفكيك.

### التتبع والنطاق

- [ ] كل Story مرتبطة بمتطلب أو Rule أو Flow.
- [ ] لا تتجاوز حدود الموديول أو المرحلة.
- [ ] الاعتماديات على الموديولات الأخرى واضحة.
- [ ] العناصر المؤجلة أو خارج النطاق لا تدخل في Definition of Done.
- [ ] لا توجد Story بلا قيمة أعمال أو مستخدم أو تشغيل.

### معايير القبول

- [ ] Acceptance Criteria محددة وقابلة للاختبار.
- [ ] تغطي المسار الرئيسي والقيود وحالات الرفض أو الفشل المناسبة.
- [ ] الصلاحيات والحالات والتأكيدات مذكورة عند الحاجة.
- [ ] لا تخترع سياسة أو قاعدة عمل جديدة.
- [ ] لا تستخدم عبارات غير قابلة للقياس مثل يعمل بشكل صحيح أو واجهة سهلة.

### Definition of Done والتنفيذ

- [ ] DoD يشير إلى UX/API/Data/Tests حسب الحاجة.
- [ ] التحقق والرسائل والأمان والتدقيق والـ Analytics مذكورة عند الحاجة.
- [ ] المخاطر والقرارات المفتوحة واضحة.
- [ ] القصة قابلة للتقدير والتنفيذ ضمن دورة منطقية أو مقسمة.
- [ ] ترتيب التنفيذ يحترم الاعتماديات.

---

## 6. أسباب الرفض أو الإيقاف

- Story بلا قيمة أو مصدر أو دور واضح.
- معيار قبول يخالف Rule أو Flow.
- غموض يمنع التقدير أو الاختبار.
- دمج وظائف مستقلة كثيرة دون تفكيك.
- قرار OPEN حرج يمنع التنفيذ.
- عمل خارج المرحلة أو ملكية الموديول.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | خطأ في النطاق أو المال أو الأمان أو الصلاحيات أو القانون أو حالة السجل | يمنع الاعتماد |
| High | نقص أو تعارض قد يسبب تنفيذًا خاطئًا أو إعادة عمل كبيرة | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

---

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## قابلية التتبع
| Story ID | Requirement / Rule | Flow / Screen | Dependency | Test Scenario | Result |
|---|---|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- عدد `Critical = 0` و`High = 0`.
- كل Story لها قيمة ومصدر ومعايير قبول قابلة للاختبار.
- القصص ضمن المرحلة وحدود الموديول.
- الاعتماديات والقرارات الحرجة موثقة.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
