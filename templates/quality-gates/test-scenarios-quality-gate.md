# بوابة جودة سيناريوهات الاختبار — Test Scenarios Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/test-scenarios-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن `test-scenarios.md` يغطي المسارات الرئيسية والبديلة والاستثنائية والحدود والصلاحيات والحالات المالية والتكاملات، بصورة قابلة للتنفيذ والتتبع ومتسقة مع المتطلبات وقواعد العمل والتدفقات والشاشات ونموذج البيانات وعقود API وقصص المستخدم.

---

## 2. متى تُنفذ؟

- بعد إعداد أو تعديل `test-scenarios.md`.
- قبل تسليم الموديول لفريق QA أو بدء كتابة الاختبارات الآلية.
- عند تغيير متطلب أو قاعدة عمل أو تدفق أو شاشة أو API أو نموذج بيانات أو قصة مستخدم.

---

## 3. المراجع والمدخلات الإلزامية

- `requirements.md`
- `business-rules.md`
- `user-flows.md`
- `screen-inventory.md`
- `screens/`
- `permission-matrix.md`
- `data-model.md`
- `api-contracts.md`
- `user-stories.md`
- `project-decisions.md`
- `business-rules-global.md`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. طابق كل سيناريو بمتطلب أو قاعدة عمل أو تدفق أو قصة مستخدم.
2. تحقق من تغطية المسار الرئيسي والبدائل والاستثناءات والحدود.
3. تأكد من أن السيناريوهات الحساسة (مال، صلاحيات، حالات، ملكية) لها أولوية واضحة.
4. لا تعدل في الجولة الأولى — أنشئ التقرير أولًا.
5. أصلح مشكلات `Critical` و`High` وأعد المراجعة.

---

## 5. قائمة التحقق

### الهوية والبنية

- [ ] كل سيناريو يحمل معرفًا مثل `TS-[MODULE]-###`.
- [ ] مرتبط بمتطلب أو قاعدة عمل أو تدفق أو قصة مستخدم.
- [ ] الأولوية والمرحلة والنوع (وظيفي، أمان، صلاحيات، أداء، تكامل) محددة.
- [ ] لا يوجد سيناريو بلا غرض أو مصدر.

### التغطية الوظيفية

- [ ] المسارات الرئيسية لكل تدفق مغطاة.
- [ ] المسارات البديلة والاستثنائية مغطاة.
- [ ] حالات الحدود (القيم الدنيا والقصوى والفارغة وغير الصالحة) مغطاة.
- [ ] الحالات الانتقالية مغطاة (إنشاء، تعديل، اعتماد، رفض، إلغاء، أرشفة).
- [ ] قواعد التحقق ورسائل الخطأ المتوقعة محددة.

### الصلاحيات والأمان

- [ ] كل دور مستهدف له سيناريوهات إيجابية وسلبية.
- [ ] محاولة الوصول بدون صلاحية مغطاة.
- [ ] نطاق البيانات المرئية لكل دور مختبر.
- [ ] العمليات الحساسة (مالية، حذف، نقل ملكية) لها سيناريوهات أمان مستقلة.

### البيانات والتكامل

- [ ] سيناريوهات البيانات المرجعية والقوائم الفارغة والبيانات الكبيرة مغطاة.
- [ ] التكامل مع الموديولات المشتركة (مدفوعات، إشعارات، وسائط، تدقيق) مغطى.
- [ ] سيناريوهات الفشل الجزئي وإعادة المحاولة والتزامن محددة عند الحاجة.
- [ ] اتساق البيانات بين الشاشات وAPI ونموذج البيانات مختبر.

### الجودة والقابلية للتنفيذ

- [ ] كل سيناريو يحدد: الشرط المسبق، الخطوات، البيانات المدخلة، النتيجة المتوقعة.
- [ ] النتائج المتوقعة قابلة للقياس والتحقق.
- [ ] لا يوجد تداخل أو تكرار غير مبرر بين السيناريوهات.
- [ ] لا يختبر السيناريو وظيفة مملوكة لموديول آخر إلا كنقطة تكامل.

---

## 6. أسباب الرفض أو الإيقاف

- سيناريو بلا مصدر أو غرض أو نتيجة متوقعة.
- غياب تغطية لمسار رئيسي أو قاعدة عمل حساسة.
- غياب سيناريوهات صلاحيات لعملية حساسة.
- سيناريو يخالف قاعدة عمل أو تدفق معتمد.
- غياب سيناريوهات حدود لعملية مالية أو انتقال حالة.
- تكرار اختبار وظيفة مشتركة مملوكة لموديول آخر كاختبار وحدة.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | غياب تغطية لعملية مالية أو صلاحية حساسة أو انتقال حالة حرج | يمنع الاعتماد |
| High | نقص أو تعارض قد يسبب تنفيذًا خاطئًا أو فشل اختبار جوهري | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## تغطية السيناريوهات
| Requirement / Rule / Flow | Scenario ID(s) | Coverage | Notes |
|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- عدد `Critical = 0` و`High = 0`.
- المسارات الرئيسية والبديلة والاستثنائية مغطاة.
- العمليات الحساسة (مالية، صلاحيات، حالات، ملكية) لها سيناريوهات كافية.
- السيناريوهات متسقة مع المتطلبات والقواعد والتدفقات والشاشات وAPI.
- كل سيناريو قابل للتنفيذ والتحقق.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
