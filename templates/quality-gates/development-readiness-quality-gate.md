# بوابة جاهزية التطوير — Development Readiness Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/development-readiness-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن الموديول مستوفٍ لجميع شروط الانتقال من التوثيق الهندسي إلى التطوير الفعلي (Backend، Frontend، QA). تجمع نتائج بوابات الجودة الفردية (نموذج البيانات، عقود API، قصص المستخدم، سيناريوهات الاختبار) وتتحقق من الاتساق الشامل وحل الاعتماديات والقرارات المفتوحة.

---

## 2. متى تُنفذ؟

- بعد اكتمال جميع المخرجات الهندسية للموديول.
- قبل بدء Sprint التطوير الأول.
- قبل تسليم الموديول لفريق Backend أو Frontend أو QA.
- عند تغيير جوهري في النطاق أو القرارات أو الاعتماديات بعد الاعتماد الأولي.

---

## 4. بروتوكول المراجعة الإلزامي

1. تحقق من اجتياز كل مخرج لبوابة الجودة الخاصة به.
2. أنشئ مصفوفة تتبع من Requirement إلى Rule وFlow وScreen وData وAPI وStory وTest.
3. افحص التناقضات بين الملفات الهندسية ومخرجات Phase 0.
4. تحقق من حل جميع القرارات المفتوحة الحرجة.
5. افحص الاعتماديات المشتركة وجاهزية الموديولات المالكة.
6. قيّم الجاهزية لكل مسار: Backend، Frontend، QA، Integration.
7. لا تعدل في الجولة الأولى — أنشئ التقرير أولًا.
8. أصلح مشكلات `Critical` و`High` وأعد المراجعة الكاملة.

---

## 5. قائمة التحقق

### 5.1 اكتمال المخرجات وبوابات الجودة

- [ ] `engineering-input-analysis.md` اجتاز `engineering-input-quality-gate.md`.
- [ ] `data-model.md` اجتاز `data-model-quality-gate.md`.
- [ ] `api-contracts.md` اجتاز `api-contract-quality-gate.md`.
- [ ] `user-stories.md` اجتاز `user-stories-quality-gate.md`.
- [ ] `test-scenarios.md` اجتاز `test-scenarios-quality-gate.md`.
- [ ] لا يوجد مخرج هندسي بحالة `NEEDS_REVISION` أو `BLOCKED`.

### 5.2 الاتساق وقابلية التتبع

- [ ] لكل متطلب وظيفي تغطية مناسبة في: Data Entity، API، Story، Test.
- [ ] كل قاعدة عمل مؤثرة تنعكس في Data Model أو API أو Test.
- [ ] كل شاشة لها API Endpoints كافية لدعمها.
- [ ] كل API Endpoint له قصة مستخدم ومصدر وظيفي.
- [ ] كل عملية حساسة (مالية، صلاحيات، حالات) لها سيناريو اختبار.
- [ ] المعرّفات والمصطلحات والحالات موحدة عبر جميع الملفات.
- [ ] لا توجد عملية ظاهرة في ملف واحد فقط دون انعكاس في الملفات الأخرى.

### 5.3 النطاق والملكية

- [ ] هوية الموديول وحدوده ومرحلته مطابقة لسجل الموديولات.
- [ ] لا توجد وظائف مكررة من موديولات مالكة أخرى.
- [ ] الوظائف المشتركة المستهلكة تشير لمالكيها بوضوح.
- [ ] لا يوجد كيان أو API أو قصة تتجاوز حدود الموديول.

### 5.4 القرارات والمخاطر

- [ ] جميع القرارات `OPEN` المصنفة كحاجبة تم حسمها أو استبعادها صراحة.
- [ ] لا توجد افتراضات `PROPOSED` تمس المال أو الصلاحيات أو الخصوصية أو الامتثال.
- [ ] المخاطر والتبعيات الحرجة لها مالك وخطة معالجة.
- [ ] المخاطر المقبولة موثقة بموافقة صريحة من مالك المنتج.

### 5.5 الاعتماديات والتكامل

- [ ] الاعتماديات المباشرة على موديولات أخرى محددة وقابلة للتنفيذ.
- [ ] الموديولات المالكة للوظائف المشتركة المطلوبة جاهزة أو لها خطة بديلة.
- [ ] نقاط التكامل مع الموديولات الأخرى واضحة ومتفق عليها.
- [ ] لا يوجد اعتماد خارجي بلا مسؤولية أو Contract أو خطة فشل.

### 5.6 الجاهزية التقنية

- [ ] Authentication وAuthorization واضحان أو محالان لموديول المالك.
- [ ] Audit Log والإشعارات والمدفوعات والوسائط تشير لمالكيها.
- [ ] حالات الفشل والاسترجاع وإعادة المحاولة واضحة للعمليات الحساسة.
- [ ] الأداء والقوائم الكبيرة والوسائط والخصوصية والاحتفاظ بالبيانات مغطاة عند الحاجة.


---

## 7. أسباب الرفض أو الإيقاف

- مخرج هندسي لم يجتز بوابة الجودة الخاصة به.
- تناقض غير محلول بين المخرجات الهندسية ومخرجات Phase 0.
- قرار مفتوح حرج (مالي، صلاحيات، ملكية، حالة) غير محسوم.
- اعتماد على موديول آخر غير جاهز بلا خطة بديلة.
- غياب تغطية اختبار لعملية حساسة.
- كيان أو API بلا مالك أو مصدر وظيفي.

---

## 8. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Blocker | يمنع انتقال الموديول للتطوير | لا اعتماد |
| Critical | خلل في المال أو الصلاحيات أو الحالة أو النطاق أو الامتثال | لا اعتماد |
| High | نقص أو تناقض قد يؤدي لتنفيذ خاطئ أو إعادة عمل كبيرة | لا اعتماد |
| Medium | فجوة مهمة تحتاج خطة أو موافقة | اعتماد مشروط فقط |
| Low | تحسين محدود لا يمنع العمل | يمكن تأجيله |

## 10. معايير الاعتماد النهائي

- لا يوجد `Blocker` أو `Critical` أو `High` مفتوح.
- جميع المخرجات الهندسية اجتازت بوابات الجودة الخاصة بها.
- مصفوفة التتبع لا تحتوي فجوات غير مبررة.
- الاعتماديات المشتركة قابلة للتنفيذ.
- القرارات المفتوحة الحرجة حُسمت أو استبعدت صراحة.
- خطة الاختبار تغطي المسارات الرئيسية والعمليات الحساسة.
- تمت إعادة المراجعة بعد آخر إصلاح جوهري.

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
