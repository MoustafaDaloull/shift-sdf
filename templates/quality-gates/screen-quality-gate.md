# بوابة جودة مواصفات الشاشات — Screen Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/screen-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تحدد هذه البوابة معايير الجودة الإلزامية لكل ملف `screens/SCR-XXX.md` قبل اعتباره جاهزًا للتصميم أو التطوير أو الاختبار. لا تكفي قائمة العناصر؛ يجب أن تكون المواصفة متسقة مع المتطلبات والقواعد والتدفقات والصلاحيات والبيانات وAPI والحالات التشغيلية.

---

## 2. متى تُنفذ؟

- بعد إنشاء كل Screen Specification مباشرة.
- بعد تعديل سلوك الشاشة أو حقولها أو إجراءاتها أو صلاحياتها.
- قبل التسليم إلى UX/UI أو Frontend أو QA.
- ضمن مراجعة جاهزية الموديول.

---

## 3. المراجع والمدخلات الإلزامية

- `requirements.md`
- `business-rules.md`
- `user-flows.md`
- `screen-inventory.md`
- `permission-matrix.md`
- `data-model.md`
- `api-contracts.md`
- `user-stories.md`
- `test-scenarios.md`
- `المراجع العالمية وسجل القرارات`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. اقرأ ملف الشاشة والمراجع ذات الصلة.
2. افترض وجود نواقص أو أخطاء ولا تعتمد النص القائم تلقائيًا.
3. أصدر Review Report دون تعديل في الجولة الأولى.
4. أصلح كل Critical وHigh.
5. أعد المراجعة كاملة من الصفر قبل الانتقال للشاشة التالية.

---

## 5. قائمة التحقق

### الهوية والنطاق

- [ ] معرف الشاشة يتبع `SCR-[MODULE-CODE]-###`.
- [ ] الاسم والغرض والدور ونقاط الدخول والخروج محددة.
- [ ] الشاشة مرتبطة بتدفقات ومتطلبات وقواعد ذات صلة.
- [ ] الأولوية والمرحلة متوافقتان مع `screen-inventory.md`.
- [ ] لا تكرر شاشة لوظيفة مملوكة لموديول آخر.

### التخطيط والمكونات

- [ ] الأقسام والمكونات والحقول والجداول والأزرار لها أسماء وسلوك واضح.
- [ ] الحقول الإلزامية والاختيارية وRead-only والمخفية محددة.
- [ ] القيم الافتراضية والـ Placeholder والظهور الشرطي موثقة عند الحاجة.
- [ ] تستخدم المكونات المشتركة بدل تكرارها.
- [ ] لا تفرض تفاصيل تصميم بصري خارج ما يلزم للمواصفة.

### السلوك وقواعد التحقق

- [ ] كل Action يحدد من يراه ومتى يتاح وماذا يفعل ونتيجته.
- [ ] الإجراءات التدميرية أو المالية أو غير العكوسة لها Confirmation Dialog.
- [ ] Navigation والحفظ والإلغاء والعودة والاستئناف واضحة.
- [ ] كل Business Rule مؤثرة مذكورة بمعرفها.
- [ ] Required وFormat وLength وRange وDuplicate وCross-field وBusiness Validation مغطاة عند الحاجة.
- [ ] توقيت ورسائل التحقق محددان ولا تكشف الرسائل بيانات حساسة.

### الصلاحيات وحالات الشاشة

- [ ] صلاحيات View/Create/Edit/Delete/Approve/Reject/Export/Print محددة حسب الانطباق.
- [ ] حالات Permission Denied وRead-only وRestricted محددة.
- [ ] Initial وLoading وEmpty وError وSuccess وDisabled موثقة.
- [ ] Pending Approval وOffline/Retry وNot Found/Archived/Expired مذكورة عند الحاجة.
- [ ] التدقيق والبيانات الحساسة والملكية مقيدة حسب المرجع.

### البيانات وAPI وUX

- [ ] مصدر كل قسم أو حقل واضح ومتسق مع Data Model.
- [ ] APIs والاستجابات وحالات الخطأ المطلوبة محددة.
- [ ] Pagination وSearch وFilter وSort وLazy Loading موثقة عند الحاجة.
- [ ] لا توجد تعارضات مع حالات السجل أو API أو الحقول المسموح بها.
- [ ] الهدف يمكن إنجازه دون تعقيد، ولا توجد Dead Ends.
- [ ] تُراعى تسميات الحقول والوصول وقارئ الشاشة وعناصر اللمس والأداء عند الحاجة.

---

## 6. أسباب الرفض أو الإيقاف

- وجود إجراء حساس بلا Permission أو Confirmation أو نتيجة واضحة.
- غياب Loading أو Error أو Empty أو Permission Denied أساسية.
- تعارض في الحقول أو API أو حالات السجل مع المراجع.
- منطق مالي أو قانوني أو تشغيلي غير موثق.
- تكرار وظيفة أو شاشة مشتركة مملوكة لموديول آخر.
- مواصفة لا يمكن تحويلها إلى تصميم أو تنفيذ أو اختبار.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | خطأ في النطاق أو المال أو الأمان أو الصلاحيات أو القانون أو حالة السجل | يمنع الاعتماد |
| High | نقص أو تعارض قد يسبب تنفيذًا خاطئًا أو إعادة عمل كبيرة | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

---

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## قابلية التتبع
| Screen ID | Requirement / Rule / Flow | Data Entity | API Contract | Test Scenario | Result |
|---|---|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- تم تنفيذ AI Self-Review وتوثيقه.
- عدد `Critical = 0` و`High = 0`.
- لا توجد قرارات OPEN تمنع بناء سلوك الشاشة.
- الحالات والإجراءات والصلاحيات والبيانات وAPI قابلة للبناء والاختبار.
- تمت إعادة المراجعة بعد آخر إصلاح.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
