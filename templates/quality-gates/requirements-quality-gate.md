# بوابة جودة المتطلبات — Requirements Quality Gate

**الإصدار:** 1.0  
**المسار القياسي:** `docs/99-quality/requirements-quality-gate.md`  
**الحالة:** مرجع إلزامي  
**النطاق:** جميع موديولات {{PROJECT_NAME}} ما لم يعتمد مالك المنتج استثناءً صريحًا.

---

## 1. الغرض

تضمن هذه البوابة أن `requirements.md` يحدد نطاق الموديول وقدراته وحدوده واعتمادياته بصورة قابلة للتتبع والبناء والاختبار، دون خلط المتطلبات مع التدفقات أو تفاصيل الشاشات أو واجهات API أو نموذج البيانات.

---

## 2. متى تُنفذ؟

- بعد إعداد المسودة الأولى من `requirements.md`.
- بعد أي تعديل على النطاق أو الأدوار أو الاعتماديات أو المرحلة.
- قبل اعتماد قواعد العمل أو تدفقات المستخدم أو حصر الشاشات.

---

## 3. المراجع والمدخلات الإلزامية

- `module-registry.md`
- `brd.md`
- `project-decisions.md`
- `glossary.md`
- `business-rules-global.md`
- `الأسئلة والإجابات والوثائق التشغيلية المعتمدة`

لا تُنشئ افتراضًا بدل مرجع مفقود. سجّل المرجع المفقود أو القرار الناقص كـ `OPEN`، واعتبره عائقًا إذا كان يؤثر في المال أو الصلاحيات أو الملكية أو الحالة أو الخصوصية أو الالتزام القانوني.

---

## 4. بروتوكول المراجعة الإلزامي

1. اقرأ الملف كاملًا قبل التعليق.
2. طابق هوية الموديول وملكيته مع سجل الموديولات.
3. تحقق من مصدر وقابلية اختبار كل متطلب.
4. أصدر تقريرًا أولًا دون تعديل الملف.
5. أصلح Critical وHigh ثم أعد المراجعة من الصفر.

---

## 5. قائمة التحقق

### هوية الموديول والنطاق

- [ ] Module ID وModule Code والاسم الرسمي والمرحلة والمجلد الرسمي مطابقة لسجل الموديولات.
- [ ] نطاق الموديول يوضح ما يملكه وما لا يملكه بوضوح.
- [ ] الوظائف المشتركة المستهلكة تشير إلى الموديول المالك بدل تكرار منطقها.
- [ ] العناصر المؤجلة وخارج النطاق محددة صراحة.
- [ ] لا توجد عبارات عامة أو غير قابلة للقياس دون معيار.

### الأدوار والمتطلبات الوظيفية

- [ ] الأدوار المتأثرة معرفة بأسمائها الرسمية.
- [ ] كل متطلب يحمل معرفًا ثابتًا مثل `FR-[MODULE]-###`.
- [ ] كل متطلب يصف قدرة أو نتيجة مطلوبة لا حلًا تقنيًا غير لازم.
- [ ] المتطلبات الذرية قابلة للتقدير والاختبار ولا تدمج أهدافًا مستقلة.
- [ ] الشروط المسبقة والنتيجة والسلوك الاستثنائي موثقة أو محالة لقاعدة عمل.

### الجودة والتتبع

- [ ] لكل متطلب مصدر واضح: BRD أو قرار أو إجابة معتمدة أو قاعدة عالمية.
- [ ] لا توجد متطلبات مكررة أو متعارضة أو خارج المرحلة.
- [ ] المتطلبات غير الوظيفية الخاصة بالموديول قابلة للقياس عند الإمكان.
- [ ] القرارات المفتوحة مرتبطة بالمتطلبات المتأثرة.
- [ ] الملف لا يحوي تفاصيل حقول أو تصميم شاشة أو API خارج نطاقه.

### الجاهزية للمخرجات التالية

- [ ] يمكن اشتقاق قواعد عمل وتدفقات واختبارات من المتطلبات دون افتراضات تجارية جديدة.
- [ ] التبعيات الداخلية والخارجية محددة مع سبب الاعتماد.
- [ ] المتطلبات الحساسة للمال أو الصلاحية أو الخصوصية أو الملكية محددة بوضوح.

---

## 6. أسباب الرفض أو الإيقاف

- حدود ملكية الموديول غير واضحة أو مخالفة للسجل.
- قرار مالي أو قانوني أو متعلق بالصلاحيات حرج وغير محسوم.
- متطلب متعارض مع BRD أو قرار معتمد.
- متطلب غير قابل للتتبع أو الاختبار.
- خلط جوهري بين المتطلبات والتصميم أو API أو قواعد العمل.

---

## 7. تصنيف الملاحظات

| المستوى | المعنى | أثره على الاعتماد |
|---|---|---|
| Critical | خطأ في النطاق أو المال أو الأمان أو الصلاحيات أو القانون أو حالة السجل | يمنع الاعتماد |
| High | نقص أو تعارض قد يسبب تنفيذًا خاطئًا أو إعادة عمل كبيرة | يمنع الاعتماد |
| Medium | فجوة مهمة تحتاج إصلاحًا أو موافقة صريحة | لا يعتمد تلقائيًا |
| Low | تحسين محدود في الوضوح أو الصياغة أو التنظيم | يمكن تأجيله |

---

## 8. قالب تقرير المراجعة

```markdown
# Quality Review — [MODULE CODE]

**الملف المراجع:** [المسار]  
**المراجع المستخدمة:** [قائمة]  
**حالة المراجعة:** PASS / CONDITIONAL PASS / FAIL

## ملخص الملاحظات
| Severity | Count |
|---|---:|
| Critical | 0 |
| High | 0 |
| Medium | 0 |
| Low | 0 |

## قابلية التتبع
| Requirement ID | Source / Decision | Module Owner | Next Deliverables | Result |
|---|---|---|---|---|

## Findings

### QG-[MODULE]-001
- **Severity:** Critical / High / Medium / Low
- **العنصر المتأثر:** [المعرف أو القسم]
- **الوصف:** [المشكلة بدقة]
- **الأثر:** [الأثر التشغيلي أو الفني أو القانوني]
- **التوصية:** [الإجراء المطلوب]
- **المرجع:** [Requirement / Rule / Flow / Decision / File]
- **الحالة:** Open / Resolved / Accepted Risk
```

---

## 9. معايير الاعتماد النهائي

- عدد `Critical = 0` و`High = 0`.
- كل المتطلبات قابلة للتتبع والاختبار.
- لا توجد قرارات OPEN حرجة للمرحلة الحالية.
- لا يوجد تعارض مع ملكية الوظائف المشتركة أو حدود المرحلة.

لا تعتبر الوثيقة مكتملة أو جاهزة للمخرج التالي إلا بعد إعادة المراجعة عقب الإصلاح.

استخدم النتيجة النهائية فقط عند تحقق الشروط:

```text
STATUS = APPROVED
```

وفي غير ذلك استخدم الحالة المناسبة:

```text
STATUS = BLOCKED
STATUS = NEEDS_REVISION
STATUS = CONDITIONAL_REVIEW
```
