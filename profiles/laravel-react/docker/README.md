# بيئة Docker — حزمة الخدمات التسع

**النطاق:** بيئة تطوير واختبار وتكامل وإنتاج بالحاويات
**الخدمات:** `nginx` · `php` · `queue` · `scheduler` · `node` · `mysql` · `redis` · `redis-cache` · `mailpit`

---

## 1. التشغيل السريع

```bash
make init      # ينشئ .env من القالب — عدّل كلمات المرور الثلاث قبل المتابعة
make up        # يبني ويشغّل بيئة التطوير وينتظر حتى تصبح كل خدمة healthy
make db-init   # ⬅ مرة واحدة على كل جهاز: يهجّر القاعدة ثم يبذرها
make hooks     # ⬅ مرة واحدة على كل نسخة: يثبّت خطّافَي Git
make ps        # حالة الخدمات
make down      # إيقاف (البيانات محفوظة)
```

> **`make db-init` ليست خطوة تحسينية.** `make up` يترك القاعدة بلا مخطط، وأي بوابة تقرأ من القاعدة وقت التوليد — بوابة عقد OpenAPI تحديدًا، لأن المولّد يستدعي `rules()` وقد يقرأ `FormRequest` حدوده من جدول إعدادات — **تسقط على كودٍ سليم لم يُمسّ**. هذا صنف «الدافئ مقابل البارد»: لا يظهر على جهازٍ بُذرت قاعدته منذ شهور، ولا مفرّ منه على جهاز جديد. في المشروع المرجعي كانت هذه الخطوة موثَّقة في موضع واحد — ملف CI — فكان CI أخضر والمسار المحلي الموثَّق أحمر.

**بدون `make` — وهذا هو المسار الذي يجب أن يعمل** (`make` غير مُثبَّت على كل جهاز تطوير، ولا على ويندوز افتراضيًا):

```bash
# 1. القالب ⟵ الإعداد.
cp .env.example .env

# 2. عدّل في `.env` كلمات المرور الثلاث (MYSQL_ROOT_PASSWORD · MYSQL_PASSWORD ·
#    REDIS_PASSWORD). الحزمة لا تُقلع بقيم فارغة — بعضها معلَّم بـ`:?` عمدًا.

# 3. على Linux/WSL2 فقط: طابِق هوية المستخدم حتى تبقى الملفات المربوطة قابلة
#    للتحرير بلا sudo. على Docker Desktop لويندوز اترك الافتراضي.
#        sed -i "s/^APP_UID=.*/APP_UID=$(id -u)/" .env
#        sed -i "s/^APP_GID=.*/APP_GID=$(id -g)/" .env

# 4. الإقلاع
docker compose --project-directory . \
  -f docker/compose/compose.yaml \
  -f docker/compose/compose.dev.yaml up -d --wait

# 5. تهيئة القاعدة — مرة واحدة على كل جهاز. **ليست اختيارية** (التنبيه أعلاه).
docker compose --project-directory . \
  -f docker/compose/compose.yaml \
  -f docker/compose/compose.dev.yaml \
  exec -T php sh -lc "cd /var/www/html && php artisan migrate --force && php artisan db:seed --force"

# 6. تثبيت خطّافَي Git — مرة واحدة على كل نسخة. الخطّافان لا يُستنسخان مع
#    المستودع. خطّافٌ في scripts/hooks/ لا يُنسخ = بوابة غير موجودة.
cp scripts/hooks/pre-commit  .git/hooks/pre-commit
cp scripts/hooks/post-commit .git/hooks/post-commit
chmod +x .git/hooks/pre-commit .git/hooks/post-commit
```

> **لماذا الخطوة 3 ليست تفصيلًا:** مُشغِّل GitHub مستخدمه `1001` والقالب يثبّت `1000`، فكانت الحاوية لا تملك النسخة المربوطة وتسقط الكتابة في `storage/logs` — وهو ما أفشل تشغيل CI في المشروع المرجعي. لا يظهر على ويندوز لأن Docker Desktop يعرض كل ربط بـ`0777`. ملف `ci.yml` في هذا الملف الشخصي يضبطها آليًّا.

> `--project-directory .` **إلزامي**. بدونه يعتبر Compose أن `docker/compose/`
> هي جذر المشروع، فتُحلّ مسارات البناء من مكان خاطئ ويُقرأ `.env` من ملف آخر.
> ملف `Makefile` يضبط ذلك تلقائيًا.

## 2. السلوك قبل وجود التطبيق

كل نقطة دخول تتحمّل غياب التطبيق **بلا حلقة إعادة تشغيل**:

| الخدمة | السلوك عند غياب الكود |
|---|---|
| `nginx` | يخدم صفحة مؤقتة من `docker/nginx/html/placeholder.html` |
| `php` | يُقلع FPM بلا تطبيق ويبلّغ healthy |
| `queue` / `scheduler` | **يخملان مع رسالة إرشادية** حتى يظهر `artisan` |
| `node` | يخمل حتى يظهر `package.json`، ويبلّغ healthy في الخمول |

**لماذا الخمول بدل الخروج؟** حاوية تخرج ستُعاد تشغيلها إلى ما لا نهاية بسبب سياسة
`restart`، فتغرق السجلات وتظهر البيئة كأنها معطلة. الخمول يبقي الخدمة متاحة ويعطي
رسالة تشرح الخطوة التالية.

بعد إنشاء التطبيقات:

```bash
docker compose restart queue scheduler node
```

## 3. البنية

```
docker/
├── compose/
│   ├── compose.yaml        # الأساس — الطوبولوجيا المشتركة
│   ├── compose.dev.yaml    # تطوير  — bind mounts، منافذ، Xdebug، Mailpit
│   ├── compose.test.yaml   # اختبار — معزول، tmpfs، بلا منافذ، قاعدة مستقلة
│   ├── compose.ci.yaml     # CI     — ذاكرة طبقات BuildKit فقط، لا خدمة
│   └── compose.prod.yaml   # إنتاج  — صور ثابتة، تحصين، بلا قواعد بيانات
├── php/                    # Dockerfile متعدد المراحل + php.ini + FPM pool
├── nginx/                  # Dockerfile + nginx.conf + vhosts + snippets
├── mysql/                  # Dockerfile + server.cnf + سكربتات التهيئة
├── redis/                  # redis-persistent.conf + redis-cache.conf
├── node/                   # Dockerfile + entrypoint + healthcheck (+ Chromium للبوابات)
└── mailpit/                # README (يُضبط بمتغيرات البيئة فقط)
```

الملف الأساسي يُدمج دائمًا مع **طبقة بيئة واحدة**، ولا يُستخدم وحده أبدًا.

## 4. القرارات التصميمية الرئيسية

### 4.1 شبكتان لا شبكة واحدة

`frontend` (الحافة) و`backend` (طبقة البيانات، `internal: true`).

MySQL ونسختا Redis على `backend` فقط، فلا مسار لها من المضيف إطلاقاً. حتى لو نُشر
منفذ بالخطأ، فمن يخترق Nginx لا يصل لقاعدة البيانات دون اختراق PHP أولاً.

**مُتحقَّق منه:** حاوية `node` (على `frontend` فقط) لا تصل إلى `mysql` ولا `redis`،
بينما `php` تصل إليها جميعاً.

### 4.2 عامل الطابور والمجدول حاويات منفصلة

ليست عمليات خلفية داخل حاوية PHP، لأن:

- **التوسع مستقل** — ذروة العمل الخلفي تحتاج عمّالاً أكثر لا سعة ويب أكثر.
- **الفشل معزول** — مهمة سامّة تعيد تشغيل حاويتها فقط.
- **الإشارات صحيحة** — `docker stop` يرسل SIGTERM فينهي Laravel المهمة الجارية
  قبل الخروج (`stop_grace_period: 120s` في الإنتاج لمكالمات المزوّدين الخارجيين).

**المجدول** — نسختان تعنيان تنفيذ كل مهمة مجدولة مرتين: رسم مكرر، إشعار مكرر،
موعد يُغلق مرتين. على منصة تتوسّع تلقائيًّا لا تضمن نسخة واحدة، يُعتمد **مجدول
خارجي** يستدعي نقطة HTTP بدل الحاوية الدائمة — الحاوية تبقى خلف profile للاستضافة
حيث يُفرض عدد النسخ فعلياً.

### 4.3 لا MySQL ولا Redis في الإنتاج

أُزيلتا عمداً من `compose.prod.yaml` لصالح **خدمات مُدارة**. تشغيل قاعدة بيانات في
حاوية يعني تملّك النسخ الاحتياطي والتعافي والترقيع بنفسك — لمنصة قد تعالج أموالًا.

إزالتهما هي ما يجعل النشر بقاعدة بيانات مؤقتة **مستحيلاً** لا مجرد غير مستحسن.

### 4.4 فحوص الصحة تفحص خدمة واحدة فقط

- `nginx` → `/healthz` يُجاب من Nginx نفسه، **لا يمر على PHP إطلاقاً**.
- `php` → FastCGI مباشرة عبر `cgi-fcgi` إلى `/ping`، **لا يمر على Nginx**.
- `queue` / `scheduler` → وجود العملية (`pgrep`) لأنهما لا يخدمان منفذًا — أضعف من
  طلب مُجاب لكنه أقوى حاسمًا من لا شيء، و`disable: true` كان يُسقط `up --wait`.

لو مرّ فحص Nginx على PHP، لأدى خطأ في Laravel إلى إعادة تشغيل Nginx السليم بينما
يبقى العطل الحقيقي دون معالجة.

الفحوص الأعمق (قاعدة البيانات، Redis) تخص مسار تطبيقي منفصل مثل `/up`، وهي فحص
**جاهزية** لا فحص **حياة**.

### 4.5 نسختا Redis لا نسخة واحدة

| النسخة | تحمل | السياسة | الاستمرارية |
|---|---|---|---|
| `redis` | مهام الطابور + الجلسات | `noeviction` | مفعّلة |
| `redis-cache` | Cache + تحديد المعدل | `allkeys-lru` | معطّلة |

النسخة الواحدة تجعل نمو الـ Cache ينافس مهام الطابور على الذاكرة نفسها، وأي سياسة
موحّدة تنتج أحد ضررين: **حذف صامت** لمهمة دفع، أو **توقف قبول مهام جديدة** بسبب
بيانات قابلة للاستبدال أصلاً.

الفصل هو ما يجعل `allkeys-lru` آمنة للـ Cache: أسوأ نتيجة هي إعادة حساب، لا فقدان
مهمة مالية.

#### إعداد Laravel المطلوب لفصل Redis

في `config/database.php` ضمن `redis`:

```php
'cache' => [
    'host'     => env('REDIS_CACHE_HOST', env('REDIS_HOST', '127.0.0.1')),
    'port'     => env('REDIS_CACHE_PORT', 6379),
    'password' => env('REDIS_CACHE_PASSWORD', env('REDIS_PASSWORD')),
    'database' => 0,
],
```

الاتصال الافتراضي يبقى على `REDIS_HOST` (الطابور والجلسات). توجيه الاثنين إلى
النسخة نفسها يُلغي الغرض من الفصل ويعيد خطر حذف مهمة دفع بصمت.

### 4.6 مجلدات التبعيات كـ named volumes

`vendor/` و`node_modules/` مركّبة كـ named volumes فوق الـ bind mount:

1. **السرعة** — آلاف الملفات الصغيرة عبر جسر ملفات Windows بطيئة جداً.
2. **الصحة** — الوحدات المُصرَّفة تُبنى على libc الحاوية، ومشاركتها مع Windows
   تنتج ثنائيات لا تعمل في أي منهما.

### 4.7 حزمة الاختبار معزولة بقاعدة مستقلة

**الاختبارات تكتب.** `php artisan test` يشغّل `migrate:fresh`؛ تشغيله في حاوية
التطوير يمحو قاعدة المطوّر. لذلك:

- `compose.test.yaml` يحمل `COMPOSE_PROJECT_NAME` مختلفًا فتختلف كل الأسماء.
- القاعدة `${MYSQL_TEST_DATABASE}` يُنشئها `initdb/01-init-databases.sh` على القاعدة
  نفسها، وتشير إليها حزمة الاختبار وحدها.
- خدمة `test-deps` تثبّت الاعتماديات **بمنفذ شبكة**، وخدمة `test` تنفّذ **بلا منفذ**
  على شبكة `internal: true` — فلا اختبار يصل إلى sandbox دفع حقيقي بالخطأ.

## 5. أخطاء اكتُشفت بالتشغيل الفعلي

هذه ليست نظرية — كل واحدة ظهرت عند تشغيل البيئة فعلياً وأُصلحت:

| # | العطل | السبب الجذري | الإصلاح |
|---|---|---|---|
| 1 | فشل بناء صورة PHP عند Xdebug | `disable_functions` في الطبقة الأساسية يمنع `exec`، وPECL يحتاجها للتصريف. الخطأ يشير إلى `OS/Guess.php` ولا يذكر السبب | نُقل التقييد إلى `20-production.ini` فقط |
| 2 | Redis يسقط عند الإقلاع | `rename-command CONFIG ""` يكسر وحدات Redis 8 المدمجة (RediSearch تستدعي `CONFIG GET` وتفشل في assertion) | أُبقي `KEYS` فقط، ووُثّقت ACLs كالآلية الصحيحة |
| 3 | **كل إعدادات MySQL مُتجاهَلة بصمت** | ملف مركّب من قرص Windows يظهر بصلاحية 0777، وMySQL يتجاهل ملفات الإعداد القابلة للكتابة للجميع مع تحذير واحد فقط | صورة MySQL مخصصة مع `COPY --chmod=0444` |
| 4 | MySQL يرفض الإقلاع بعد الإصلاح 3 | `log_error = /dev/stderr` — يضيف MySQL لاحقة `.err` فيحاول فتح `/dev/stderr.err` | حُذف السطر (الصورة الرسمية تسجّل للكونسول أصلاً) |
| 5 | Nginx يرفض الإقلاع | تركيب مجلد `conf.d` كاملاً حمّل vhosts التطوير والإنتاج معاً → `duplicate upstream` | تركيب ملف vhost واحد كـ `default.conf` |
| 6 | ترويسات الأمان مفقودة على `/healthz` | قاعدة وراثة `add_header` في Nginx: أي كتلة لها `add_header` خاص تُسقط كل ترويسات الأب | استُخدم `default_type` بدل `add_header` |
| 7 | `queue`/`scheduler`/`node` في حلقة إعادة تشغيل | لا يوجد `artisan` ولا `package.json` بعد | حارس خمول في الـ entrypoints |
| 8 | سكربت تهيئة MySQL يُسقط الإقلاع في CI وحده | بت التنفيذ غير مُلتزَم؛ المُدخل **يُصدِّر** السكربت بدل تنفيذه فيرث `set -euo pipefail` | `git update-index --chmod=+x` على السكربت |
| 9 | `up --wait` يفشل في CI على `queue`/`scheduler` | `healthcheck: disable: true` = لا حالة جاهزية، و`--wait` يرفض الانتظار على ما لا يحكم عليه | فحص `pgrep -f '[q]ueue:work'` (القوس حاسم كي لا يطابق الفحص نفسه) |
| 10 | `.env` للتطبيق غائب في CI فتصدر 19 تحذيرًا وCI أخضر | phpdotenv يبتلع الفشل، وPHPUnit يبلّغ التشخيصات المكبوتة ويخرج 0 | المُدخل ينشئ `.env` فارغًا موثَّقًا (الإعداد كله من بيئة الحاوية) |
| 11 | `vendor/` يبقى فارغًا وCOMPOSER_AUTO_INSTALL لا يعمل | الفحص على `-d vendor` والـvolume يُنشئ المجلد قبل أن يعمل السكربت | الفحص على `vendor/autoload.php` |
| 12 | صورة الإنتاج تحمّل صفر صنف من `App\` | `--classmap-authoritative` بُني من `composer.json` وحده قبل نسخ الكود | `composer dump-autoload` بعد `COPY backend/` مع إثبات `class_exists` وقت البناء |

**الخطأ رقم 3 هو الأخطر.** لولا التشغيل الفعلي لكانت قاعدة البيانات تُنشأ بترتيب
`utf8mb4_0900_ai_ci` — ترتيب غير حساس للتشكيل تتساوى فيه الأسماء العربية المختلفة
بهمزة أو حركة فقط. فهرس `UNIQUE` على أسماء الأشخاص كان سيرفض سجلات مختلفة
فعلياً، والسبب سطر تحذير واحد في السجل.

**مُتحقَّق منه بعد الإصلاح:** `أحمد` و`احمد` يُخزَّنان كسجلين متمايزين.

## 6. Xdebug

مُحمَّل لكنه **معطّل افتراضياً** (`XDEBUG_MODE=off`) لأن التفعيل الدائم يبطئ كل طلب.

```bash
# تصحيح تفاعلي (IDE يستمع على 9003)
XDEBUG_MODE=debug docker compose up -d php

# تغطية اختبارات
docker compose exec -e XDEBUG_MODE=coverage php php artisan test --coverage
```

## 7. الأسرار

لا يوجد أي سر في الكود أو الصور.

- `.env` مُستثنى في `.gitignore` و`.dockerignore`.
- `compose.prod.yaml` يستخدم `${VAR:?}` فيفشل بوضوح إن غاب السر.
- في الإنتاج تُحقن القيم من **مدير أسرار** عبر المنصة.
- كلمة مرور Redis تُمرَّر كوسيط سطر أوامر لا داخل `redis.conf` المُودَع في Git.

> **تنبيه:** غيّر كلمات المرور في `.env` قبل أي استخدام حقيقي: `openssl rand -base64 24`.

## 8. أعلام MySQL المطلوبة على الخدمة المُدارة

`log_bin_trust_function_creators=ON` مضبوط في `server.cnf` محليًّا، ويجب ضبطه **كعَلَم
على نسخة قاعدة البيانات المُدارة** أيضًا: بدونه تفشل أول هجرة تُنشئ مُحفِّزًا
(جدول append-only لسجل التدقيق مثلًا) بـ`ERROR 1419` عند أول نشر — تمامًا كما
فشلت محليًّا قبل السطر.

## 9. مشاكل شائعة

**البيئة لا تبدأ / أخطاء TLS أثناء البناء**
برامج الحماية التي تفحص HTTPS على المضيف (Web Shield في بعض مضادات الفيروسات)
تعترض اتصال الحاويات وتقدّم شهادتها الخاصة التي لا تثق بها الصور، فتفشل `apk add`
و`pecl` و`composer` بـ`SSL certificate problem`. الحلول بترتيب التفضيل: استثنِ
`dl-cdn.alpinelinux.org` و`pecl.php.net` و`registry.npmjs.org` و`repo.packagist.org`
من الفحص · أو أضف جذر شهادة المضاد إلى مخزن ثقة الحاوية · أو عطّل فحص HTTPS
مؤقتاً أثناء البناء.

**بوابة عقد OpenAPI حمراء على كودٍ لم تمسّه**
السبب غالبًا **قاعدة بيانات غير مبذورة** لا خللٌ في الكود (§1). العلاج `make db-init`
ثم أعد البوابة. **ولا يُعالَج بتخفيف البوابة.**

**البوابات تُعلن الخضرة وقد فشلت واحدة**
`bash scripts/quality.sh ... | tail -n` يجعل رمز الخروج رمزَ `tail` لا رمز
السكربت. احفظ الناتج في ملف بدل الأنبوب:
`bash scripts/quality.sh --with-tests > gates.log 2>&1; echo $?`.

**تعديلات MySQL في `server.cnf` لا تظهر**
الملف مخبوز في الصورة — أعد البناء: `make build` ثم `docker compose up -d mysql`.

**سكربتات `initdb/` لا تعمل**
تعمل مرة واحدة فقط عند أول تهيئة. لإعادة تشغيلها: `make clean` (يحذف البيانات).

**HMR لا يعمل في Vite**
إن كان المستودع على قرص Windows اضبط `CHOKIDAR_USEPOLLING=true` (الافتراضي هنا).
إن كان داخل WSL2 اضبطها `false` لتوفير المعالج.

**نهايات الأسطر CRLF تُسقط حاوية بـ`no such file or directory`**
النواة تقرأ shebang بـ`\r` فتبحث عن مُفسِّر لا وجود له. `.gitattributes` في الملف
الشخصي يفرض LF على كل ما يُنفَّذ أو يُقرأ داخل حاوية.
