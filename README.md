# Shift SDF — إطار شفت لتطوير البرمجيات

**Shift Software Development Framework.** إطار عمل لتطوير البرمجيات بمساعدة وكيل برمجي (Claude Code أو ما يماثله) تحت حوكمة مالك منتج بشري، مستخلَص من مشروع مرجعي كامل مرّ بجمع المتطلبات والتحليل والتصميم والتوثيق الهندسي والبرمجة والتشغيل على خادم تجريبي والفحص.

**لغة العمل:** العربية هي اللغة الرئيسية للوثائق والمحادثة. الإنجليزية للمعرّفات وأسماء الملفات والمصطلحات التقنية ورسائل Git وطلبات الدمج.

---

## 0. الفكرة في فقرة

البرمجيات تُبنى **على عقد مكتوب لا على ذاكرة**. كل سطر كود يُردّ إلى معرّف في وثيقة معتمدة، وكل وثيقة تُردّ إلى قرار معتمد من مالك المنتج، وكل ادّعاء إنجاز يُردّ إلى أمر يُعيد إنتاجه. الوكيل ينفّذ ويقترح ويقيس، ومالك المنتج يقرّر ويعتمد. وما ليس محسومًا لا يُخترع بل يُرفع بندًا مفتوحًا.

## 1. المبادئ الحاكمة

| # | المبدأ | ما يعنيه عمليًا |
|---|---|---|
| P-01 | **الوثيقة فوق الكود** | تعارضٌ بين الكود والوثيقة يُسجَّل ويُرفع. لا تُعدَّل الوثيقة لتوافق الكود ولا يُكتب كود يخالفها بصمت |
| P-02 | **مصدر حقيقة واحد لكل حالة** | رقم مكتوب في موضعين يتباعد. حالة المشروع في الـBaseline، وحالة التنفيذ في المتتبع، ولا تُكرَّر |
| P-03 | **كل معرّف يُردّ إلى مصدر** | كود بلا معرّف مصدري هو نطاق مُخترَع. أوقف واسأل |
| P-04 | **لا اختراع في المحسوم بشريًا** | المال والصلاحيات والقانون والخصوصية والملكية قرارات مالك المنتج حصرًا |
| P-05 | **البوابة تُثبَت بالفشل** | لا تُعدّ بوابة جودة عاملة قبل أن تفشل عمدًا مرة واحدة |
| P-06 | **القياس لا الادّعاء** | كل رقم في وثيقة مسنود بأمر يُعيد إنتاجه. «يعمل عندي» ليست حالة؛ الإقلاع النظيف هو الاختبار |
| P-07 | **الشريحة الرأسية** | تُبنى شريحة تعبر كل الطبقات وتنتهي بشيء يعمل، ثم تُعرض ويُتوقَّف |
| P-08 | **المُوقَف يُعلن نفسه** | بوابة تُوقَف بقرار تُعلن إيقافها في كل تشغيلة وتعمل حين تُطلب. المتخطّاة صمتًا كذب |
| P-09 | **التكافؤ البصري 1:1** | واجهة الإنتاج تُطابق النموذج المعتمد بلا ابتكار. الأداة تُغيَّر لا التصميم |
| P-10 | **ملكية واحدة لكل وظيفة مشتركة** | موديول مالك واحد، والاستهلاك عبر عقد مشترك، ولا مفتاح أجنبي ولا JOIN عابر |

## 2. المراحل الثلاث وملفات التعليمات الثلاثة

| المرحلة | المخرجات | ملف التعليمات في الإطار | يُثبَّت في المشروع باسم |
|---|---|---|---|
| **Phase 0 — التحليل ومواصفات الواجهات** | requirements · business-rules · user-flows · screen-inventory · permission-matrix · screens/SCR-* · module-readiness-review | `governance/phase0-instructions.md` | `CLAUDE-PHASE0.md` |
| **الهندسة — التوثيق الهندسي** | data-model · api-contracts · user-stories · test-scenarios · traceability-matrix | `governance/engineering-instructions.md` | `CLAUDE-ENGINEERING.md` |
| **التنفيذ — الكود** | backend · frontend · docker · scripts · CI | `governance/execution-instructions.md` | `CLAUDE.md` |

الملف المُحمَّل تلقائيًا في كل جلسة هو `CLAUDE.md` وحده، ولذلك يحمل قواعد المرحلة النشطة ويبدأ بـ**موجّه المراحل** الذي يحيل إلى الملفين الآخرين. قاعدة التفعيل: نوع المخرج يحدد الملف الحاكم، وعند الالتباس يُسأل مالك المنتج.

**ملف رابع يرافقها:** `PROJECT-BASELINE.md` (قالبه في `governance/project-baseline-template.md`) — حالة المشروع والمرحلة والحواجب وسلّم مصادر الحقيقة وبوابات القرار البشري.

**وفوقها جميعًا الدستور:** `governance/PROJECT-CONSTITUTION.md` يُنسخ كما هو إلى الجذر باسم `CONSTITUTION.md` — القواعد التي لا تتغيّر من مشروع إلى مشروع (المواد العشر · الأدوار والسلطة · سلّم الحقيقة · المنهجية · مبادئ البوابات · بوابات القرار البشري · Git والتوازي · السجلات · البيئة · الوكيل وذاكرته). الدستور يقول *ما الذي يُحكم وبأي مبدأ*، والإطار يقول *كيف*؛ وكل قاعدة في `CLAUDE.md` تُردّ إلى مادة فيه.

**وقبل Phase 0 حين يبدأ المشروع من ملفات خام** (عطاء · عرض · عقد · SRS · شاشات): **الدراسة التأسيسية** بموجّه `templates/discovery/discovery-brief-template.md` — جرد مصادر وتعارضات وفجوات وأسئلة بخيارات وتوصية وحكم جاهزية للمواصفات.

## 3. سلّم مصادر الحقيقة

من الأعلى إلى الأدنى. الأعلى يحكم عند التعارض، والإحالة **بالاسم لا برقم الإصدار** لأن رقم الإصدار داخل إحالة يتقادم بصمت.

1. قرارات مالك المنتج المعتمدة — `docs/00-product/project-decisions.md`
2. وثائق المنتج — BRD · المعجم · قواعد العمل العالمية · سجل الموديولات
3. حزمة الموديول (Phase 0 ثم الهندسية) — `docs/01-modules/[module]/`
4. التصميم — `design-system.md` · خرائط التنقل · النماذج الثابتة (مرجع مطابقة لا كود)
5. المعايير الهندسية والمعمارية — `standards/` · ADRs
6. منظومة التخطيط التنفيذي — ترتّب وتقيس ولا تُنشئ متطلبًا
7. الكود

## 4. مستويات الحوكمة

الإطار بكامله ثقيل على مشروع صغير. يُختار المستوى عند بدء المشروع ويُسجَّل في الـBaseline، ويُرفع المستوى لا يُخفَّض إلا بقرار.

| العنصر | **خفيف** (Light) | **قياسي** (Standard) | **كامل** (Full) |
|---|---|---|---|
| ملفات التعليمات | `CLAUDE.md` واحد مدمج | الثلاثة | الثلاثة + Baseline كامل |
| Phase 0 لكل موديول | requirements + business-rules + screens | الوثائق الست | الوثائق الست + بوابات الجودة التوثيقية الـ14 |
| الحزمة الهندسية | data-model + api-contracts | الخمس | الخمس + مصفوفة التتبع مفحوصة آليًا |
| سجل القرارات | ملف واحد | ملف + فهرس بالحالة | ملف + الفهارس الستة + طلبات التغيير |
| بوابات الكود | تنسيق · تحليل ساكن · أسرار · اختبارات | + الحدود المعمارية · المسارات · OpenAPI · التغطية | كل البوابات الـ17 بما فيها البصرية والإتاحة والتكامل |
| التوازي الكتابي | ممنوع (شجرة واحدة) | ممنوع | Pilot مضبوط حتى 3 شجرات معزولة؛ يُرفع الحدّ بقرار بعد قياس السعة (المرجع: 5) |
| البرامج متعددة الدورات | شرائح متفرقة | قوالب `templates/programmes/` | القوالب + فحص شامل قبل كل رفع تجريبي (`checklists/release-to-staging.md`) |
| CI | على `main` وطلبات الدمج | نفسه | نفسه + فحص الوثائق المحميّة + CODEOWNERS |
| تعريف الإنجاز | DoD-SL-01 · 02 · 04 | DoD-SL-01..06 · 08 · 09 | التسعة كلها |
| المراجعة | ذاتية | ذاتية + مراجع مستقل | ذاتية + مراجع مستقل + قالب PR إلزامي |

ما ليس في مستوى **خفيف** ليس اختياريًا فيه فحسب، بل **لا يُدَّعى**: مشروع خفيف لا يكتب «كل البوابات خضراء» بل «البوابات الأربع المفعّلة خضراء».

## 6. منظومة المعرّفات

| النطاق | المعرّف | المصدر |
|---|---|---|
| الموديول | `MOD-NN` + كود ثلاثي `XXX` | سجل الموديولات وخريطة الأسماء |
| Phase 0 | `FR-XXX-NNN` · `BR-XXX-NNN` · `UF-XXX-NNN` · `SCR-XXX-NNN` · `PM-XXX-NNN` | حزمة الموديول |
| الهندسة | `ENT-XXX-NNN` · `API-XXX-NNN` · `US-XXX-NNN` · `TS-XXX-NNN` · `ERR-XXX-*` · `PERM-XXX-*` (صفوف مصفوفة التتبع تُفهرَس بـ`FR-*`) | الحزمة الهندسية |
| القرارات | `DEC-<AREA>-NNN` · `DEC-XXX-IMP-NNN` · `CR-NNN` · `OPEN` | سجل القرارات |
| الحوكمة | `HG-E-NN` (هندسية) · `HG-I-NN` (تنفيذ) · `EV-NNNN` (دليل) · `COR-NN` (تصحيح) · `CFL-NNN` (تعارض) | Baseline · المتتبع |
| التنفيذ | `SL-XXX-NN` (شريحة) · `DoD-SL-NN` | المتتبع · DoD |
| البوابات | `QG-*` · `GATE-FE-NN` · `AS-NNN` | استراتيجية الأتمتة |

**قاعدتان:** رقم مأخوذ لا يُعاد استعماله أبدًا، ومعرّف لا يُعاد ترقيمه أبدًا. التفصيل في `governance/decisions/identifier-scheme-template.md`.

## 7. بوابات القرار البشري

الوكيل يتوقف ويرفع القرار لمالك المنتج في هذه الحالات، ولا يتجاوزها تفويض عام:

| البوابة | متى |
|---|---|
| **HG-I-01** | أي قيمة مالية أو نسبة أو رسم أو ضريبة في كود أو بذرة، ولو «مؤقتة» |
| **HG-I-02** | تحويل صف من مصفوفة الصلاحيات إلى قاعدة تفويض تقنية |
| **HG-I-03** | هجرة مُدمِّرة أو تشغيل هجرة على بيئة تحمل بيانات |
| **HG-I-04** | نقطة API تُستهلك من خارج المنصة أو تُصدِّر بيانات شخصية |
| **HG-I-05** | انحراف عن `data-model.md` أو `api-contracts.md` معتمد — يستلزم Change Request |
| **HG-I-06** | البناء على عنصر `PROPOSED` أو `OPEN` |
| **HG-I-07** | الدفع المباشر إلى `main` · النشر · تغيير CI أو إدارة الأسرار |
| **HG-I-08** | حذف أو نقل أي ملف من المستودع |

البوابات الهندسية `HG-E-*` في `governance/engineering-instructions.md`. وما يُمنع اختراعه (المال، المسؤولية القانونية، الصلاحيات، الملكية، الخصوصية، التوثيق، التدخل اليدوي) مُعدَّد في كل ملف تعليمات.

## 8. بوابات الجودة الآلية

أمر واحد هو مصدر الحقيقة لتسلسل الفحوص، والـMakefile وCI يفوّضان إليه:

```bash
bash scripts/quality.sh --with-tests
```

| # | البوابة | ما تفحصه |
|---|---|---|
| 1 | `QG-SYNC` | التزامات غير مدفوعة · عدد الشجرات · قفل التشغيل — أولًا لأنها الأرخص |
| 2 | التنسيق | Pint / Prettier |
| 3 | التحليل الساكن | PHPStan level 8 + Larastan |
| 4 | الحدود المعمارية | Deptrac + `arch-check.sh` — ملكية الجداول والعقود العابرة |
| 5 | تغطية السيناريوهات | كل اختبار موسوم بسيناريو موجود |
| 6 | مسارات الواجهة | `route-check.sh` — كل مسار مسنود بصف في سجل معتمد |
| 7 | الفحص الساكن للواجهة | ESLint + `tsc --noEmit` بصفر تحذير |
| 8 | `GATE-I18N` (ثنائي اللغة) | تطابق مفاتيح الكتالوجين · سقف النص الحرفي يتقلّص · جملة واحدة = مفتاح واحد. `N/A` بصوت في مشروع بلغة واحدة |
| 9 | اختبار المكوّنات | Vitest + RTL |
| 10 | كاشف الأسرار | `secret-scan.sh` |
| 11 | تدقيق الاعتماديات | `composer audit --locked` + `npm audit` |
| 12 | عقد OpenAPI | مُولَّد من الكود ومُقارَن بالملف الملتزَم |
| 13 | تدفقات الواجهة | Playwright Chromium |
| 14 | المطابقة البصرية | لقطات بعتبة صفر |
| 15 | الإتاحة | axe-core |
| 16 | التكامل | الواجهة على الخلفية الحقيقية |
| 17 | الاختبارات | PHPUnit على MySQL في حزمة معزولة |
| 18 | عتبات التغطية | من ناتج الاختبارات |

الافتراضي: **كلها مفعّلة**. الإيقاف يكون بقرار مسجَّل، وتُعلن البوابة إيقافها في كل تشغيلة، وتعمل بأمرها المفرد أو بـ`--include-suspended`، ويذكر تقرير الإغلاق عدد الموقَفات. وإيقاف كتابة الاختبارات لا يُطلق البند بل يحوّله إلى **دَين يُقاس** ويُقبل بقرار بحجمه، **وشرائح المال تُستثنى من الإيقاف** وتُكتب لها اختبارات خادم تُشغَّل قبل الدمج. التفصيل في `scripts/README.md` و`templates/implementation/definition-of-done.md`.

## 9. خطوات الاستخدام — من الدراسة إلى إنهاء المشروع

هذا القسم هو **دليل التنفيذ الذي يُتَّبع خطوةً خطوة**. كل مرحلة فيه لها: ما يدخلها، ومن يقرّر، وما يفعله الوكيل، وما يخرج منها، و**بوابة خروج** لا تُعبَر إلا باعتماد مالك المنتج المسجَّل. القاعدة الواحدة فوق المراحل كلها: **الوكيل ينفّذ ويقترح ويقيس ويتوقف؛ ومالك المنتج يقرّر ويعتمد** — ولا تُفتح مرحلة قبل إغلاق ما قبلها بقرار.

### 9.0 خريطة المراحل

| # | المرحلة | الملف الحاكم | بوابة الخروج |
|---|---|---|---|
| 0 | الدراسة التأسيسية (حين تبدأ من ملفات خام) | `templates/discovery/` | حكم جاهزية للمواصفات + إجابات العميل عن الأسئلة الحاجبة |
| 1 | تأسيس المشروع | `checklists/project-start.md` | القائمة مكتملة ومسجَّلة في الخط الأساسي §20 |
| 2 | وثائق المنتج وإغلاق القرارات | `governance/decisions/` | BRD والمعجم وسجل الموديولات معتمدة · لا قرار `OPEN` حاجب |
| 3 | Phase 0 — التحليل ومواصفات الواجهات (لكل موديول) | `CLAUDE-PHASE0.md` | اعتماد حزمة كل موديول · ثم التدقيق النهائي للوثائق واعتماد الخط الأساسي |
| 4 | التصميم والنماذج الثابتة | `docs/02-design/` · بوابات مرحلة الواجهة | نظام التصميم وخرائط التنقل معتمدة · النماذج مُدقَّقة ومعتمدة بصريًّا |
| 5 | المعمارية والمعايير (الموجات 0–2) | `standards/` · `CLAUDE-ENGINEERING.md` | ADR الحزمة والمعمارية والمعايير الأربعة عشر معتمدة |
| 6 | التوثيق الهندسي (الموجتان 3–4، لكل موديول) | `CLAUDE-ENGINEERING.md` | `DEVELOPMENT READY` لكل موديول · تدقيق هندسي عابر للموديولات |
| 7 | التخطيط التنفيذي | `templates/implementation/` | الخطة والمتتبع والاعتماديات معتمدة · نطاق الشريحة التأسيسية بقرار |
| 8 | التنفيذ — الشريحة التأسيسية ثم الشرائح الرأسية | `CLAUDE.md` | إغلاق كل شريحة بتقرير · إغلاق كل موديول بتدقيق وقرار |
| 9 | الاختبار والجودة | البوابات الآلية · `templates/programmes/qa-report-programme.md` | البوابات خضراء · برنامج تقرير الجودة مُغلق بفحص شامل |
| 10 | النشر على البيئة التجريبية والبرامج التكميلية | `checklists/release-to-staging.md` · ADR النشر | بصمة منشورة بأمر المالك · المفاتيح الكبيرة مطفأة حتى قراره |

**ثلاث حلقات تدور داخل كل مرحلة** (§9.12): حلقة إغلاق القرارات، وحلقة طلب التغيير، وحلقة التقرير والتوقف.

### 9.1 المرحلة 0 — الدراسة التأسيسية

تُنفَّذ حين تكون المدخلات ملفات خام (عطاء · عرض فني ومالي · عقد · SRS · شاشات · محاضر) ولا توجد وثيقة متطلبات معتمدة.

1. المصادر في `docs/source/` ولا تُمسّ. انسخ `templates/discovery/discovery-brief-template.md` إلى `PROMPT-DISCOVERY.md` واملأ `{{...}}`.
2. الوكيل يُنتج التقرير (Markdown + Word) في `docs/discovery/`: جرد المصادر `SRC-*` بسلطتها المرجعية · خريطة النطاق (`MOD-` · `FEAT-` · `SCR-` · `RPT-` · `KPI-` · `INT-` · `ROLE-`) · الأدوار · الشاشات · البيانات والمؤشرات · التكاملات · غير الوظيفي · الأمن · سجل التعارضات `CON-*` · الفجوات `GAP-*` · RAID · مصفوفة التتبع · **الأسئلة `Q-*` بخيارات وتوصية** · حكم الجاهزية.
3. **مالك المنتج/العميل يجيب عن الأسئلة الحاجبة للمواصفات** في جولات (≤ 8 أسئلة في الجولة). ما لم يُجَب عنه يبقى بافتراضه المؤقت ولا يُعدّ قرارًا.
4. **بوابة الخروج:** `READY_FOR_SPECIFICATION` (أو `READY_WITH_BLOCKERS` بحواجب مسمّاة بمالك وموعد). الإجابات تصير أول صفوف سجل القرارات في المرحلة 2.

### 9.2 المرحلة 1 — تأسيس المشروع

القائمة الكاملة في `checklists/project-start.md`. ترتيبها:

1. **قرارات المالك الأولى (تُسجَّل في الخط الأساسي):** اسم المشروع ومعرّفه · مستوى الحوكمة (§4) · الحزمة التقنية بـADR واحد · نموذج العمل والمراجع المستقل · تفويض الدمج (الافتراضي لا) · بيئة التشغيل (محلية حصرًا حتى قرار) · اللغات والظهور العام (`N/A` بصوت لما لا ينطبق) · سقف شجرات العمل.
2. **المستودع:** GitHub بفرع `main` محمي (فحص مطلوب «بوابات الجودة» · لا دفع مباشر) · نسخ `scripts/` و`profiles/<stack>/` · الخطافات · `.gitignore` مفحوص · لا سر.
3. **ملفات الجذر:** `CONSTITUTION.md` · `CLAUDE.md` · `CLAUDE-ENGINEERING.md` · `CLAUDE-PHASE0.md` · `PROJECT-BASELINE.md` — كل `{{...}}` مستبدَل (`grep -rn '{{' *.md` يعود فارغًا). `CLAUDE.md` يبدأ بموجّه المراحل ويقول إن المرحلة النشطة هي **Phase 0**.
4. **شجرة `docs/`** من القوالب، وسجل القرارات وفهارسه من `governance/decisions/`، و`identifier-alias-map.md`.
5. **سجل الموديولات** (`MOD-NN` · كود ثلاثي · مجلد توثيق · مجلد كود · بادئة جدول) في `module-registry.md` و`scripts/config/modules.tsv`، وملكية كل وظيفة مشتركة محسومة لموديول واحد.
6. **إثبات البوابات قبل أول شريحة:** إقلاع من نسخة نظيفة · كل بوابة مفعّلة أُسقطت بخرق متعمَّد وسُجّل الدليل `EV-*` · CI أخضر على `main` برقم تشغيلة · المُوقفات في `SUSPENDED_GATES` تُعلن نفسها.
7. **بوابة الخروج:** تسجيل اكتمال القائمة في `PROJECT-BASELINE.md §20` بتاريخ واعتماد.

### 9.3 المرحلة 2 — وثائق المنتج وإغلاق القرارات

1. `docs/00-product/`: `brd.md` (نطاق الأعمال المرجعي) · `glossary.md` · `business-rules-global.md` · `module-registry.md` · `project-decisions.md` وفهارسه الستة · `change-requests/` · `legal/` (نصوص السياسات **من المالك وحده**، بعلامة `DRAFT` حتى يكتبها `APPROVED`).
2. **كل ما لا يُحسم من الوثائق يُحوَّل إلى «قرار مطلوب»** بقالب `decision-request-template.md`: سؤال واحد · لماذا يهم وما يحجبه · خياران أو ثلاثة بأثرها · توصية · المتأثرات. يُعرض في جولات ≤ 8 أسئلة قابلة للإجابة بالرقم.
3. **الجواب يُسجَّل نصًّا** بين علامتَي تنصيص بتاريخه في `project-decisions.md` (`DEC-<AREA>-NNN`)، ويُحدَّث فهرس القرارات المفتوحة بتصنيف الحجب (`GLOBAL` · `MODULE-SPECIFIC` · `FEATURE-SPECIFIC`).
4. **ما يُمنع اختراعه لا يُسأل عنه بتوصية مُلزِمة:** المال · الصلاحيات · القانون · الخصوصية · الملكية · التوثيق · الظهور العام · الاستثناءات اليدوية — توصية مهنية مع لفت النظر إلى الخيار الأقل أثرًا، والقرار للمالك.
5. **بوابة الخروج:** BRD والمعجم وسجل الموديولات معتمدة؛ ولا قرار `OPEN` مصنَّف `GLOBAL` بلا مالك وموعد. **القرارات غير المحسومة لا توقف المشروع كله:** توقف الموديول أو الميزة التي تحجبها فقط، ويُرتَّب العمل على ما لا يعتمد عليها.

### 9.4 المرحلة 3 — Phase 0: التحليل ومواصفات الواجهات (لكل موديول)

الملف الحاكم `CLAUDE-PHASE0.md`. **موديول واحد في كل مرة**، بترتيب الاعتماديات لا بأرقام الموديولات، والوظائف المشتركة تُوثَّق عند مالكها أولًا (الهوية · الوسائط · الإشعارات · المدفوعات · الإعدادات · التدقيق).

1. **موجز تخطيط الموديول** أولًا (الهوية · ما يملكه وما يستهلكه · الأدوار · النطاق · الاعتماديات · القرارات المعتمدة والناقصة · المخاطر · تسلسل التوثيق · توصية بالبدء أو الإيقاف) ⟵ **لا توثيق قبل موافقة المالك على الموجز**.
2. **الوثائق بالترتيب وبوابات الانتقال:** `requirements.md` ⟵ `business-rules.md` ⟵ `user-flows.md` ⟵ فحص جاهزية الواجهات ⟵ `screen-inventory.md` + `permission-matrix.md` ⟵ `screens/SCR-*.md` (ملف لكل شاشة بمعايير قبولها). لا انتقال وقاعدة أعمال أو صلاحية حساسة غير محسومة — تُرفع «قرار مطلوب» ويُرحَّل الجزء المتأثر.
3. **بوابة الجودة التوثيقية لكل وثيقة** (`templates/quality-gates/`) مراجعةً ذاتية **قبل العرض**: تقرير أولًا بلا تعديل، إصلاح `Critical`/`High` ثم إعادة من الصفر، والتقرير في `docs/99-quality/` باسم الموديول والتاريخ.
4. **مراجعة التناسق** بين الوثائق الست والتحقق من الوظائف المشتركة، ثم `module-readiness-review.md` بحكم: جاهز · جاهز بشروط · غير جاهز.
5. **اعتماد المالك** للحزمة ⟵ يُسجَّل في frontmatter وسجل القرارات وأعمدة التقدم في `module-registry.md` ⟵ **تصير الحزمة محميّة** ⟵ STOP (`checklists/module-closure.md §أ`).
6. **عند حدّ أول مجموعة موديولات:** مراجعة المعلم (Project Milestone Review) على مستوى المشروع كله — حدود الموديولات والملكية والتعارضات والتكرار — تقريرًا بلا تعديل. **وعند اكتمال كل الموديولات:** التدقيق النهائي للوثائق (Final Documentation Audit) ⟵ **اعتماد الخط الأساسي للوثائق** في `PROJECT-BASELINE.md §20`.
7. **بوابة الخروج:** كل موديول في النطاق معتمدًا، والتدقيق النهائي بلا `Critical`/`High`، والخط الأساسي معتمدًا.

### 9.5 المرحلة 4 — التصميم والنماذج الثابتة

تُبنى **نماذج HTML ثابتة** تكون لاحقًا المرجع البصري والسلوكي المُلزِم للواجهة (`P-09`)، وليست كود إنتاج.

1. **`design-system.md`** (التوكنز · الخطوط · الاتجاه · المكوّنات ومبادئها · الإتاحة) ⟵ اعتماد المالك ⟵ محميّ ومرجع حاكم.
2. **خرائط التنقل** معتمدة قبل أول شاشة: خريطة الإدارة (سجل المسارات) وخريطة العملاء — كل مسار يُنسخ منها لاحقًا حرفيًّا ولا يُشتق.
3. **تمكين الهيكل (المرحلة 0 للنموذج):** القائمة والهيكل والإتاحة الأساسية والخط، بتقرير وبوابة خروج (صفر خطأ Console · صفر 404 · صفر طلب خارجي)، و**سجل المكوّنات المعتمدة** (`component-registry.md`) بحالات `APPROVED` · `PROVISIONAL` · `DEFERRED`.
4. **الشاشات دفعاتٍ** (B1, B2, …): لكل دفعة **فحص جاهزية** للمواصفات قبل البناء يرصد التعارضات الصامتة بين المصادر ويرفعها قرارًا (`DEC-Bn-UI-*`) ⟵ البناء من مواصفة الشاشة حرفيًّا (كل حقل وإجراء وحالة يُردّ إلى معرّف) ⟵ `ui-implementation-quality-gate.md` ⟵ تقرير الدفعة ⟵ اعتماد المالك البصري.
5. **التدقيق النهائي للنماذج** (واجهة العملاء · بوابة الإدارة) ثم **اعتماد المالك**؛ وتُسجَّل حالة النماذج في `PROJECT-BASELINE.md §7A`.
6. **بوابة الخروج:** نظام التصميم وخرائط التنقل والنماذج معتمدة. ما يُعدَّل بعدها في النموذج ⟵ طلب تغيير.

### 9.6 المرحلة 5 — المعمارية والمعايير (الموجات 0–2)

1. **الموجة 0 — المتطلبات المسبقة:** Git فعّال · `identifier-alias-map.md` · `CLAUDE-ENGINEERING.md` مثبَّت · بوابات الجودة الهندسية بأسمائها · **تدقيق الانتقال إلى المرحلة الهندسية** (يقترح الموديول التجريبي ويرصد المعرّفات الشاذة والقرارات الحاجبة).
2. **المعمارية:** `architecture.md` من `standards/architecture-template.md` + `ADR-ARCH-001` للحزمة التقنية (محسومة ولا يُعاد تقييمها) ⟵ تقرير اعتماد المعمارية ⟵ قرار المالك (`DEC-ARCH-*`). العناصر `PROPOSED` (خدمات سحابية · تخزين مؤقت · إهمال إصدارات) تُسمّى ولا يُبنى عليها.
3. **الموجة 1 — المعايير الأربعة عشر** من `standards/` بالترتيب، مُكيَّفة للمشروع (أسماء الموديولات المالكة · العملة · اللغة)، بتدقيق عابر للوثائق ⟵ اعتماد المالك ⟵ محميّة.
4. **الموجة 2 — السحابة والبيئات:** تُؤجَّل حتى قرار نشر (`HG-E-05`)؛ ما قبله محلي وCI حصرًا، ولا تكوين «استباقي».
5. **بوابة الخروج:** الموجتان 0 و1 معتمدتان في `PROJECT-BASELINE.md §19`.

### 9.7 المرحلة 6 — التوثيق الهندسي (الموجتان 3–4، لكل موديول)

الملف الحاكم `CLAUDE-ENGINEERING.md`. وثائق Phase 0 **محميّة** هنا؛ ما يناقضها يُرفع ولا يُصحَّح بصمت.

1. **الموجة 3 — الموديول التجريبي:** أصغر موديول بلا قرارات مفتوحة ولا اعتماديات مالية (المرجع: سجل التدقيق) لاختبار سلسلة التوليد كاملة قبل تعميمها ⟵ اعتماد المالك (`HG-E-02` · `HG-E-03` للنموذج والعقود الأولى).
2. **الموجة 4 — الباقي بترتيب يعتمده المالك** ويُسجَّل قرارًا، لا برقم الموديول؛ والموديول الذي يحجبه قرار يُؤخَّر لا يُقفز فوقه.
3. **لكل موديول:** موجز التخطيط الهندسي ⟵ موافقة المالك ⟵ `engineering-input-analysis.md` ⟵ `data-model.md` (بوابة + **اعتماد المالك**) ⟵ `api-contracts.md` (بوابة + **اعتماد المالك**) ⟵ `user-stories.md` ⟵ `test-scenarios.md` ⟵ `traceability-matrix.md` ⟵ `module-development-readiness-review.md` ⟵ اعتماد ⟵ STOP. بوابات `HG-E-01..06` (الكيان المشترك · ذرّية المال · تحويل الصلاحيات · API خارجية · ترقية خدمة سحابية · حذف ملف) تُعبَر بقرار قبل الكتابة.
4. **العقود العابرة** تُسجَّل في سجل العقود المشتركة عند الموديول المالك؛ وما نقص من الحزمة يُرفع `OPEN` لا يُملأ بالاجتهاد.
5. **عند اكتمال الموجة 4:** تدقيق هندسي نهائي عابر للموديولات (مصالحة العقود والأحداث والمعرّفات) ⟵ `CLEARED` ⟵ حالات الجاهزية في `PROJECT-BASELINE.md §7B` (`DEVELOPMENT READY` · `CONDITIONALLY READY` · `NOT READY`).
6. **بوابة الخروج:** كل موديول في نطاق المرحلة `DEVELOPMENT READY` أو بشروط مسمّاة، والتكامل العابر `CLEARED`.

### 9.8 المرحلة 7 — التخطيط التنفيذي

1. انسخ `templates/implementation/` إلى `docs/03-development/implementation/`: الخطة الرئيسية (مستويات التخطيط · نظام `SL-`/`CMP-`/`TSK-`) · خطط الموديولات · **المتتبع** (مصدر حالة التنفيذ الوحيد، بـ`Last Verified Commit`) · تعريف الإنجاز · **الاعتماديات والموجات بالقياس** (لا موديولان متوازيان يتشاركان جدولًا أو عقدًا أو حدثًا) · المخاطر وبوابات القرار.
2. **نطاق الشريحة التأسيسية بقرار** (`DEC-FS-001`): أساس تقني وإثبات معايير — حزمة الحاويات · CI · البوابات مُثبتة بالخرق · النواة المشتركة (الأخطاء · الاستجابة · التتبع) · الموديولات التأسيسية (الإعدادات · الهوية · التدقيق) إلى حدّ يُثبت أن المعايير تعمل **لا حزمة مكتملة** — بتعريف إنجاز مكتوب بنوده.
3. **إن كانت الحزم الهندسية قديمة أو تغيّر المشروع من حولها** (مرحلة ثانية): مراجعة جاهزية المرحلة بقالب `templates/programmes/phase-readiness-review.md` قبل البرمجة.
4. **بوابة الخروج:** الخطة والاعتماديات معتمدة، ونطاق الشريحة التأسيسية وتعريف إنجازها بقرار، والمتتبع بصف لكل شريحة بحالة `NOT_STARTED`.

### 9.9 المرحلة 8 — التنفيذ

الملف الحاكم `CLAUDE.md`. **الحزمة الهندسية هي مواصفة التنفيذ؛ ولا كود بلا معرّف مصدري.**

1. **الشريحة التأسيسية:** تُبنى بنود `DEC-FS-001` ⟵ **الإقلاع البارد من نسخة نظيفة وأول تشغيلة CI حقيقية** (تكشف ما لا يظهر على جهاز التطوير: بت التنفيذ · نهايات الأسطر · هوية المستخدم · الدافئ مقابل البارد) ⟵ تدقيق إغلاق ⟵ **قرار إغلاق** (`DEC-FS-003`) يرفع الحاجب عن الشرائح التالية. لا توازٍ قبل إغلاقها.
2. **لكل شريحة رأسية بعدها** (`checklists/slice-closure.md`): تعريف الجاهزية (طلب صريح · الحزمة تسمح · لا `OPEN` حاجب · البوابات خضراء **قبل** البدء) ⟵ **موجز الشريحة** ⟵ موافقة ⟵ التسلسل: الهجرة ⟵ النموذج ⟵ الخدمة ⟵ العقد المشترك ⟵ الطبقة الخارجية ⟵ الاختبارات الموسومة بسيناريوها ⟵ `bash scripts/quality.sh --with-tests` ⟵ التوثيق (المتتبع · التتبع · سجل القرارات · طلب التغيير) ⟵ **تقرير الإغلاق** بصيغته الثابتة ⟵ **STOP**. تعريف الإنجاز تسعة بنود كلها بدليل يُعاد إنتاجه، وما لا ينطبق يُعلَن.
3. **الواجهة:** الشاشة تُؤلَّف من مواصفتها والنموذج الثابت **1:1** بلا ابتكار (إعادة تأليف لا استيراد)، ومسارها من سجل التنقل حرفيًّا، وبوابات الواجهة (الساكنة · المكوّنات · التدفقات · البصرية بعتبة صفر · الإتاحة) ضمن التسلسل الواحد.
4. **إغلاق الموديول** (`checklists/module-closure.md §ج`): جرد مقيس (النقاط · الشاشات · الكيانات · السيناريوهات مقابل الحزمة) ⟵ تدقيق إغلاق في `docs/99-quality/` ⟵ حكم `CLOSED` أو `CLOSED_WITH_DECLARED_DEFICIT` بدَين مسمّى ⟵ قرار المالك (`DEC-CLOSE-*`).
5. **التوازي المضبوط** حين توجد موديولات مستقلة (§8.4 في `CLAUDE.md`): شجرة معزولة لكل مهمة بـ`agent-worktree.sh` · كاتب واحد لكل موديول · الملفات المشتركة لمهندس التكامل تسلسليًّا (الدورة 0 أولًا) · فرع تكامل واحد وطلب دمج واحد لكل دورة · الدمج بشروطه الستة إن فُوِّض · ترتيب المسارات بالاعتماديات.
6. **أثناء التنفيذ تتكرر الحلقات الثلاث** (§9.12): كل انحراف عن العقد طلب تغيير قبل البناء؛ كل قرار بتفويض موسوم ومعروض؛ كل شريحة تقرير وتوقف.
7. **بيانات العرض** (`DemoDataSeeder`) لحسابات العرض على بيئة المالك المحلية، تُعاد من أمر؛ والبذور الحقيقية (المرجعية · المحتوى · السياسات) في البذّار الذي يعمل على كل بيئة.
8. **بوابة الخروج للمرحلة:** كل موديول في نطاقها مُغلق بقرار، والديون المعلَنة (اختبارات موقوفة · خطوط أساس بصرية ناقصة) مقبولة بقرار **بحجمها المقيس**.

### 9.10 المرحلة 9 — الاختبار والجودة

الجودة ليست مرحلة لاحقة بل **بوابات في كل شريحة** وبرنامج عند حدّ كل مرحلة.

1. **الآلي في كل شريحة:** تسلسل `quality.sh` (18 بوابة) أخضر بتشغيل واحد وCI على مرشّح الدمج؛ المُوقف بقرار يُعلن نفسه؛ وشرائح المال مستثناة من أي إيقاف لكتابة الاختبارات.
2. **القبول اليدوي لكل موديول:** يبني الوكيل ملف حالات القبول `QA-<CODE>-NNN` ممّا هو مطوَّر فعلًا (ستة أوراق — `qa-report-programme.md §1.2`) ويسلّمه لفريق الفحص أو للمالك.
3. **برنامج تقرير الجودة** حين يصل تقرير الملاحظات: فرز على الكود ⟵ **أحكام المالك بندًا بندًا** (`DEC-QA-IMP-001`) ⟵ دورات تنفيذ بمسارات متوازية بقرار لكل دورة (المنفَّذ · بالتفويض · المرفوع) ⟵ عمود «رد فريق التطوير» ⟵ **الفحص الشامل في حزمة نظيفة** بثلاثة مسارات (تحقق البنود · انحدار المجموعات الموقوفة · قبول يدوي) ⟵ جولة إصلاح ⟵ قرار «توصيات» يجيب عنه المالك.
4. **جولة المالك اليدوية** على البيئة التجريبية بعد كل نشر؛ ملاحظاتها تُفتح بنودًا بأرقامها لا تُصلَح صامتًا.
5. **بوابة الخروج:** لا بند «مفتوح» بلا سبب ومالك، والفحص الشامل مُغلق بقرار، ونتيجته في المتتبع.

### 9.11 المرحلة 10 — النشر على البيئة التجريبية والبرامج التكميلية

1. **قرار البيئة التجريبية** (`HG-E-05` · ADR نشر): المزوّد والمنطقة وخدمات البيانات والكلفة التقريبية — **لا مورد مدفوع قبل عرض اسمه وحجمه وكلفته واعتماده** · الأسرار في مدير أسرار يُدخلها المالك · الصور موسومة ببصمة Git · لا `latest` · لا هجرة مُدمِّرة تلقائيًّا · الإنتاج يبقى خارج النطاق بقرار مستقل.
2. **سكربت نشر في المستودع** (المرجع: `gcp-staging.sh` و`docker/cloudrun/` — خاص بالمزوّد ولا يُنقل في الإطار) ونشر الحافة إن وُجدت (`SEO-030`).
3. **قبل كل رفع:** `checklists/release-to-staging.md` — أمر المالك بنصّه · الدمج الكامل · الفحص الشامل بعد برنامج متعدد الدورات · مفاتيح الميزات الكبيرة مطفأة · لا سر حيّ · البذور الحقيقية وحدها · فحص بعد النشر قابل لإعادة التشغيل.
4. **البرامج التكميلية بقرار المالك وبقوالبها:** الظهور في محركات البحث (`seo-public-visibility-standard.md`) ثم اللغة الثانية (`internationalization-standard.md` · `i18n-programme.md`) — كلٌّ ببرنامج يبدأ بالقرارات ثم التأمين ثم الشرائح ثم الإغلاق والمفتاح مطفأ حتى يأمر المالك.
5. **بوابة الخروج:** البصمة المنشورة = `main`، مسجَّلة في المتتبع والخط الأساسي، وجولة المالك عليها مكتملة.

### 9.12 المرحلة 11 — القبول والإنهاء

1. **بدء UAT** (`HG-E-06`) بعد اكتمال موديول واحد على الأقل خادمًا وواجهةً، على البيئة التجريبية ببيانات تجريبية وحسابات مبذورة بسكربت؛ وبملفات القبول لكل موديول وتقرير ملاحظات بالأعمدة المعتمدة.
2. **ما يقرّره المالك مسبقًا ويُسجَّل:** مدة UAT · التشغيل التجريبي بعده · محضر النتائج والأخطاء والملاحظات المؤجَّلة · شرط القبول النهائي (المرجع: شهر تشغيل بعد UAT وإصلاح الحرج ثم محضر قبول).
3. **إغلاق المرحلة** (`checklists/phase-closure.md`): جرد مقيس لكل موديول (`STALE — REVERIFY` لما تخلّف عن `HEAD`) · كل `OPEN` محسوم أو مرحَّل بمعرّفه · كل قرار بتفويض مثبَّت أو منقوض · تشغيلة كاملة `--include-suspended` مرة واحدة بنتيجة مُعلَنة لكل بوابة · إقلاع من نسخة نظيفة · **سجل ديون الحوكمة** (`PROJECT-BASELINE.md §22`) · حكم `CLOSED` · `CONDITIONALLY CLOSED` · `NOT CLOSED` بقرار المالك.
4. **حزمة التسليم:** الوثائق المعتمدة بإصداراتها · `openapi.json` المُولَّد · دليل التشغيل (`docker/README.md` ودليل التشغيل بلا Docker للعرض) · النصوص القانونية بعلامة `APPROVED` من المالك · حسابات الإدارة الأولى بسكربت · تدوير كل سر عرفه الفريق · اختبار استعادة نسخة احتياطية · سجل القرارات والمتتبع بآخر بصمة.
5. **الإنتاج قرار مستقل** بـADR وبوابة `HG-I-07`: لا يُنشر إلا بأمر المالك، بعد قبول UAT، بالبصمة المقبولة نفسها.
6. **إغلاق المشروع:** قرار مسجَّل، والدروس المدفوع ثمنها تُستخلص إلى `lessons/` والقوالب إلى الإطار بإصدار جديد (§10) — فالمشروع التالي يبدأ من حيث انتهى هذا.

## 10. العلاقة بالمشروع المرجعي

الإطار نفسه يخضع لقواعده: تغييره يكون بإصدار جديد مسجَّل في `CHANGELOG.md`، ولا يُعدَّل معيار بصمت.
